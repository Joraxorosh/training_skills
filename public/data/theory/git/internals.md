Большинство «магии» Git становится очевидной, когда понимаешь его модель данных. Git — это контентно-адресуемое хранилище объектов плюс набор подвижных указателей на них. Ветки, теги, HEAD, rebase и reflog — всё это надстройки над двумя простыми идеями: объекты неизменяемы и адресуются хешем содержимого, а ссылки — это просто файлы с хешами.

## Четыре типа объектов

В `.git/objects` лежат объекты всего четырёх типов:

| Тип | Что хранит | Пример содержимого |
|---|---|---|
| **blob** | Содержимое файла (без имени и прав) | байты файла |
| **tree** | Каталог: режим, тип, SHA и имя каждой записи | `100644 blob ce01… a.txt` |
| **commit** | tree, родители, автор, коммиттер, сообщение | `tree 2e81…`, `parent d997…` |
| **tag** | Аннотированный тег: объект, имя, автор, сообщение | `object 20b2…`, `type commit` |

Посмотреть объект изнутри позволяет `git cat-file`:

```bash
git cat-file -t HEAD          # commit
git cat-file -p HEAD          # tree, parent, author, committer, сообщение
git cat-file -p HEAD^{tree}   # содержимое корневого каталога
git cat-file -p HEAD:src/app.py   # содержимое файла в коммите
```

Важно: **коммит хранит снимок, а не дифф**. Дифф Git вычисляет на лету, сравнивая tree коммита и родителя. Лёгкий тег (`git tag v1`) объекта не создаёт — это просто ссылка на коммит; аннотированный (`git tag -a v1 -m ...`) создаёт объект tag.

## Хеши и контентная адресация

Имя объекта — SHA-1 (в новых репозиториях может быть SHA-256) от заголовка и содержимого. Для blob это `blob <размер>\0<данные>`:

```bash
echo hello > a.txt
git hash-object a.txt            # ce013625030ba8dba906f756967f9e9ca394464a
printf 'blob 6\0hello\n' | sha1sum   # тот же хеш
```

Следствия:

- Одинаковое содержимое хранится один раз, даже в разных файлах и коммитах.
- Объекты неизменяемы: «изменить» коммит нельзя, можно только создать новый.
- Коммит содержит SHA родителя, поэтому изменение любого старого коммита меняет хеши всех потомков. Именно поэтому amend, rebase и filter-repo «переписывают историю».

Blob создаётся уже при `git add`, а tree и commit — при `git commit`.

## Ссылки, ветки и HEAD

Ветка — это файл `.git/refs/heads/<имя>` с 40 символами хеша (после `git gc` — строка в `.git/packed-refs`). Создать ветку — значит записать один хеш, поэтому ветки в Git дешёвые.

```bash
cat .git/HEAD               # ref: refs/heads/main
cat .git/refs/heads/main    # d997999897eb6f0cb3b0218a273a89e7298d1826
```

**HEAD** обычно символическая ссылка на ветку: новый коммит двигает ветку, а HEAD следует за ней. В состоянии **detached HEAD** файл `.git/HEAD` содержит сразу хеш коммита. Коммиты, сделанные в таком состоянии, не принадлежат ни одной ветке; при переключении Git предупредит «you are leaving 1 commit behind», и сохранить их можно командой `git branch rescue <sha>`.

## Индекс и устройство .git

Индекс (`.git/index`) — бинарный файл со списком путей, хешей их blob-ов и метаданных файловой системы. Коммит строится именно из индекса, а не из рабочей директории.

- `objects/` — объекты (loose в `xx/yyyy…` и упакованные в `pack/`).
- `refs/heads`, `refs/tags`, `refs/remotes` — ветки, теги, remote-tracking ветки.
- `HEAD`, `index`, `config`, `hooks/`, `logs/` (reflog), `packed-refs`.

## Packfiles, gc и reflog

Новые объекты пишутся как отдельные сжатые zlib файлы (loose). `git gc` упаковывает их в packfile (`.pack` + `.idx`) с дельта-сжатием похожих объектов, переносит ссылки в `packed-refs` и удаляет недостижимые объекты старше grace-периода (по умолчанию две недели). База для дельты выбирается эвристикой и не обязана быть предыдущей версией файла.

**Reflog** (`.git/logs/`) — локальный журнал перемещений HEAD и веток: каждый commit, reset, checkout, rebase. Пока объект упомянут в reflog, gc его не удалит. По умолчанию записи живут 90 дней, для недостижимых коммитов — 30. Reflog не передаётся при push и clone.

## Remote-tracking ветки, fetch и refspec

`origin/main` — локальная копия состояния ветки на сервере на момент последней синхронизации. Её обновляют только `fetch`, `pull` и `push`. `git fetch` скачивает объекты и двигает remote-tracking ветки, не трогая ваши ветки и рабочую директорию; `git pull` — это fetch плюс merge (или rebase при `pull.rebase=true`).

Соответствие задаёт refspec в `.git/config`:

```ini
[remote "origin"]
    fetch = +refs/heads/*:refs/remotes/origin/*
```

Слева — ссылки на сервере, справа — куда их записать локально; `+` разрешает не-fast-forward обновление (ветку на сервере могли переписать).

```bash
git log main..origin/main   # что пришло с сервера и ещё не в main
git log origin/main..main   # мои незапушенные коммиты
```

## Частые вопросы на собеседовании

- Хранит ли Git диффы? → Логически — снимки (tree), физически в packfile — дельты для экономии места.
- Что такое ветка? → Файл с хешем коммита, подвижный указатель.
- Что такое detached HEAD и чем опасен? → HEAD указывает на коммит, а не на ветку; новые коммиты легко «потерять», но их видно в reflog.
- Почему rebase меняет хеши? → Меняется родитель, а он входит в содержимое коммита.
- Чем fetch отличается от pull? → fetch обновляет только `origin/*`, pull ещё и интегрирует изменения в текущую ветку.
- Как найти коммит, потерянный после detached HEAD? → `git reflog` или `git fsck --lost-found`.

## Шпаргалка

```bash
git cat-file -t|-p <obj>       # тип / содержимое объекта
git hash-object file           # хеш, который получит blob
git rev-parse HEAD             # хеш, на который указывает ссылка
git ls-files -s                # содержимое индекса
git count-objects -v           # loose и упакованные объекты
git gc                         # упаковка и уборка
git reflog [ветка]             # журнал перемещений
git fsck --lost-found          # висящие коммиты и blob-ы
git log A..B                   # коммиты из B, которых нет в A
```
