Код-ревью — главный механизм контроля качества и обмена знаниями в команде. Хорошее ревью ловит баги и архитектурные проблемы, плохое превращается в спор о кавычках или в формальный аппрув. На собеседовании проверяют, умеете ли вы готовить удобные для ревью изменения, давать полезную обратную связь и автоматизировать то, что не должны проверять люди.

## Хороший pull request

- **Маленький и сфокусированный**: одна задача, по возможности до нескольких сотен строк. Рефакторинг и новая функциональность — отдельными PR.
- **Описание**: что и зачем изменено, как проверить, ссылка на задачу, скриншоты для UI, известные ограничения.
- **Самопроверка** перед запросом ревью: прочитать свой дифф, убрать отладочный код, убедиться, что CI зелёный.
- **Draft PR** для раннего фидбэка по подходу, пока работа не закончена.

> Качество ревью падает с размером: 50 строк читают внимательно, 2000 — по диагонали. Если PR огромный, честнее попросить разбить его или провести совместный разбор, чем поставить формальный аппрув.

## Что смотрит ревьюер

1. Корректность: граничные случаи, обработка ошибок, конкурентность.
2. Дизайн: правильное ли место для логики, не нарушены ли границы модулей.
3. Читаемость: имена, размер функций, понятность без автора рядом.
4. Тесты: проверяют ли они поведение, а не реализацию.
5. Безопасность и производительность: инъекции, секреты, N+1 запросы.

Комментарии формулируют про код, а не про человека, и разделяют блокирующие замечания и пожелания: префиксы `nit:`, `question:`, `suggestion:`. Отступы и порядок импортов не должны обсуждаться вообще — это работа форматтера и линтера.

## Conventional Commits и версии

Формат сообщения: `<type>(<scope>)!: <описание>`.

```text
feat(api): add /orders/export endpoint
fix: correct rounding in totals
docs: update README
feat(api)!: remove deprecated v1 endpoints
```

| Тип коммита | Изменение версии |
|---|---|
| `fix` | PATCH: 1.4.2 → 1.4.3 |
| `feat` | MINOR: 1.4.2 → 1.5.0 |
| `!` или футер `BREAKING CHANGE:` | MAJOR: 1.4.2 → 2.0.0 |
| `docs`, `chore`, `test`, `refactor` | не меняют версию |

Инструменты вроде semantic-release и release-please берут «старший» тип с последнего релиза, поднимают версию, ставят тег и генерируют CHANGELOG. Правила semver: части сравниваются как числа (`1.10.0 > 1.9.0`), пре-релиз `1.0.0-rc.1` младше `1.0.0`, метаданные `+build.5` не влияют на порядок, в `0.y.z` API может меняться в любой момент.

## Автоматические проверки и защита веток

- **CI на PR**: сборка, тесты, линтеры, статический анализ, проверка покрытия и уязвимостей зависимостей.
- **Branch protection**: обязательный PR, N одобрений, обязательные status checks, запрет force-push и удаления ветки.
- **CODEOWNERS**: автоматически назначает ревьюеров по путям (`/infra/ @org/platform`), а с опцией «Require review from Code Owners» без них не влить.
- **Merge queue**: при требовании «up to date with main» очередь сама проверяет PR поверх актуального main и вливает по очереди, убирая гонку ручных обновлений.
- **Статический анализ**: SonarQube, ESLint, mypy, Semgrep/CodeQL (SAST) — находят проблемы без запуска кода.

## Чистый код: DRY, KISS, YAGNI

| Принцип | Суть | Типичное нарушение |
|---|---|---|
| DRY | Одно знание — одно место | Одна бизнес-формула скопирована в три сервиса |
| KISS | Простейшее работающее решение | Три слоя абстракций для одной реализации |
| YAGNI | Не делать «на будущее» | Настройки и плагины, которые никто не просил |
| SRP | Одна причина для изменения | Класс, который и считает, и пишет в БД, и шлёт email |

DRY касается знаний, а не похожего текста: два одинаковых на вид куска с разным смыслом объединять вредно. Имена должны раскрывать намерение (`retryCount`, а не `n`), функции — делать одну вещь на одном уровне абстракции.

## Технический долг, рефакторинг и переписывание

Технический долг — осознанные или случайные компромиссы, за которые платят «процентами»: каждая следующая задача идёт медленнее. Чтобы им управлять, его делают видимым в бэклоге, связывают с метриками (lead time, частота инцидентов) и выделяют регулярную долю ёмкости, например 15–20%.

**Рефакторинг** — изменение структуры без изменения поведения, маленькими шагами под защитой тестов. **Переписывание с нуля** рискованно: теряются неявные знания старого кода, долго нет ценности и приходится поддерживать две системы. Обычно надёжнее паттерн strangler fig — постепенная замена частей системы.

## Частые вопросы на собеседовании

- Каким должен быть хороший PR? → Маленьким, с описанием «что и зачем», зелёным CI и самопроверкой.
- Как давать фидбэк на ревью? → Про код, а не про человека; разделять блокирующее и `nit:`; задавать вопросы.
- Какую версию даст `feat!:`? → MAJOR.
- Рефакторинг или переписать? → Чаще инкрементальный рефакторинг/strangler fig, переписывание — когда старое действительно нельзя развивать.
- Как убедить бизнес заняться техдолгом? → Перевести в метрики и деньги, выделять фиксированную долю спринта.

## Шпаргалка

```text
PR: маленький, «что/зачем/как проверить», ссылка на задачу
Комментарии: blocking vs nit:, про код, а не про автора
Commits: fix → PATCH, feat → MINOR, ! / BREAKING CHANGE → MAJOR
Защита main: PR + approvals + status checks + no force-push
CODEOWNERS: ревьюеры по путям
Автоматизировать: formatter, linter, tests, SAST
DRY / KISS / YAGNI / SRP
Рефакторинг = структура меняется, поведение нет
```
