Ветвление в Git дешёвое, поэтому основная сложность не в создании веток, а в их интеграции: как сливать, когда переписывать историю, как разрешать конфликты и какую модель ветвления выбрать команде. На собеседовании ждут понимания разницы merge/rebase/squash, «золотого правила» rebase и умения объяснить, почему ours/theirs иногда «перевёрнуты».

## Способы интеграции

| Способ | Что происходит | История |
|---|---|---|
| Fast-forward | Указатель ветки просто перематывается вперёд | Линейная, без нового коммита |
| Merge-коммит | Создаётся коммит с двумя родителями | Сохраняет ветвление как было |
| Squash | Все изменения ветки — одним новым коммитом с одним родителем | Линейная, коммиты ветки теряются |
| Rebase + ff | Коммиты ветки пересоздаются поверх цели | Линейная, хеши меняются |

Fast-forward возможен, только если текущая ветка — предок сливаемой. `--no-ff` заставляет создать merge-коммит, `--ff-only` запрещает всё, кроме перемотки:

```bash
git merge --ff-only feat
# fatal: Not possible to fast-forward, aborting.
```

После squash-merge Git не считает коммиты ветки слитыми (`git branch -d` откажется её удалять), поэтому такую ветку удаляют, а не продолжают.

## Rebase и золотое правило

`git rebase main` на ветке feature по очереди переприменяет ваши коммиты поверх main. Это новые коммиты с новыми хешами. **Золотое правило:** не ребейзить коммиты, на которых уже основана чужая работа. Свою личную ветку в PR ребейзить можно, но пушить её придётся через `--force-with-lease`.

```bash
git rebase -i HEAD~4                 # pick, reword, edit, squash, fixup, drop
git commit --fixup a1b2c3d           # коммит "fixup! ..."
git rebase -i --autosquash a1b2c3d~1 # сам поставит fixup куда нужно
git rebase --onto main feature-a feature-b  # пересадить feature-b без feature-a
```

`cherry-pick` копирует отдельный коммит (новый хеш); `-x` добавляет в сообщение строку `(cherry picked from commit …)` — удобно при бэкпортах.

## Конфликты и ours/theirs

Конфликт возникает, когда обе стороны изменили одни и те же строки:

```text
<<<<<<< HEAD
timeout = 30
||||||| f526a0f
timeout = 10
=======
timeout = 60
>>>>>>> feat
```

Блок между `|||||||` и `=======` (база, общий предок) показывается при `merge.conflictStyle=diff3` или `zdiff3` — очень рекомендуется. Порядок действий: отредактировать файл, `git add`, затем `git commit` или `git merge --continue`. Передумали — `git merge --abort`.

> При merge «ours» — текущая ветка, «theirs» — сливаемая. При **rebase** наоборот: Git стоит на main и применяет ваши коммиты, поэтому `--ours` — это main, а `--theirs` — ваш коммит.

## Стратегии слияния и rerere

С Git 2.34 стратегия по умолчанию — **ort** (замена `recursive`): быстрее и лучше обрабатывает переименования. `octopus` используется для слияния 3+ веток.

- `-X ours` / `-X theirs` — опции ort: конфликтные фрагменты берутся с одной стороны, а неконфликтные изменения обеих сторон сохраняются.
- `-s ours` — отдельная стратегия: результат равен текущей ветке, изменения другой полностью игнорируются (merge-коммит при этом создаётся).

**rerere** (`git config rerere.enabled true`) запоминает ваши разрешения конфликтов и применяет их автоматически при повторе — спасает при регулярных rebase долгоживущей ветки.

## Модели ветвления

| Модель | Ветки | Когда подходит |
|---|---|---|
| Git Flow | `main`, `develop` + `feature/*`, `release/*`, `hotfix/*` | Версионные релизы, несколько поддерживаемых версий |
| GitHub Flow | `main` + короткие ветки через PR | Веб-сервисы с непрерывным деплоем |
| Trunk-based | Ствол + ветки на часы/день, feature flags | Высокая частота деплоя, сильный CI |

**Feature flags** отделяют деплой от релиза: незаконченный код вливается в ствол выключенным, включается постепенно и выключается без отката. Цена — дополнительные ветви кода, которые нужно тестировать, и долг из старых флагов.

## Force-push безопасно

`git push --force` перезаписывает ветку на сервере безусловно. `--force-with-lease` сначала проверяет, что ветка на сервере совпадает с вашей `origin/<branch>`; иначе push отклоняется с `stale info`. Ловушка: фоновый `git fetch` в IDE обновит `origin/<branch>`, и проверка пройдёт. Надёжнее указывать ожидаемый SHA или добавлять `--force-if-includes`.

## Частые вопросы на собеседовании

- Merge или rebase? → Rebase для чистой истории своей ветки, merge для интеграции общих веток; никогда не ребейзить опубликованное, с чем работают другие.
- Что такое fast-forward? → Перемотка указателя без нового коммита, когда история не разошлась.
- Почему ours/theirs меняются при rebase? → Rebase применяет ваши коммиты поверх upstream, «наша» сторона — upstream.
- Чем `-X ours` отличается от `-s ours`? → Первое решает только конфликты, второе выбрасывает все изменения другой ветки.
- Git Flow или trunk-based? → Зависит от частоты релизов; для continuous delivery — trunk-based с feature flags.

## Шпаргалка

```bash
git merge --no-ff | --ff-only | --squash feat
git merge --abort / git merge --continue
git rebase main / git rebase -i HEAD~3 / git rebase --abort
git rebase --onto <новая база> <старая база> <ветка>
git cherry-pick -x <sha>
git checkout --ours|--theirs <file>
git config merge.conflictStyle zdiff3
git config rerere.enabled true
git push --force-with-lease
```
