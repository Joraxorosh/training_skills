Память в Linux — одна из самых частых тем на собеседованиях DevOps и SRE: почему `free` показывает почти ноль свободной памяти, чем RSS отличается от VSZ, когда приходит OOM killer и почему контейнер с кодом 137 «умер от памяти», хотя на хосте её полно. Ключевая идея: незанятая RAM — потерянная RAM, поэтому ядро заполняет её кэшем и освобождает по требованию.

## Виртуальная память, RSS и VSZ

Каждый процесс видит собственное **виртуальное адресное пространство**. Ядро отображает его страницы (обычно 4 КиБ) на физическую RAM, файлы или swap через таблицы страниц. Физическая страница выделяется **лениво** — при первом обращении (page fault).

- **Minor page fault** — страница уже есть в памяти или её нужно просто выделить.
- **Major page fault** — нужно чтение с диска (swap или файл), это дорого.

| Метрика | Что показывает |
|---|---|
| VSZ (VIRT) | Весь размер виртуального адресного пространства, включая неиспользуемое |
| RSS (RES) | Страницы процесса, находящиеся в RAM, включая общие |
| PSS | RSS, в которой общие страницы поделены между процессами |
| USS | Только уникальные страницы процесса |

Поэтому `malloc(1 ГиБ)` увеличит VSZ, но не RSS, пока память не будет записана. А сумма RSS всех процессов может превышать объём RAM, потому что libc и shared memory учитываются у каждого процесса. Точные цифры дают `/proc/<pid>/smaps_rollup` и утилита `smem`.

## Page cache, buffers и вывод free

```bash
$ free -h
               total        used        free      shared  buff/cache   available
Mem:            15Gi       4.6Gi       0.6Gi       0.3Gi        9.8Gi         10Gi
Swap:          2.0Gi          0B       2.0Gi
```

- **page cache** — содержимое файлов в RAM, ускоряет повторное чтение;
- **buffers** — метаданные блочных устройств;
- **buff/cache** = Buffers + Cached + SReclaimable, причём в Cached входит **Shmem** (tmpfs, shared memory), которую без swap не освободить;
- **available** — оценка ядра, сколько можно выделить без свопинга. Смотреть нужно именно на неё, а не на `free`.

`sync; echo 3 > /proc/sys/vm/drop_caches` выбрасывает чистый кэш и кэши dentry/inode. Это безопасно, но бесполезно для лечения: утечки процессов команда не трогает, а диск потом нагружается повторными чтениями.

**Грязные страницы** — изменённые, но ещё не записанные данные. При превышении `vm.dirty_background_ratio` начинается фоновый сброс, а при `vm.dirty_ratio` пишущие процессы блокируются на `write()` и сами сбрасывают данные.

## Swap и swappiness

Swap — место на диске для **анонимных** страниц (heap, стек), у которых нет файла-источника. Файловые страницы просто выбрасываются и перечитываются.

`vm.swappiness` (0–200, по умолчанию 60) задаёт баланс: насколько охотно ядро выгружает анонимную память по сравнению с вытеснением page cache. Даже при 0 swap может использоваться под сильным давлением.

```bash
sysctl vm.swappiness
vmstat 1          # si/so — swap-in/swap-out страниц в секунду
swapon --show
```

Постоянные ненулевые `si`/`so` — признак нехватки памяти. Без swap ядро может освобождать только file-backed страницы, включая код программ, и система начинает «трэшить» перед OOM.

## OOM killer и overcommit

Linux по умолчанию разрешает **overcommit** — выдавать больше памяти, чем есть, рассчитывая, что не всё будет использовано.

| `vm.overcommit_memory` | Поведение |
|---|---|
| 0 (по умолчанию) | Эвристика: отклоняются только явно невозможные запросы |
| 1 | Разрешать всегда |
| 2 | Строгий учёт: лимит `CommitLimit = swap + RAM × overcommit_ratio / 100` |

При `ratio = 50`, 16 ГиБ RAM и 4 ГиБ swap получаем `CommitLimit` = 12 ГиБ; `malloc` сверх этого вернёт NULL.

Когда память кончилась и освободить нечего, **OOM killer** выбирает процесс с наибольшим `oom_score` (в основном пропорционален потреблению) и убивает его SIGKILL:

```bash
dmesg -T | grep -i 'killed process'
# Out of memory: Killed process 4242 (java) total-vm:9876544kB, anon-rss:7340032kB ...
cat /proc/1234/oom_score
echo -1000 > /proc/1234/oom_score_adj     # никогда не убивать
```

`oom_score_adj` принимает значения от −1000 до 1000, в systemd — `OOMScoreAdjust=`.

> В контейнерах лимит задаёт cgroup (`memory.max`). При его исчерпании OOM срабатывает **внутри группы**, даже если на хосте много свободной памяти. Код выхода 137 = 128 + 9 (SIGKILL), в Kubernetes — статус `OOMKilled`.

## Huge pages и диагностика утечек

**Huge pages** (2 МиБ или 1 ГиБ на x86_64) уменьшают число записей в таблицах страниц и промахов TLB — это полезно для БД и JVM с большим heap. Transparent Huge Pages (`/sys/kernel/mm/transparent_hugepage/enabled`) включаются автоматически, но иногда дают задержки, поэтому некоторые СУБД советуют их отключать.

Диагностика утечки памяти:

1. Подтвердить рост RSS/PSS во времени: `pidstat -r 60`, `ps -o rss`, мониторинг.
2. Найти растущий сегмент: `pmap -x PID`, `/proc/PID/smaps`.
3. Профилировать аллокации: valgrind/heaptrack для C/C++, heap dump для JVM, tracemalloc для Python.

Рост `buff/cache` — не утечка, а нормальная работа кэша.

## Частые вопросы на собеседовании

- `free` показывает 200 МБ свободно — это проблема? → Нет, смотрите `available`; остальное занято кэшем.
- RSS vs VSZ? → Резидентная память против всего виртуального адресного пространства.
- Как OOM killer выбирает жертву? → По `oom_score`, который корректируется через `oom_score_adj`.
- Что значит код 137? → SIGKILL, чаще всего OOM в cgroup.
- Почему сумма RSS больше RAM? → Общие страницы учитываются в каждом процессе, нужен PSS.
- Что делает `swappiness`? → Баланс между свопингом анонимной памяти и вытеснением кэша.

## Шпаргалка

- `free -h` → смотреть `available`
- `vmstat 1` (si/so), `sar -r`, `pidstat -r`
- `/proc/meminfo`, `/proc/<pid>/smaps_rollup`, `pmap -x`, `smem`
- `vm.swappiness`, `vm.overcommit_memory`, `vm.dirty_ratio`
- `dmesg -T | grep -i oom`, `oom_score`, `oom_score_adj` (−1000..1000)
- cgroup: `memory.max`, `memory.current`, `memory.events`
- `echo 3 > /proc/sys/vm/drop_caches` — только для тестов
