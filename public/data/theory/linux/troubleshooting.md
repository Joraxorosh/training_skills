Диагностика — главный практический навык Linux-инженера. На собеседовании дают сценарий («сервер тормозит», «диск заполнен», «сервис падает с `Too many open files`») и смотрят, как кандидат рассуждает: какие команды запускает первыми, как читает их вывод и отличает CPU-проблему от дисковой. Важно не помнить все флаги, а иметь систему.

## Метод USE и первые 60 секунд

**USE** (Brendan Gregg): для каждого ресурса — CPU, памяти, дисков, сети — проверить три вещи:

- **Utilization** — насколько ресурс занят;
- **Saturation** — есть ли очередь (run queue, очередь диска, свопинг);
- **Errors** — ошибки (I/O errors, drops, retransmits).

Быстрый первичный осмотр:

```bash
uptime                 # load average
dmesg -T | tail        # OOM, ошибки дисков, сегфолты
vmstat 1               # CPU, очередь, swap, I/O
mpstat -P ALL 1        # загрузка по ядрам
pidstat 1              # какие процессы едят CPU
iostat -xz 1           # диски
free -h                # память
sar -n DEV 1           # сеть
top                    # общая картина
```

## Load average

`load average: 3.50, 2.10, 1.05` — экспоненциально сглаженное среднее числа задач за **1, 5 и 15 минут**. В Linux учитываются задачи в состоянии **R** (выполняются или ждут CPU) и **D** (непрерываемое ожидание, обычно I/O). Спящие процессы в `S` и зомби не учитываются.

LA сравнивают с числом ядер (`nproc`): LA 4 на 8 ядрах — запас есть, LA 20 на 4 ядрах — перегрузка. Но высокий LA при простаивающем CPU и большом `wa` означает не нехватку CPU, а процессы в D, ждущие медленный диск или NFS.

```bash
ps -eo stat,pid,cmd | awk '$1 ~ /^D/'    # кто в состоянии D
```

## CPU: top, vmstat и perf

Строка `%Cpu(s)` в top:

| Поле | Значение |
|---|---|
| `us` / `sy` | Пользовательский код / ядро |
| `ni` | Процессы с nice > 0 |
| `id` | Простой |
| `wa` | Простой при незавершённом дисковом I/O |
| `hi` / `si` | Аппаратные / программные прерывания |
| `st` | Steal: гипервизор отдал CPU другим VM |

Высокий `st` внутри VM не исправить: перегружен хост. В `vmstat 1` смотрят на `r` (очередь на CPU, сравнить с числом ядер), `b` (процессы в D), `si`/`so` (свопинг), `wa`.

```
 r  b   swpd   free  si  so    bi    bo  us sy id wa st
 1 12      0 812340   0   0 51200  1024   4  3 28 65  0
```

Здесь узкое место — диск: 12 заблокированных процессов, `wa` 65 %, свопинга нет.

Если процесс съедает 100 % CPU в user space, strace бесполезен — нужен сэмплирующий профилировщик:

```bash
perf top -p 1234
perf record -g -p 1234 -- sleep 30 && perf report
```

## Диски и место

```bash
iostat -xz 1
```

Признаки насыщения — растущие `r_await`/`w_await` (мс на запрос) и длина очереди `aqu-sz`. `%util` = 100 % на NVMe и RAID ещё не означает предел: он показывает только долю времени с хотя бы одним запросом. Кто именно пишет — покажут `iotop` и `pidstat -d`.

Алгоритм «диск заполнен»:

1. `df -h` и `df -i` — кончились блоки или inode, на какой ФС.
2. `du -xh --max-depth=1 / | sort -h` — где лежат данные (`-x` не выходит на другие ФС).
3. Если `du` < `df` — `lsof +L1`: удалённые, но открытые файлы. Освободить без рестарта: `: > /proc/PID/fd/N`.
4. Учесть 5 % блоков ext4, зарезервированных для root.

## Сеть: ss, lsof, strace

```bash
ss -tlnp                      # слушающие TCP-сокеты и процессы
ss -tan state close-wait      # соединения в CLOSE_WAIT
ss -s                         # сводка
lsof -i :8080                 # кто держит порт
ss -ltnp 'sport = :8080'
```

| Симптом | Значение |
|---|---|
| Много `TIME_WAIT` | Нормально после активного закрытия, уходит само |
| Много `CLOSE_WAIT` | Приложение не закрывает сокеты после FIN от клиента — баг |
| LISTEN с `Recv-Q` > `Send-Q` | Очередь accept переполнена, приложение не успевает `accept()` |

Для LISTEN-сокета `Send-Q` — размер backlog (ограничен `net.core.somaxconn`), `Recv-Q` — текущая очередь.

strace показывает системные вызовы:

```bash
strace -f -p 1234 -e trace=network     # сетевые syscalls
strace -c -f -p 1234                   # сводка: число вызовов, время, ошибки
strace -f -e trace=openat ./app 2>&1 | grep ENOENT
```

strace сильно замедляет процесс — в продакшене только короткими сессиями.

## Лимиты: Too many open files

`EMFILE` (`Too many open files`) — исчерпан лимит дескрипторов **процесса**, `ENFILE` — системный (`fs.file-max`).

```bash
ulimit -n                         # лимит текущей оболочки
cat /proc/1234/limits | grep files
ls /proc/1234/fd | wc -l          # сколько открыто сейчас
```

> `/etc/security/limits.conf` применяется через PAM при входе пользователя (ssh, su). На сервисы systemd он не действует: лимит задают в юните `LimitNOFILE=65535`, затем `daemon-reload` и рестарт. Проверка — `/proc/PID/limits`.

Также стоит проверить, не утекают ли дескрипторы: рост `ls /proc/PID/fd | wc -l` со временем — это баг приложения.

## История: sar

`top` показывает только текущий момент. Пакет **sysstat** по таймеру сохраняет метрики в `/var/log/sa/` (Debian/Ubuntu — `/var/log/sysstat/`):

```bash
sar -u -f /var/log/sa/sa25     # CPU за 25-е число
sar -r                         # память
sar -d                         # диски
sar -n DEV                     # сеть
```

## Частые вопросы на собеседовании

- Что такое load average? → Среднее число задач в R и D за 1/5/15 минут; сравнивать с числом ядер.
- Высокий LA, CPU простаивает — почему? → Процессы в D ждут I/O.
- `df` и `du` расходятся? → Удалённые открытые файлы, `lsof +L1`.
- Много CLOSE_WAIT? → Приложение не закрывает сокеты.
- Подняли limits.conf, а сервис всё равно падает? → Для systemd нужен `LimitNOFILE=`.
- Что такое steal? → Время CPU, которое гипервизор отдал другим VM.
