Процесс — это выполняющаяся программа со своим PID, адресным пространством, открытыми файлами и правами. На собеседованиях по Linux проверяют, как процессы рождаются (`fork`/`exec`), почему появляются зомби, что значат буквы в столбце `STAT`, какие сигналы можно перехватить и как контейнеры изолируют процессы с помощью namespaces и cgroups.

## Создание процесса: fork и exec

Новый процесс в Unix создаётся в два шага:

1. `fork()` создаёт копию текущего процесса. Потомку возвращается **0**, родителю — **PID потомка** (−1 при ошибке). Память не копируется сразу, а разделяется по принципу **copy-on-write**: страница копируется только при записи.
2. `exec()` (`execve`) заменяет код, данные и стек процесса новой программой. **PID не меняется**, открытые дескрипторы сохраняются, кроме помеченных `O_CLOEXEC`.

Так shell запускает каждую команду: делает `fork`, в потомке настраивает перенаправления и вызывает `exec`. У каждого процесса есть **PPID** — PID родителя.

```bash
echo $$          # PID текущей оболочки
sleep 100 &
echo $!          # PID последнего фонового процесса
ps -o pid,ppid,stat,cmd -p $$
```

Потоки в Linux — это тоже задачи (tasks), созданные `clone()` с общей памятью и дескрипторами. У каждого потока свой **TID**, а `getpid()` у всех возвращает общий **TGID**. Потоки видны в `ps -L` и в `/proc/<pid>/task/`.

## Состояния процессов, зомби и сироты

| Код | Состояние | Комментарий |
|---|---|---|
| `R` | Running/runnable | Выполняется или ждёт CPU |
| `S` | Interruptible sleep | Ждёт события (сеть, таймер), прерывается сигналом |
| `D` | Uninterruptible sleep | Ждёт I/O внутри ядра, не реагирует даже на SIGKILL |
| `T` / `t` | Stopped / traced | Остановлен (Ctrl+Z, SIGSTOP) или отладчиком |
| `Z` | Zombie | Завершился, но родитель не забрал код возврата |

**Зомби** не занимает ни CPU, ни память — остаётся лишь запись в таблице процессов с кодом выхода. Убить его нельзя, он уже мёртв. Запись удаляет `wait()`/`waitpid()` родителя (обычно в обработчике SIGCHLD). Если родитель завершится, зомби усыновит PID 1 и сразу «пожнёт».

**Сирота** — живой процесс, родитель которого завершился. Его PPID становится 1 (systemd) или PID ближайшего **subreaper**. Автоматически сирота не умирает.

Много процессов в `D` — признак проблем с диском или зависшего NFS.

## Сигналы

| Сигнал | Номер | Типичный смысл |
|---|---|---|
| SIGHUP | 1 | Обрыв терминала; у демонов — перечитать конфиг |
| SIGINT | 2 | Ctrl+C |
| SIGQUIT | 3 | Ctrl+\, завершение с core dump |
| SIGKILL | 9 | Немедленное убийство, перехватить нельзя |
| SIGTERM | 15 | Вежливая просьба завершиться, сигнал `kill` по умолчанию |
| SIGCHLD | 17 | Потомок изменил состояние |
| SIGSTOP / SIGTSTP | 19 / 20 | Остановка (SIGSTOP не перехватывается) / Ctrl+Z |

**SIGKILL и SIGSTOP нельзя перехватить, заблокировать или проигнорировать.** Сначала всегда шлют SIGTERM, чтобы процесс закрыл ресурсы.

Код возврата процесса, убитого сигналом, равен **128 + номер**: 130 — SIGINT, 137 — SIGKILL, 143 — SIGTERM.

```bash
#!/bin/bash
tmp=$(mktemp)
trap 'rm -f "$tmp"' EXIT          # уборка при любом выходе
trap 'echo "reload"; load_config' HUP
trap '' INT                       # игнорировать Ctrl+C
```

`trap ... EXIT` срабатывает и при `exit N`, код возврата при этом сохраняется.

> Проблема PID 1 в контейнерах: если `CMD` запускает shell-скрипт без `exec`, SIGTERM от `docker stop` получает shell и не пересылает его приложению. К тому же для PID 1 ядро не применяет действия по умолчанию, поэтому через 10 секунд приходит SIGKILL. Решение — `exec app` в конце скрипта или init вроде `tini` (`docker run --init`).

## Приоритеты: nice и renice

Планировщик CFS/EEVDF распределяет CPU с учётом **nice** от −20 (высший приоритет) до 19 (низший), по умолчанию 0.

```bash
nice -n 10 ./batch-job       # запустить с пониженным приоритетом
renice -n 5 -p 1234          # изменить у работающего процесса
ionice -c3 -p 1234           # приоритет I/O: idle
```

Обычный пользователь может только **повышать** nice своих процессов. Понизить его можно с CAP_SYS_NICE (root) или при настроенном `RLIMIT_NICE`. В `top` столбец `NI` — nice, `PR` — итоговый приоритет.

## Namespaces, cgroups и /proc

Контейнер — это обычный процесс с двумя механизмами ядра:

- **namespaces** ограничивают, что процесс **видит**: `pid`, `net`, `mnt`, `uts`, `ipc`, `user`, `cgroup`, `time`;
- **cgroups** ограничивают, сколько ресурсов он **потребляет**: CPU, память, I/O, число процессов.

В cgroups v2 одна иерархия в `/sys/fs/cgroup`, и каждый процесс состоит ровно в одной группе:

```bash
cat /proc/self/cgroup                       # 0::/user.slice/...
cat /sys/fs/cgroup/system.slice/nginx.service/memory.max
echo "50000 100000" > cpu.max               # 50 % одного CPU
unshare --pid --fork --mount-proc bash      # оболочка в новом PID namespace
```

`/proc` — виртуальная ФС с данными о процессах: `/proc/<pid>/status` (состояние, PPid, память), `cmdline`, `environ`, `fd/` (открытые файлы), `limits`, `maps`, `stack`.

## Частые вопросы на собеседовании

- Что возвращает `fork()`? → 0 в потомке, PID потомка в родителе.
- Как убить зомби? → Никак, нужно, чтобы родитель вызвал `wait()`, или завершить родителя.
- Чем SIGTERM отличается от SIGKILL? → SIGTERM можно перехватить и корректно завершиться, SIGKILL — нет.
- Почему `docker stop` ждёт 10 секунд? → PID 1 не обрабатывает SIGTERM (shell без `exec`), и приходит SIGKILL.
- Что значит состояние D? → Непрерываемое ожидание I/O, процесс не убить до завершения операции.
- Namespaces vs cgroups? → Изоляция видимости против лимитов ресурсов.

## Шпаргалка

- `ps -eo pid,ppid,stat,ni,cmd`, `pstree -p`, `top`, `htop`
- `$$` — PID оболочки, `$!` — последний фоновый, `$?` — код возврата
- `kill -TERM`, `kill -9`, `kill -0 PID` (проверка существования), `pkill`, `killall`
- 128 + N: 130 SIGINT, 137 SIGKILL, 143 SIGTERM
- `trap 'cmd' EXIT INT TERM`
- `nice -n`, `renice`, `ionice`
- `/proc/<pid>/{status,cmdline,environ,fd,limits}`
- `unshare`, `nsenter`, `/sys/fs/cgroup`, `memory.max`, `cpu.max`, `pids.max`
