Хранилище данных (DWH) собирает данные из продуктовых баз, событий, CRM и рекламных кабинетов в одном месте, где их удобно и быстро анализировать. ETL-процессы доставляют и преобразуют эти данные. Аналитику нужно понимать, откуда берутся таблицы, почему они так устроены и что может пойти не так при загрузке — эти вопросы часто задают на позиции analytics engineer и data analyst.

## OLTP, OLAP, DWH, data lake и lakehouse

| Система | Назначение | Примеры |
|---|---|---|
| OLTP | Короткие транзакции приложения, нормализованная схема | PostgreSQL, MySQL |
| OLAP / DWH | Аналитические запросы по большим объёмам, схема при записи | ClickHouse, BigQuery, Snowflake, Greenplum |
| Data lake | Сырые файлы любого формата, схема при чтении | S3, HDFS, GCS |
| Lakehouse | Табличные форматы с ACID поверх data lake | Delta Lake, Apache Iceberg, Hudi |

Аналитические СУБД обычно **колоночные**: значения одного столбца лежат рядом, поэтому запрос читает только нужные столбцы и данные хорошо сжимаются. Это же делает дорогими точечные обновления отдельных строк.

**Lakehouse** добавляет к дешёвым файлам в объектном хранилище журнал транзакций: атомарные записи, MERGE, эволюцию схемы и time travel. Одни и те же таблицы читают Spark, Trino и Flink.

## Моделирование: факты, измерения, звезда

- **Факт** — событие на определённом уровне детализации (grain): строка заказа, платёж, показ. Содержит числовые меры и внешние ключи.
- **Измерение** — описательный контекст: клиент, товар, дата, магазин.
- **Звезда** — факт в центре, денормализованные измерения связаны с ним одним JOIN.
- **Снежинка** — измерения нормализованы в цепочки (товар → категория → департамент): меньше дублирования, больше JOIN.

В колоночных DWH чаще выбирают звезду или широкие таблицы (One Big Table): повторы хорошо сжимаются, а JOIN-ы дороги.

### Медленно меняющиеся измерения (SCD)

| Тип | Что происходит | История |
|---|---|---|
| SCD 0 | Значение не меняется | — |
| SCD 1 | Перезапись на месте | Теряется |
| SCD 2 | Новая версия строки с `valid_from`, `valid_to`, `is_current` | Полная |
| SCD 3 | Столбец с предыдущим значением | Только последнее изменение |

Атрибут на момент события берут по интервалу действия версии:

```sql
SELECT o.order_id, c.city
FROM fact_orders o
JOIN dim_customer c
  ON c.customer_id = o.customer_id
 AND o.order_ts >= c.valid_from
 AND o.order_ts <  c.valid_to;
```

## ETL, ELT, dbt и Airflow

**ETL** трансформирует данные до загрузки во внешнем инструменте. **ELT** загружает сырые данные в хранилище и трансформирует их внутри SQL-моделями. С облачными DWH стандартом стал ELT: сырые данные сохраняются, логику легко пересчитать.

Типичные слои: `raw` (как в источнике) → `staging` (очистка, типы, переименования) → `marts` (витрины для бизнеса).

**dbt** отвечает за «T»: модель — это SELECT, зависимости задаются через `ref()`, материализации — view, table, incremental. Встроенные тесты: `unique`, `not_null`, `accepted_values`, `relationships`.

**Airflow** — оркестратор: DAG на Python описывает задачи, зависимости и расписание. Сам Airflow данные не обрабатывает, а запускает задачи в нужном порядке.

```python
with DAG('daily_orders', schedule='@daily', start_date=datetime(2024, 1, 1),
         catchup=True) as dag:
    extract = PythonOperator(task_id='extract', python_callable=load_orders)
    transform = BashOperator(task_id='dbt_run', bash_command='dbt run -s orders')
    extract >> transform
```

## Идемпотентность, backfill и партиционирование

**Идемпотентная** задача даёт одинаковый результат при любом числе запусков. Приёмы:

- перезаписывать партицию за обрабатываемый день (delete + insert, `INSERT OVERWRITE`);
- MERGE / upsert по бизнес-ключу вместо слепого append;
- брать период из логической даты запуска (`data_interval_start`), а не из `now()`.

**Backfill** — пересчёт за исторические периоды после исправления логики или падения источника. С идемпотентными задачами это просто запуск DAG по диапазону дат.

**Партиционирование** по дате позволяет partition pruning: запрос с фильтром по дате читает только нужные партиции, а в BigQuery ещё и стоит дешевле. Слишком мелкие партиции порождают проблему множества маленьких файлов.

**Parquet** — колоночный файловый формат со схемой, сжатием и статистиками min/max по блокам, что позволяет пропускать ненужные блоки (predicate pushdown).

## Spark и аналитические СУБД

- **Lazy evaluation**: трансформации (`filter`, `select`, `join`) строят план, выполнение запускает действие (`count`, `collect`, `write`). Оптимизатор видит весь план и проталкивает фильтры.
- **Shuffle** — перераспределение данных по сети при `groupBy`, `join`, `distinct`. Дорого; маленькую таблицу присоединяют через broadcast join.
- **Data skew** — одна задача работает часами из-за «горячего» ключа (NULL, бот). Лечат фильтрацией мусорных ключей, salting, AQE.

| СУБД | Особенности |
|---|---|
| ClickHouse | Open-source, колоночная, движки MergeTree, очень быстрые агрегации, вставка пачками |
| BigQuery | Serverless, on-demand оплата за просканированные байты, партиции и кластеризация |
| Snowflake | Разделение storage и compute, virtual warehouses, time travel |

## Качество данных

Проверяйте: уникальность ключей, отсутствие NULL в обязательных полях, ссылочную целостность, допустимые значения, свежесть (данные за вчера пришли), объём строк против исторической нормы. Проверки встраивают в пайплайн (тесты dbt, Great Expectations, Soda), а при падении останавливают публикацию витрин.

## Частые вопросы на собеседовании

- Чем OLTP отличается от OLAP? → Короткие транзакции против аналитических агрегаций; строчное против колоночного хранения.
- Факт или измерение? → События с мерами против описательного контекста.
- Чем SCD 2 отличается от SCD 1? → Хранит версии с датами действия, а не перезаписывает.
- ETL или ELT? → ELT: грузим сырые данные, трансформируем в DWH, сырьё остаётся.
- Что такое идемпотентный пайплайн? → Повторный запуск не меняет результат: overwrite партиции или MERGE.
- Почему Parquet быстрее CSV? → Колоночный, сжатый, со схемой и статистиками.
