Нефункциональное тестирование отвечает на вопрос «насколько хорошо» работает система: быстро ли, под какой нагрузкой, безопасно ли, удобно ли и для всех ли пользователей. Чаще всего на собеседовании спрашивают про виды нагрузочного тестирования, метрики и перцентили, расчёт числа виртуальных пользователей и поиск узких мест. Базовые вопросы по безопасности, доступности и мобильному тестированию тоже встречаются регулярно.

## Виды тестирования производительности

| Вид | Профиль нагрузки | Что ищем |
|---|---|---|
| Load | Ожидаемая и пиковая нагрузка | Выполнение SLA |
| Stress | Выше предела | Точку отказа, характер деградации, восстановление |
| Spike | Резкий всплеск и спад | Реакцию на рывок, автоскейлинг |
| Soak / endurance | Умеренная нагрузка часами | Утечки памяти и соединений, деградацию со временем |
| Scalability | Растущая нагрузка и ресурсы | Насколько линейно растёт throughput при добавлении ресурсов |
| Volume | Большой объём данных | Поведение на больших таблицах и файлах |

## Метрики

- **Throughput** — запросы или транзакции в секунду (RPS, TPS).
- **Latency** — время ответа; описывается перцентилями. p95 = 800 мс: 95% запросов уложились в 800 мс.
- **Error rate** — доля неуспешных ответов.
- Ресурсы: CPU, память, диск, сеть, пулы соединений, очереди.

Среднее скрывает хвост: если 1% запросов отвечает 10 секунд, среднее почти не изменится, но пользователь за сессию из десятков запросов почти наверняка на такой попадёт. Поэтому SLO формулируют через p95 и p99.

## Модель нагрузки и расчёт пользователей

**Workload model** описывает, какие сценарии, в какой пропорции и с какой интенсивностью выполняются: 60% — поиск, 30% — карточка, 10% — заказ, пик 200 RPS. Строится по продакшен-аналитике и логам.

**Think time** — пауза пользователя между действиями. Без неё виртуальный пользователь создаёт нагрузку как десятки реальных.

Связь величин даёт закон Литтла: **N = X × (R + Z)**, где N — число пользователей, X — throughput, R — время ответа, Z — think time. Для 100 RPS при R = 0,5 с и Z = 1,5 с нужно 100 × 2 = 200 виртуальных пользователей.

**Закрытая модель** — фиксированное число пользователей, каждый ждёт ответа. **Открытая** — запросы приходят с заданной частотой независимо от ответов, как в реальном интернете. В закрытой модели возникает **coordinated omission**: если сервер завис, генератор не отправляет новые запросы, и задержки сильно занижаются. Лечение — открытая модель (`constant-arrival-rate` в k6) или корректировка измерений.

## Инструменты и сценарий k6

| Инструмент | Язык сценариев | Особенности |
|---|---|---|
| JMeter | GUI, XML | Много протоколов и плагинов, тяжеловат |
| k6 | JavaScript | Лёгкий, удобен в CI, пороги pass/fail |
| Gatling | Scala, Java, Kotlin | Высокая производительность, подробные отчёты |
| Locust | Python | Сценарии кодом, распределённый запуск |

```javascript
import http from 'k6/http';
import { sleep } from 'k6';

export const options = {
  stages: [
    { duration: '2m', target: 100 },  // разгон
    { duration: '5m', target: 100 },  // плато
    { duration: '1m', target: 0 },    // спад
  ],
  thresholds: {
    http_req_duration: ['p(95)<500'],
    http_req_failed: ['rate<0.01'],
  },
};

export default function () {
  http.get('https://stage.example.com/api/products');
  sleep(Math.random() * 2 + 1);       // think time 1–3 с
}
```

При нарушении `thresholds` k6 завершается с ненулевым кодом, и пайплайн падает.

## Анализ узких мест и окружение

Узкое место — ресурс, который насыщается первым: утилизация около 100%, растёт очередь, throughput выходит на плато, а задержки резко растут. Если у приложения CPU 35%, а у БД 100%, смотрят медленные запросы, индексы, блокировки и пул соединений.

> Сначала убедитесь, что узкое место не в самом генераторе нагрузки: его CPU и сеть тоже нужно мониторить.

Результаты валидны только на **prod-like окружении**: сопоставимые ресурсы, конфигурация, топология и объём данных. Запрос к пустой таблице быстрый, а к 100 млн строк без индекса — нет. Дополнительно применяют тестирование в проде: shadow traffic, канареечные релизы.

## Безопасность, доступность, юзабилити, совместимость и мобильные

- **Безопасность**: базовые проверки по OWASP Top 10 — XSS (`<script>alert(1)</script>` в поле комментария), SQL-инъекции (`' OR '1'='1`), IDOR, перебор паролей, утечки в ошибках. Инструменты: OWASP ZAP, Burp Suite.
- **Доступность (WCAG 2.x)**: принципы POUR. Клавиатурная навигация и видимый фокус, alt-тексты, подписи полей, контраст 4.5:1 для обычного текста на уровне AA (3:1 для крупного), информация не только цветом. Инструменты: axe, Lighthouse, скринридеры.
- **Юзабилити**: насколько легко пользователи решают задачи; проверяют наблюдением за 5–8 реальными пользователями.
- **Совместимость**: браузеры, ОС, устройства, разрешения по аналитике аудитории; облачные фермы устройств.
- **Мобильные**: прерывания (звонки, уведомления, сворачивание), смена и потеря сети, повороты экрана, фрагментация устройств, батарея и фоновый режим, обновление приложения. Эмулятор не заменяет реальные устройства.

## Частые вопросы на собеседовании

- Load vs stress? → Ожидаемая нагрузка и SLA vs поиск предела и восстановления.
- Почему перцентили, а не среднее? → Среднее прячет медленный хвост.
- Сколько нужно VU? → N = X × (R + Z) по закону Литтла.
- Что такое coordinated omission? → Занижение задержек в закрытой модели; лечится открытой моделью.
- Как найти узкое место? → Ресурс в насыщении с растущей очередью при плато throughput.
- Что проверить в мобильном приложении? → Прерывания, сеть, ориентацию, устройства, фон и батарею.

## Шпаргалка

- Load, stress, spike, soak, scalability, volume.
- Метрики: throughput, p95/p99, error rate, ресурсы.
- Think time и workload model делают нагрузку реалистичной.
- N = X × (R + Z).
- k6: `stages` — профиль, `thresholds` — критерии pass/fail.
- WCAG AA: контраст 4.5:1, клавиатура, alt, label.
