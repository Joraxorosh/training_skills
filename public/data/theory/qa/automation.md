Автоматизация тестирования — это разработка программ, которые проверяют программы. Хороший автотест быстрый, стабильный и дешёвый в поддержке; плохой — медленный, «моргающий» и мешает команде больше, чем помогает. На собеседовании спрашивают, что автоматизировать, как устроены test doubles, как бороться с flaky-тестами и как писать устойчивые UI-тесты.

## Что автоматизировать и ROI

Автоматизация окупается, когда тест запускают много раз, а поведение стабильно.

| Хорошие кандидаты | Плохие кандидаты |
|---|---|
| Регресс критичных сценариев | Разовые проверки |
| Data-driven проверки с сотнями наборов | Функциональность, которая скоро поменяется |
| Проверки в матрице браузеров или окружений | Оценка дизайна и удобства |
| Smoke на каждую сборку | Исследовательское тестирование |

ROI ≈ (сэкономленное время ручных прогонов − стоимость разработки и поддержки) / стоимость. Поддержка — главная скрытая статья расходов: тесты, которые постоянно чинят, съедают всю выгоду.

## Unit-тесты: AAA и FIRST

Тест читается как история: **Arrange** — подготовка, **Act** — действие, **Assert** — проверка.

```python
def test_cart_total():
    cart = Cart()                       # Arrange
    cart.add(Item("book", price=300))
    total = cart.total()                # Act
    assert total == 300                 # Assert
```

Принципы **FIRST**: Fast, Independent, Repeatable, Self-validating (сам решает, прошёл или нет), Timely (пишется вовремя, рядом с кодом).

## Test doubles

| Двойник | Что делает | Пример |
|---|---|---|
| Dummy | Заполняет параметр, не используется | `None` вместо логгера |
| Stub | Возвращает заранее заданные ответы | Курс валют всегда 90 |
| Spy | Записывает вызовы для последующей проверки | Счётчик отправленных писем |
| Mock | Содержит ожидания вызовов, проверяет взаимодействие | `send` вызван один раз с email |
| Fake | Упрощённая рабочая реализация | In-memory репозиторий |

Stub — для проверки состояния, mock — для проверки поведения.

```python
mailer = Mock()
register_user("a@b.c", mailer=mailer)
mailer.send.assert_called_once_with("a@b.c", template="welcome")
```

> Чрезмерное мокирование делает тесты хрупкими: они проверяют реализацию, а не поведение, и ломаются при любом рефакторинге.

## TDD и BDD

**TDD** — цикл Red → Green → Refactor: падающий тест, минимальный код, рефакторинг. Результат — тестируемый дизайн и покрытие «бесплатно».

**BDD** описывает поведение на языке бизнеса в формате Gherkin. Сценарии обсуждают «три амиго»: бизнес, разработка, тестирование.

```gherkin
Feature: Вход в систему
  Scenario: Успешный вход
    Given пользователь "anna" зарегистрирован
    When она вводит верный пароль
    Then открывается личный кабинет
```

Шаги связываются с кодом через step definitions (Cucumber, Behave, SpecFlow).

## UI-автоматизация

| Инструмент | Особенности |
|---|---|
| Selenium | W3C WebDriver, все браузеры и множество языков, ожидания пишутся явно |
| Playwright | Chromium, Firefox, WebKit; auto-waiting, перехват сети, трассировка |
| Cypress | Работает внутри браузера, быстрая отладка, `cy.intercept`; ограничения с вкладками |

**Локаторы** по устойчивости: `data-testid` и роль с доступным именем → id → CSS по смыслу → XPath по тексту. Абсолютный XPath (`/html/body/div[2]/...`) и стилевые классы ломаются при любом изменении вёрстки.

**Page Object** выносит локаторы и действия страницы в класс: тест вызывает `login_page.login(user)`, а изменения UI правятся в одном месте.

**Ожидания**: `sleep` делает тесты одновременно медленными и нестабильными. Implicit wait — глобальный таймаут поиска, explicit wait — ожидание конкретного условия. Смешивать их не стоит.

```python
WebDriverWait(driver, 10).until(
    EC.text_to_be_present_in_element((By.ID, "result"), "OK")
)
```

## Flaky-тесты, параллельность и данные

Причины нестабильности и лечение:

- Общее состояние и зависимость от порядка → изоляция, свежие данные на тест, scope фикстур `function`.
- Гонки и фиксированные таймауты → explicit waits, auto-waiting.
- Внешние сервисы и сеть → моки и стабы (WireMock, `page.route`).
- Текущее время и случайность → фиксированные часы, seed.
- Ресурсы стенда → отдельные окружения, контейнеры.

Параллельный запуск требует независимости тестов. Тестовые данные создают через API или фабрики, используют уникальные значения (uuid в email), откатывают транзакции. Реальные персональные данные из прода без маскирования использовать нельзя.

**Мутационное тестирование** (PIT, Stryker, mutmut) вносит мелкие изменения в код и проверяет, падают ли тесты. Mutation score = убитые / (все − эквивалентные): 80 из 95 ≈ 84%. Выжившие мутанты показывают слабые проверки.

## Частые вопросы на собеседовании

- Mock vs stub? → Stub отдаёт данные, mock проверяет вызовы.
- Почему `sleep` — плохо? → Тест медленный и всё равно нестабилен; нужен explicit wait.
- Что такое Page Object? → Класс страницы с локаторами и действиями, тесты не знают о селекторах.
- Как бороться с flaky? → Изоляция, ожидания условий, моки внешнего, фиксированное время, карантин и разбор.
- Чем Playwright отличается от Selenium? → Auto-waiting, свой протокол, перехват сети из коробки.
- Что показывает мутационное тестирование? → Качество проверок, а не только покрытие строк.

## Шпаргалка

- Автоматизировать стабильное и повторяемое, ROI съедает поддержка.
- AAA и FIRST для unit-тестов.
- Dummy, stub, spy, mock, fake — от простого к сложному.
- TDD: Red → Green → Refactor; BDD: Given / When / Then.
- Локаторы: `data-testid` и роли, а не абсолютный XPath.
- Explicit wait вместо `sleep`; тесты независимы, данные свои.
