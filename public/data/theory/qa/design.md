Тест-дизайн — это умение выбрать из бесконечного множества возможных проверок небольшой набор, который с наибольшей вероятностью найдёт дефекты. На собеседовании почти всегда дают задачу «поле принимает от 1 до 100 — какие значения проверите?» и просят посчитать число тестов. Важно не просто назвать технику, а показать расчёт.

## Классы эквивалентности

Входные данные делят на группы, внутри которых система должна вести себя одинаково. Из каждого класса достаточно одного представителя.

Поле «Возраст» принимает целые от 18 до 60:

| Класс | Пример | Тип |
|---|---|---|
| Меньше 18 | 10 | Невалидный |
| От 18 до 60 | 35 | Валидный |
| Больше 60 | 75 | Невалидный |
| Дробное число | 25.5 | Невалидный |
| Не число или пусто | `abc`, `""` | Невалидный |

Классы выделяют не только по диапазону, но и по типу, формату, длине и обязательности. Невалидные классы обычно проверяют по одному на тест, чтобы одна ошибка не маскировала другую.

## Анализ граничных значений

Ошибки чаще всего живут на границах: `>` вместо `>=`, off-by-one в циклах. BVA дополняет классы эквивалентности.

- **Двухточечный** — граница и ближайшее значение за ней. Для 1–100: `0, 1, 100, 101` (4 значения).
- **Трёхточечный** — до границы, граница и после. Для 1–100: `0, 1, 2, 99, 100, 101` (6 значений).

Для нескольких диапазонов (скидка: до 999 — 0%, 1000–4999 — 5%, от 5000 — 10%) границы есть на каждом стыке: `999/1000` и `4999/5000`.

```javascript
// Требование: доступ с 18 лет включительно
function canAccess(age) {
  return age > 18;   // баг ловится только тестом age = 18
}
```

> Границы бывают не только у чисел: длина строки (пароль 8–20 символов → 7, 8, 20, 21), размер файла, количество элементов, даты.

## Таблицы решений и причинно-следственный анализ

Таблица решений нужна, когда результат зависит от комбинации условий. Полная таблица для n булевых условий содержит 2ⁿ правил, но её сокращают: если условие не влияет на результат, ставят «—».

| Условие / Правило | R1 | R2 | R3 |
|---|---|---|---|
| Логин существует | Нет | Да | Да |
| Пароль верный | — | Нет | Да |
| Результат | Ошибка «нет пользователя» | Ошибка «неверный пароль» | Вход |

Из четырёх правил осталось три. **Cause-effect graphing** формализует то же: причины и следствия связываются операторами И/ИЛИ/НЕ, а граф преобразуется в таблицу решений.

## Переходы состояний и сценарии использования

**State transition** подходит для объектов с жизненным циклом: заказ, карта, тикет. Строят диаграмму состояний и проверяют:

- все допустимые переходы (0-switch coverage);
- недопустимые переходы — например, снять деньги с заблокированной карты;
- последовательности из двух переходов (1-switch) для сложной логики.

**Use case testing** строится по сценарию использования: основной успешный поток, альтернативные ветки и исключения. Каждый поток должен быть пройден хотя бы одним тестом.

**Error guessing** — опытная техника: пустые поля, ноль, отрицательные числа, спецсимволы, emoji, двойной клик, обрыв сети. Её используют поверх формальных техник.

## Попарное тестирование

Большинство дефектов вызывается одним параметром или взаимодействием двух. **Pairwise** покрывает все пары значений, а не все комбинации.

| Параметры | Полный перебор | Pairwise (минимум) |
|---|---|---|
| 3 параметра × 2 значения | 8 | 4 |
| 4 параметра × 3 значения | 81 | 9 |
| 10 параметров × 2 значения | 1024 | ~6 |

Нижняя оценка для pairwise — произведение двух самых больших доменов. Наборы генерируют инструментами (PICT, AllPairs) или ортогональными массивами.

## Метрики покрытия кода

- **Statement coverage** — доля выполненных операторов.
- **Branch coverage** — доля пройденных ветвей каждого решения (true и false).
- **Path coverage** — доля пройденных путей выполнения.

```python
def price(base, is_vip, has_coupon):
    if is_vip:
        base *= 0.9
    if has_coupon:
        base -= 100
    return base
```

Для 100% операторов хватит одного теста (оба условия true), для ветвей — двух (оба true, оба false), для путей — четырёх (2 × 2). Иерархия строгая: путь ⇒ ветви ⇒ операторы, но не наоборот. При этом 100% покрытия не гарантирует отсутствия багов: покрытие показывает, что код выполнялся, а не что результат проверен.

## Частые вопросы на собеседовании

- Поле 1–100, что проверить? → Классы: <1, 1–100, >100, не число, пусто; границы 0, 1, 100, 101.
- Сколько правил в таблице для 3 условий? → 8 в полной, меньше после сокращения.
- Зачем pairwise? → Покрыть все пары значений малым числом тестов: 4 × 3 значения — 9 вместо 81.
- Statement vs branch? → Branch строже: `if` без else требует двух тестов.
- Что проверяет state transition? → Допустимые и недопустимые переходы между состояниями.
- Даёт ли 100% покрытие гарантию? → Нет, только показывает, что код выполнялся.

## Шпаргалка

- Классы эквивалентности: один представитель на класс, невалидные — по одному на тест.
- BVA: 2-точечный — 4 значения на диапазон, 3-точечный — 6.
- Таблица решений: 2ⁿ правил, сокращение через «—».
- State transition: валидные и невалидные переходы.
- Pairwise: все пары, а не все комбинации.
- Покрытие: path ⇒ branch ⇒ statement.
