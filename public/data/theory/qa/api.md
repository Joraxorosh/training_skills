Большая часть логики современных приложений живёт за API, поэтому тестирование API — обязательный навык QA. Оно быстрее и стабильнее UI-тестов, позволяет проверить негативные сценарии, недоступные через интерфейс, и раньше находит дефекты интеграции. На собеседовании ждут уверенного знания HTTP, умения проектировать проверки и знакомства с инструментами.

## HTTP глазами тестировщика

| Метод | Назначение | Идемпотентен | Типичный успех |
|---|---|---|---|
| GET | Чтение | Да | 200 |
| POST | Создание, действие | Нет | 201 |
| PUT | Полная замена | Да | 200 или 204 |
| PATCH | Частичное изменение | Не гарантирован | 200 |
| DELETE | Удаление | Да | 204 |

Коды ответа, которые нужно различать:

- **400 / 422** — невалидный запрос; **401** — не аутентифицирован; **403** — нет прав; **404** — не найдено; **409** — конфликт (дубликат).
- **5xx** — ошибка сервера. На невалидный ввод 500 — это дефект: должна быть 4xx с понятным сообщением.

**Идемпотентность** проверяют по состоянию, а не по коду ответа: повторный DELETE может вернуть 404, но ресурса нет в обоих случаях — свойство не нарушено. PUT без необязательного поля должен его сбросить, PATCH — оставить нетронутым.

## Проектирование проверок

**Позитивные**: валидные данные, корректный статус, тело соответствует контракту, побочные эффекты (запись в БД, событие в очередь).

**Негативные**: нет обязательного поля, неверный тип, формат и длина, граничные значения, пустое тело, неверный Content-Type, нет токена, чужой ресурс.

**Валидация схемы** ловит изменения типов и структуры:

```json
{
  "type": "object",
  "required": ["id", "name"],
  "properties": {
    "id":   { "type": "integer" },
    "name": { "type": "string" }
  }
}
```

Ответ `{"id": "5", "name": "A"}` не пройдёт: `id` — строка. Лишние поля допустимы, пока не задан `additionalProperties: false`.

**Проверки в БД** подтверждают, что API не только ответил 201, но и сохранил правильные данные, без дублей.

## Аутентификация и безопасность

- Без токена → 401; истёкший `exp` → 401; изменённый payload со старой подписью → 401; `alg: none` не принимается.
- Валидный токен без прав → 403.
- **BOLA/IDOR**: пользователь A запрашивает `/orders/1042` пользователя B → 403 или 404. Это первое место в OWASP API Security Top 10.
- Mass assignment: можно ли передать `"role": "admin"` в теле регистрации.

## Инструменты

**Postman** — коллекции, окружения, переменные и тест-скрипты. **Newman** запускает коллекции в CI.

```javascript
pm.test("status is 200", () => pm.response.to.have.status(200));
pm.environment.set("token", pm.response.json().access_token);
```

**pytest + requests** — гибкие тесты кодом. Данные должны быть уникальными, иначе второй запуск получит 409:

```python
def test_create_user(base_url):
    email = f"user-{uuid4()}@example.com"
    r = requests.post(f"{base_url}/users", json={"email": email, "name": "Test"})
    assert r.status_code == 201
    assert r.json()["email"] == email
```

**REST Assured** — DSL для Java в стиле given/when/then.

**DevTools (Network)**, **Charles**, **Fiddler**, **mitmproxy** — просмотр и подмена трафика. Для мобильных приложений устройство настраивают на прокси и ставят его сертификат, чтобы расшифровать HTTPS (certificate pinning может мешать). Network помогает локализовать баг: неверный запрос — фронтенд, неверный ответ — бэкенд.

## Контракты, моки и очереди

**Consumer-driven contract testing (Pact)**: потребитель описывает ожидаемые запросы и ответы, контракт публикуется в Pact Broker, провайдер проверяет его в своём CI. Ломающее изменение API обнаруживается до деплоя, без подъёма всего окружения. Контрактные тесты проверяют формат взаимодействия, а не всю бизнес-логику провайдера.

**WireMock** (и аналоги) поднимает HTTP-заглушку внешнего сервиса: детерминированные ответы, ошибки 500, таймауты, медленные ответы. Так проверяют ретраи, таймауты и деградацию.

**Очереди сообщений** (Kafka, RabbitMQ) при доставке at-least-once требуют проверить:

- идемпотентность потребителя при повторной доставке;
- уход некорректных сообщений в DLQ без блокировки остальных;
- поведение при недоступности зависимостей — повтор без потери;
- порядок там, где он важен (в пределах партиции).

## Частые вопросы на собеседовании

- 401 vs 403? → Нет аутентификации vs нет прав.
- Какие методы идемпотентны? → GET, PUT, DELETE (и HEAD, OPTIONS); POST — нет.
- 500 на невалидный ввод — баг? → Да, ожидается 4xx с описанием ошибки.
- Что такое контрактное тестирование? → Проверка соглашения о формате API между потребителем и провайдером.
- Зачем WireMock? → Изолировать тесты от внешних сервисов и воспроизводить ошибки.
- Как проверить IDOR? → Запросить чужой ресурс своим токеном, ожидать 403 или 404.

## Шпаргалка

- POST → 201, DELETE → 204, невалидный ввод → 400/422, не 500.
- Идемпотентность проверяется по состоянию.
- Негатив: обязательные поля, типы, длины, токены, чужие объекты.
- JSON Schema — от «поплывших» типов.
- Postman + Newman, pytest + requests, REST Assured.
- Pact — контракты, WireMock — заглушки, очереди — дубли и DLQ.
