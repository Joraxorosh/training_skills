Индекс — дополнительная структура данных, которая позволяет найти строки без полного просмотра таблицы. Правильный индекс ускоряет запрос в тысячи раз, неправильный — только замедляет запись. На собеседовании проверяют, когда индекс используется, а когда нет, умение читать `EXPLAIN` и знание типов индексов PostgreSQL.

## Как работает B-tree

По умолчанию `CREATE INDEX` создаёт **B-tree** — сбалансированное дерево с отсортированными ключами. Он поддерживает `=`, `<`, `>`, `BETWEEN`, `IN`, `IS NULL`, сортировку `ORDER BY` и поиск по префиксу `LIKE 'abc%'` (для не-C локали нужен класс операторов `text_pattern_ops`).

```sql
CREATE INDEX idx_users_email ON users (email);
CREATE UNIQUE INDEX ON users (lower(email));
```

Цена индекса: каждая вставка, изменение и удаление должны обновить все индексы таблицы, плюс место на диске. Поэтому «индекс на каждый столбец» — плохая идея.

## Когда индекс не используется

- **Функция или выражение над столбцом**: `WHERE lower(email) = 'a@b.c'` не использует индекс по `email`. Решение — индекс по выражению `ON users (lower(email))`.
- **Ведущий шаблон**: `LIKE '%abc'` не использует B-tree. Для такого поиска нужен GIN с `pg_trgm`.
- **Несовпадение типов**, требующее приведения столбца.
- **Низкая селективность**: если условию соответствует большая доля таблицы (например, `status = 'active'` у 90% строк), последовательное чтение дешевле, чем тысячи случайных переходов по индексу.
- **Маленькая таблица** — проще прочитать её целиком.
- **Устаревшая статистика** — планировщик ошибается в оценке числа строк; лечится `ANALYZE`.

Арифметика тоже мешает: `WHERE created_at + interval '1 day' > now()` не использует индекс, а `WHERE created_at > now() - interval '1 day'` — использует. Условия по столбцу `timestamp` вида `created_at::date = '2024-01-01'` лучше переписать диапазоном `created_at >= '2024-01-01' AND created_at < '2024-01-02'`.

## Составные, частичные и покрывающие индексы

**Составной индекс** `(country, city)` отсортирован сначала по `country`, затем по `city`. Он эффективен для условий по `country` или по `country AND city`, но почти бесполезен для одного `city` — правило **левого префикса**. Первым ставят столбец, по которому всегда идёт фильтр на равенство.

**Частичный индекс** строится только по части строк:

```sql
CREATE INDEX ON orders (created_at) WHERE status = 'pending';
```

Его можно использовать, только если условие запроса логически влечёт условие индекса: `WHERE status = 'pending' AND created_at > ...`. Он мал и идеален для «редкого» значения.

**Покрывающий индекс** с `INCLUDE` хранит дополнительные столбцы в листьях без участия в поиске:

```sql
CREATE INDEX ON orders (customer_id) INCLUDE (total);
SELECT total FROM orders WHERE customer_id = 42;  -- Index Only Scan
```

`Index Only Scan` не обращается к таблице, если страницы помечены в visibility map как полностью видимые. Если в плане `Heap Fetches` равно числу строк — visibility map устарела, поможет `VACUUM`.

## Типы индексов PostgreSQL

| Тип | Для чего |
|---|---|
| B-tree | по умолчанию: равенство, диапазоны, сортировка |
| Hash | только `=` |
| GIN | jsonb (`@>`, `?`), массивы, полнотекстовый поиск, триграммы |
| GiST | геоданные, диапазоны (`&&` — пересечение), ближайшие соседи |
| SP-GiST | несбалансированные структуры: IP, префиксы |
| BRIN | огромные таблицы, где значения коррелируют с физическим порядком (логи по времени) |

BRIN хранит минимум и максимум для блоков страниц — индекс в тысячи раз меньше B-tree, идеален для append-only таблиц с растущим `created_at`.

## EXPLAIN и планы

```sql
EXPLAIN SELECT * FROM orders WHERE customer_id = 42;
EXPLAIN (ANALYZE, BUFFERS) SELECT * FROM orders WHERE customer_id = 42;
```

`EXPLAIN` показывает **план и оценки** без выполнения. `EXPLAIN ANALYZE` **выполняет запрос** и добавляет реальное время и число строк (осторожно с `UPDATE`/`DELETE` — оберните в транзакцию с `ROLLBACK`).

```
Index Scan using idx_orders_customer on orders
  (cost=0.42..8.44 rows=100 width=48) (actual time=0.02..0.05 rows=97 loops=1)
```

- `cost=a..b` — условная стоимость до первой и до последней строки.
- `rows=100` — **оценка** планировщика числа строк; `actual ... rows` — реальность. Большое расхождение — сигнал обновить статистику.
- Основные узлы: `Seq Scan`, `Index Scan`, `Index Only Scan`, `Bitmap Index Scan` + `Bitmap Heap Scan` (много строк или комбинация индексов через `BitmapAnd`/`BitmapOr`), `Nested Loop`, `Hash Join`, `Merge Join`.

## Обслуживание

- `VACUUM` освобождает место от мёртвых версий строк (MVCC) и обновляет visibility map; `VACUUM FULL` переписывает таблицу целиком с эксклюзивной блокировкой.
- `ANALYZE` собирает статистику для планировщика. Обе команды автоматически запускает autovacuum.
- `CREATE INDEX CONCURRENTLY` строит индекс без блокировки записи, но дольше, не работает внутри транзакции и при сбое оставляет невалидный индекс, который надо удалить.
- `REINDEX` перестраивает раздутый индекс.

## Частые вопросы на собеседовании

- Какой индекс создаётся по умолчанию? → B-tree.
- Почему индекс по `email` не работает для `lower(email)`? → Нужен индекс по выражению.
- Подойдёт ли индекс `(a, b)` для `WHERE b = ?`? → Как правило, нет: правило левого префикса.
- Чем EXPLAIN отличается от EXPLAIN ANALYZE? → Второй реально выполняет запрос и показывает фактические цифры.
- Почему выбран Seq Scan при наличии индекса? → Низкая селективность, маленькая таблица или неверная статистика.
- Какой индекс для jsonb `@>`? → GIN.

## Шпаргалка

| Ситуация | Решение |
|---|---|
| Функция в WHERE | индекс по выражению |
| `LIKE '%x%'` | GIN + pg_trgm |
| Фильтр по редкому значению | частичный индекс |
| Избежать чтения таблицы | INCLUDE, Index Only Scan |
| Огромные логи по времени | BRIN |
| Пересечение интервалов | GiST |
| Индекс без блокировки | CREATE INDEX CONCURRENTLY |
| Неверные оценки rows | ANALYZE |
