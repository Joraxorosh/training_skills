Транзакция — группа операций, которая выполняется как единое целое: либо все изменения сохраняются, либо ни одно. Это основа надёжности баз данных. На собеседовании спрашивают расшифровку ACID, уровни изоляции и их аномалии, устройство MVCC в PostgreSQL и способы борьбы с гонками и взаимоблокировками.

## ACID

| Буква | Свойство | Смысл |
|---|---|---|
| A | Atomicity, атомарность | всё или ничего |
| C | Consistency, согласованность | после транзакции соблюдены все ограничения |
| I | Isolation, изоляция | параллельные транзакции не мешают друг другу (в рамках уровня) |
| D | Durability, долговечность | после COMMIT данные не пропадут даже при сбое (WAL) |

## Управление транзакцией

```sql
BEGIN;
UPDATE accounts SET balance = balance - 100 WHERE id = 1;
UPDATE accounts SET balance = balance + 100 WHERE id = 2;
COMMIT;   -- или ROLLBACK
```

Без `BEGIN` каждая команда в PostgreSQL выполняется в собственной транзакции (autocommit). Транзакцию завершают `COMMIT` (`END`) и `ROLLBACK` (`ABORT`).

Если внутри транзакции произошла ошибка, PostgreSQL переводит её в состояние aborted: все следующие команды отвергаются («current transaction is aborted»), а `COMMIT` фактически выполнит откат. Частичный откат — через точки сохранения:

```sql
BEGIN;
INSERT INTO t VALUES (1);
SAVEPOINT sp;
INSERT INTO t VALUES (1);        -- ошибка: дубликат ключа
ROLLBACK TO SAVEPOINT sp;
INSERT INTO t VALUES (2);
COMMIT;                          -- в таблице 1 и 2
```

## Уровни изоляции и аномалии

| Уровень | Грязное чтение | Неповторяемое чтение | Фантомы | Аномалия сериализации |
|---|---|---|---|---|
| READ UNCOMMITTED | в PG нет | возможно | возможно | возможно |
| READ COMMITTED | нет | возможно | возможно | возможно |
| REPEATABLE READ | нет | нет | в PG нет | возможно |
| SERIALIZABLE | нет | нет | нет | нет |

- **Грязное чтение** — видны незафиксированные изменения другой транзакции. В PostgreSQL невозможно в принципе: `READ UNCOMMITTED` работает как `READ COMMITTED`.
- **Неповторяемое чтение** — повторный SELECT строки видит изменения, зафиксированные другой транзакцией.
- **Фантом** — повторный запрос по условию возвращает новые строки.
- **Аномалия сериализации** (например, write skew) — результат не соответствует никакому последовательному порядку.

Уровень по умолчанию в PostgreSQL — **READ COMMITTED**, в MySQL InnoDB — REPEATABLE READ.

```sql
BEGIN ISOLATION LEVEL REPEATABLE READ;
-- или
BEGIN;
SET TRANSACTION ISOLATION LEVEL SERIALIZABLE;
```

## MVCC

PostgreSQL хранит несколько версий строки. `UPDATE` не перезаписывает строку, а создаёт новую версию; старая остаётся для транзакций, которым она ещё видна, и позже удаляется `VACUUM`. Каждая команда (в READ COMMITTED) или транзакция (в REPEATABLE READ и выше) работает со **снимком** данных.

Главное следствие: **читатели не блокируют писателей, писатели не блокируют читателей**. Обычный SELECT никогда не ждёт UPDATE — он просто видит последнюю зафиксированную версию.

- В READ COMMITTED каждый оператор берёт новый снимок, поэтому второй SELECT в той же транзакции увидит чужой COMMIT.
- В REPEATABLE READ снимок берётся один раз в начале первого запроса.

## Конфликты записи

Два UPDATE одной строки сериализуются блокировкой: второй ждёт, пока первый завершится.

- **READ COMMITTED**: после COMMIT первой транзакции вторая перечитывает новую версию строки, **заново проверяет WHERE** и применяет изменение к ней. Поэтому `SET balance = balance + 10` из двух транзакций корректно даст +20. Если строка после изменения перестала подходить под WHERE, она пропускается.
- **REPEATABLE READ / SERIALIZABLE**: вторая транзакция получает ошибку `could not serialize access due to concurrent update` (SQLSTATE 40001). Приложение должно **повторить транзакцию целиком**.

Потерянное обновление возникает при схеме «прочитал в приложении — посчитал — записал». Защита: атомарный `UPDATE ... SET x = x + 1`, `SELECT ... FOR UPDATE` или более строгий уровень изоляции.

## Блокировки

```sql
BEGIN;
SELECT * FROM accounts WHERE id = 1 FOR UPDATE;  -- блокирует строку от изменений
UPDATE accounts SET balance = balance - 100 WHERE id = 1;
COMMIT;
```

- `FOR UPDATE` — эксклюзивная блокировка строки; другие `UPDATE`, `DELETE` и `FOR UPDATE` ждут, обычный SELECT — нет.
- `FOR SHARE` — разделяемая: запрещает изменение, но разрешает другим тоже брать `FOR SHARE`.
- `NOWAIT` — не ждать, сразу ошибка. `SKIP LOCKED` — пропустить заблокированные строки; классический паттерн очереди задач:

```sql
SELECT id FROM jobs WHERE status = 'new'
ORDER BY id LIMIT 1
FOR UPDATE SKIP LOCKED;
```

Построчные блокировки держатся до конца транзакции; PostgreSQL не эскалирует их до блокировки таблицы. Явные блокировки таблиц — `LOCK TABLE`. **Advisory-блокировки** (`pg_advisory_lock(key)`, `pg_advisory_xact_lock(key)`) — блокировки по произвольному числу, смысл которых определяет приложение.

## Взаимоблокировки

Deadlock: T1 держит строку A и ждёт B, T2 держит B и ждёт A. PostgreSQL обнаруживает цикл (через `deadlock_timeout`, по умолчанию 1 с) и **прерывает одну из транзакций** с ошибкой, другая продолжает работу.

Профилактика: брать блокировки в **одинаковом порядке** (например, обновлять счета по возрастанию id), делать транзакции короткими, повторять упавшую транзакцию.

## Частые вопросы на собеседовании

- Что означает A в ACID? → Атомарность: всё или ничего.
- Уровень изоляции по умолчанию в PostgreSQL? → READ COMMITTED.
- Возможно ли грязное чтение в PostgreSQL? → Нет, даже на READ UNCOMMITTED.
- Что делать при ошибке 40001? → Повторить транзакцию целиком.
- Блокирует ли SELECT строку, которую обновляют? → Нет, MVCC отдаёт последнюю зафиксированную версию.
- Как избежать deadlock при переводах? → Блокировать строки в одинаковом порядке.

## Шпаргалка

| Тема | Правило |
|---|---|
| Завершение | COMMIT / ROLLBACK |
| Ошибка в транзакции | всё до ROLLBACK отвергается; SAVEPOINT для частичного отката |
| PG по умолчанию | READ COMMITTED |
| RR в PG | нет фантомов, но write skew возможен |
| 40001 | retry |
| MVCC | читатели и писатели не блокируют друг друга |
| Очередь | FOR UPDATE SKIP LOCKED |
| Deadlock | PG прерывает одну транзакцию |
