Многие инциденты начинаются не с ошибки в бизнес-логике, а с окружения приложения: сервер, который ходит по чужим URL, небезопасная десериализация, загруженный файл, вредоносная зависимость или пароль в истории Git. Эта тема объединяет SSRF, обработку недоверенных данных, цепочку поставок, секреты, логирование и тестирование безопасности.

## SSRF

SSRF (Server-Side Request Forgery) — атакующий заставляет сервер отправить запрос на выбранный адрес. Сервер находится внутри периметра и видит то, что снаружи недоступно: внутренние API, базы, админки и сервис метаданных облака `169.254.169.254`, который выдаёт временные учётные данные IAM.

Источники SSRF: вебхуки, превью ссылок, импорт по URL, загрузка аватара по ссылке, XXE, генерация PDF из HTML.

```python
# Плохо: denylist по строке
if "169.254.169.254" in url or "localhost" in url:
    abort(400)
requests.get(url)
```

Обходы: десятичная запись IP `http://2852039166/`, IPv6 `[::ffff:a9fe:a9fe]`, DNS-имя, указывающее на внутренний адрес, редирект с внешнего сервера, **DNS rebinding** (при проверке домен разрешается во внешний IP, при подключении — во внутренний).

Защита:

- Allowlist разрешённых доменов, если задача это допускает.
- Разрешить имя в IP, проверить, что адрес не приватный и не link-local, и подключиться **именно к этому IP**.
- Отключить редиректы или проверять каждый.
- Исходящий трафик через egress-прокси с политиками, сегментация сети.
- В AWS — **IMDSv2** (`HttpTokens=required`): метаданные доступны только с токеном, полученным через PUT с заголовком, а типичная SSRF умеет лишь GET.

Даже blind SSRF (ответ не виден) позволяет сканировать внутреннюю сеть и вызывать внутренние эндпоинты.

## Десериализация и загрузка файлов

Нативная десериализация восстанавливает объекты вместе с поведением и может выполнить код до любой проверки.

| Опасно | Безопасная альтернатива |
|---|---|
| `pickle.loads(data)` | JSON со схемой (Pydantic) |
| `yaml.load(data)` | `yaml.safe_load(data)` |
| Java `ObjectInputStream` | JSON; если неизбежно — `ObjectInputFilter` с allowlist |
| PHP `unserialize` | `json_decode` |

В Java опасные методы не нужно вызывать явно: **gadget chains** из библиотек на classpath выполняются внутри `readObject`.

Загрузка файлов:

- Хранить вне webroot или в объектном хранилище, имя генерирует сервер.
- Проверять тип по содержимому, а не по расширению и `Content-Type` клиента.
- Ограничивать размер и количество; помнить о zip-бомбах.
- Отдавать с отдельного домена и с `Content-Disposition: attachment` — HTML и SVG могут содержать XSS.
- При распаковке архивов проверять пути (**zip slip**): в Python 3.12+ `tar.extractall(path, filter="data")`.

## Цепочка поставок

| Атака | Суть | Защита |
|---|---|---|
| Typosquatting | Пакет `reqeusts` вместо `requests` | Проверка имён, lockfile |
| Dependency confusion | Публичный пакет с именем внутреннего и большей версией | Scoped-пакеты, привязка scope к внутреннему реестру |
| Взлом мейнтейнера | Вредоносная версия популярного пакета | Lockfile с хэшами, ревью обновлений, задержка перед обновлением |
| Install-скрипты | Код выполняется при `npm install` | `--ignore-scripts`, CI без лишних секретов |

```bash
npm ci                          # строго по lockfile, проверка хэшей
pip install --require-hashes -r requirements.txt
```

**SCA** находит известные CVE в прямых и транзитивных зависимостях, **SBOM** фиксирует состав. Свежую вредоносную версию SCA не поймает: она попадает в базы с задержкой.

## Секреты

- Не хранить секреты в коде и образах, использовать secret manager и переменные окружения из него.
- `git rm` и `.gitignore` не удаляют секрет из истории. Утёкший секрет считается скомпрометированным: сначала **ротация**, потом чистка истории.
- Сканеры секретов (gitleaks, trufflehog) — в pre-commit и CI, плюс push protection на стороне Git-хостинга.

## Логирование и мониторинг

Без логов атаку замечают через месяцы (A09). Что логировать:

- неудачные и успешные входы, всплески ошибок аутентификации;
- отказы в доступе и обращения к чужим объектам;
- изменения ролей, паролей, MFA, ключей API;
- ошибки валидации и подозрительные входные данные.

Чего не логировать: пароли (даже неверные), токены, cookie сессий, полные номера карт. Логи должны быть защищены от изменения, централизованы и связаны с алертами.

## Тестирование безопасности

| Метод | Как работает | Сильная сторона |
|---|---|---|
| SAST | Анализ исходного кода | Рано, указывает строку |
| DAST | Атакует работающее приложение снаружи | Находит проблемы конфигурации |
| IAST | Агент внутри приложения во время тестов | Мало ложных срабатываний |
| Fuzzing | Случайные и мутированные входы | Падения в парсерах, краевые случаи |
| Пентест | Ручная работа эксперта | Логические уязвимости, цепочки атак |

> Автоматические инструменты плохо находят ошибки бизнес-логики и контроля доступа, поэтому пентест и ревью кода их не заменяют.

## Частые вопросы на собеседовании

- **Почему denylist не спасает от SSRF?** → Альтернативные записи IP, DNS, редиректы и rebinding.
- **Как IMDSv2 защищает от SSRF?** → Требует токен, полученный через PUT с заголовком.
- **Чем опасен `pickle.loads`?** → Выполняет код при десериализации.
- **Что такое dependency confusion?** → Публичный пакет с именем внутреннего побеждает по версии.
- **Секрет попал в Git — что делать?** → Ротировать, затем чистить историю и включить сканирование.
- **Чем IAST отличается от DAST?** → Видит выполнение изнутри приложения и указывает место в коде.

## Шпаргалка

- SSRF: allowlist, проверка IP при подключении, без редиректов, IMDSv2, egress-прокси.
- Десериализация: только данные (JSON), никаких `pickle` и `ObjectInputStream`.
- Загрузки: вне webroot, свои имена, проверка содержимого, отдельный домен.
- Зависимости: lockfile, `npm ci`, scoped-пакеты, `--ignore-scripts`, SCA и SBOM.
- Секреты: secret manager, ротация при утечке, сканеры в pre-commit и CI.
- Логи: события безопасности есть, секретов нет.
