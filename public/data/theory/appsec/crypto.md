От разработчика не ждут умения проектировать шифры, но ждут, что он правильно использует готовые примитивы: выберет нужный режим, не повторит nonce, сравнит подписи за постоянное время и не отключит проверку сертификата. Большинство реальных криптографических уязвимостей — ошибки использования, а не взлом алгоритмов.

## Кодирование, хэширование, шифрование

| Операция | Обратима | Нужен ключ | Примеры | Зачем |
|---|---|---|---|---|
| Кодирование | Да, всем | Нет | Base64, URL-encoding, hex | Представление данных |
| Хэширование | Нет | Нет | SHA-256, SHA-3, BLAKE2 | Отпечаток, целостность |
| HMAC | Нет | Да, общий | HMAC-SHA256 | Целостность и подлинность |
| Шифрование | Да, с ключом | Да | AES-GCM, ChaCha20-Poly1305 | Конфиденциальность |
| Подпись | Проверка | Пара ключей | Ed25519, ECDSA, RSA-PSS | Подлинность, неотказуемость |

Base64 в конфиге — не защита. Хэш без ключа доказывает только целостность и только если сам хэш получен из доверенного источника. MD5 и SHA-1 непригодны там, где важна стойкость к коллизиям.

## Симметричное шифрование и режимы

Симметричное шифрование (AES, ChaCha20) использует один ключ и работает быстро. Важен режим:

- **ECB** — одинаковые блоки дают одинаковый шифротекст, структура данных видна. Не использовать.
- **CBC без MAC** — уязвим к bit-flipping и **padding oracle**: если сервер по-разному отвечает на ошибку padding, шифротекст расшифровывается побайтно.
- **AEAD (AES-GCM, ChaCha20-Poly1305)** — шифрование и проверка целостности сразу. Выбор по умолчанию.

```python
# Плохо: фиксированный nonce
nonce = b"\x00" * 12
ct = AESGCM(key).encrypt(nonce, data, None)

# Хорошо: уникальный nonce для каждого шифрования, хранится рядом с шифротекстом
nonce = os.urandom(12)
ct = nonce + AESGCM(key).encrypt(nonce, data, aad)
```

> Повтор nonce с тем же ключом в GCM — катастрофа: утекает XOR открытых текстов и становится возможной подделка тегов. Случайные 96-битные nonce безопасны примерно до 2^32 сообщений на ключ; при больших объёмах ротируйте ключ или берите XChaCha20-Poly1305 с 192-битным nonce.

Nonce и IV не секретны, но должны быть уникальными (для CBC — ещё и непредсказуемыми).

## Асимметричная криптография и подписи

- Пара ключей: публичный раздаётся, приватный хранится в секрете.
- **Шифрование**: публичным ключом получателя, расшифровка — его приватным. На практике так передают симметричный ключ, а не сами данные.
- **Подпись**: приватным ключом автора, проверка — его публичным.
- **ECC против RSA**: 256-битный ключ EC примерно равен по стойкости 3072-битному RSA, ключи и подписи короче, операции быстрее. Для подписей хорош Ed25519.
- Для RSA — только современные схемы дополнения: OAEP для шифрования, PSS для подписи.

## HMAC и типичные ошибки

```python
# Плохо: length extension и timing attack
sig = sha256(SECRET + body).hexdigest()
if sig == received: ...

# Хорошо
sig = hmac.new(SECRET, body, hashlib.sha256).hexdigest()
if hmac.compare_digest(sig, received): ...
```

- `hash(secret + message)` у SHA-256 позволяет дописать данные и пересчитать хэш без секрета (length extension). HMAC от этого защищён.
- Обычное `==` завершается на первом несовпадении, и по времени можно подобрать подпись. Используйте `compare_digest` или `crypto.timingSafeEqual`.
- Ключ из пароля получают через KDF (Argon2id, scrypt, PBKDF2) с солью, а не через `sha256(password)`.

## Случайность и управление ключами

Секреты, токены, ключи и nonce генерирует только CSPRNG:

| Язык | Небезопасно | Безопасно |
|---|---|---|
| Python | `random` | `secrets`, `os.urandom` |
| JavaScript | `Math.random()` | `crypto.randomBytes`, `crypto.getRandomValues` |
| Java | `java.util.Random` | `SecureRandom` |

Управление ключами:

- Хранить в KMS или HSM, не в коде и не рядом с данными.
- **Envelope encryption**: данные шифруются ключом DEK, DEK — мастер-ключом KEK в KMS.
- Версия ключа хранится вместе с шифротекстом — так ключи ротируются без простоя.
- Разные ключи для разных окружений и назначений.

## TLS на практике

TLS даёт конфиденциальность, целостность и аутентификацию сервера. Последнее держится на проверке сертификата: цепочки до доверенного CA и совпадения имени хоста.

```python
# Плохо: шифрование есть, но неизвестно с кем
requests.get(url, verify=False)

# Хорошо: внутренний CA явно
requests.get(url, verify="/etc/ssl/internal-ca.pem")
```

- **Forward secrecy** (ECDHE): утечка приватного ключа сервера не раскрывает ранее записанный трафик. В TLS 1.3 она есть всегда.
- Отключайте TLS 1.0/1.1 и слабые наборы шифров, включайте HSTS.
- **Не изобретайте криптографию**: берите высокоуровневые библиотеки (libsodium, Tink, `cryptography`) с безопасными настройками по умолчанию.

## Частые вопросы на собеседовании

- **Чем хэширование отличается от шифрования?** → Хэш необратим и без ключа, шифрование обратимо с ключом.
- **Почему ECB плох?** → Сохраняет структуру данных: одинаковые блоки дают одинаковый шифротекст.
- **Что будет при повторе nonce в GCM?** → Утечка XOR открытых текстов и возможность подделки.
- **Зачем HMAC, если есть SHA-256?** → Хэш без ключа не доказывает подлинность, а `sha256(key + msg)` уязвим к length extension.
- **Что даёт forward secrecy?** → Старый трафик нельзя расшифровать после утечки ключа сервера.
- **Чем опасен `verify=False`?** → Открывает MITM, хотя трафик формально шифруется.

## Шпаргалка

- Base64 — не шифрование; MD5/SHA-1 — не для подписей.
- Шифрование: AES-GCM или ChaCha20-Poly1305, уникальный nonce.
- Целостность: HMAC и `compare_digest`.
- Подписи: Ed25519/ECDSA, RSA только с PSS/OAEP.
- Случайность: только CSPRNG.
- Ключи: KMS, envelope encryption, ротация с версиями.
- TLS: проверка цепочки и имени хоста, TLS 1.2+, ECDHE.
