Инъекция возникает, когда данные пользователя попадают в интерпретатор — SQL, shell, шаблонизатор, XML-парсер — и меняют структуру команды. Данные становятся кодом. На собеседовании ждут, что вы узнаете уязвимый код с первого взгляда, объясните, почему параметризация работает, а «фильтрация опасных символов» — нет, и знаете типовые ловушки ORM.

## SQL-инъекции и параметризация

Классический пример — сборка запроса строкой:

```python
# Уязвимо
cur.execute(f"SELECT * FROM users WHERE name = '{name}'")

# Безопасно: значение передаётся отдельно от текста запроса
cur.execute("SELECT * FROM users WHERE name = %s", (name,))
```

Ввод `' OR '1'='1` закрывает строковый литерал и превращает условие в истинное. При параметризации запрос разбирается без значений, и никакой ввод не может изменить его синтаксис.

Разновидности:

- **Classic (in-band)** — результат виден в ответе, часто через `UNION SELECT`.
- **Blind** — результата не видно, данные извлекают по признакам: другой ответ (boolean-based) или задержка `pg_sleep(5)` (time-based). Скрытие ошибок не лечит уязвимость.
- **Second-order** — ввод безопасно сохранили, а позже другой код достал его из базы и вставил в запрос строкой. Данные из своей базы тоже недоверенные.

Ограничения плейсхолдеров:

- Работают только для **значений**. Имена таблиц, колонок и `ASC`/`DESC` выбирают через allowlist.
- В `LIKE` символы `%` и `_` остаются масками — экранируйте их, если это важно.
- Хранимая процедура, которая склеивает строку и вызывает `EXEC`, снова уязвима.

```python
SORT = {"date": "created_at", "title": "title"}
column = SORT.get(request.args.get("sort"), "created_at")
cur.execute(f"SELECT * FROM posts ORDER BY {column}")  # column только из словаря
```

## Ловушки ORM

ORM защищает, пока вы не пишете SQL вручную:

| Безопасно | Уязвимо |
|---|---|
| `User.objects.filter(name=name)` | `User.objects.extra(where=[f"name = '{name}'"])` |
| `User.objects.raw("... WHERE name = %s", [name])` | `User.objects.raw(f"... WHERE name = '{name}'")` |
| `session.execute(text("... = :n"), {"n": name})` | `session.execute(text(f"... = '{name}'"))` |

Отдельная проблема NoSQL — инъекция операторов. Если в MongoDB вместо строки придёт объект `{"$ne": null}`, условие станет «пароль не пустой». Защита — строгая валидация типов по схеме.

## Инъекции команд и path traversal

```python
# Уязвимо: host = "8.8.8.8; cat /etc/passwd"
os.system("ping -c 1 " + host)

# Безопасно: без shell, аргументы списком, плюс проверка формата
subprocess.run(["ping", "-c", "1", host], check=True)
```

Даже без shell остаётся **argument injection**: значение, начинающееся с `-`, программа воспримет как флаг (`git clone --upload-pack=...`). Ставьте `--` перед позиционными аргументами и проверяйте формат.

Path traversal — выход за пределы директории через `../`:

```python
# Безопасно: канонизировать и проверить префикс
base = os.path.realpath("/srv/files")
full = os.path.realpath(os.path.join(base, name))
if not full.startswith(base + os.sep):
    abort(400)
```

Типичные обходы наивных проверок: `....//` после удаления `../`, двойное URL-кодирование `%252e%252e%252f`, абсолютный путь (`os.path.join` отбрасывает базу). Лучше всего вообще не принимать путь, а хранить соответствие «ID → файл».

## SSTI, XXE, LDAP

- **SSTI** (Server-Side Template Injection) — ввод становится частью шаблона: `render_template_string("Hello " + name)`. Признак — `{{7*7}}` выводит `49`. Часто ведёт к RCE. Исправление — передавать данные в шаблон как переменные.
- **XXE** — XML с `<!ENTITY x SYSTEM "file:///etc/passwd">` читает файлы и делает SSRF. Даже без внешних сущностей вложенные внутренние сущности дают «billion laughs» (DoS). Решение — запретить DTD целиком (`defusedxml`, `disallow-doctype-decl`).
- **LDAP-инъекция** — метасимволы фильтра `*`, `(`, `)`, `\` меняют логику. Экранируйте по RFC 4515 функцией библиотеки.

## Валидация ввода и кодирование вывода

Это разные инструменты:

- **Валидация ввода** — проверка, что данные соответствуют ожиданиям: тип, длина, формат. Лучше через **allowlist** (`^[a-z0-9_]{3,32}$`), потому что denylist всегда неполон.
- **Обработка на выходе** — параметризация для SQL, передача аргументов списком для команд, контекстное кодирование для HTML.

> Основная защита от инъекций — правильная обработка в точке использования. Валидация — дополнительный слой: имя `O'Brien` проходит любую разумную валидацию и при этом ломает склеенный SQL.

## Частые вопросы на собеседовании

- **Почему prepared statements защищают от SQLi?** → Структура запроса фиксирована, значения всегда трактуются как данные.
- **Можно ли параметризовать имя колонки?** → Нет, только через allowlist.
- **Что такое second-order SQLi?** → Сохранённые данные позже вставляются в запрос без параметризации.
- **Спасает ли отказ от `shell=True`?** → От метасимволов да, от argument injection нет.
- **Как защититься от XXE?** → Отключить DTD и внешние сущности в парсере.
- **Allowlist или denylist?** → Allowlist: описать допустимое проще и надёжнее.

## Шпаргалка

- SQL: только плейсхолдеры; идентификаторы — из словаря.
- ORM: опасны `raw`, `extra`, `text()` с f-строками.
- Команды: `subprocess.run([...])` без shell, `--` перед аргументами.
- Пути: `realpath` и проверка префикса или ID вместо пути.
- Шаблоны: данные — переменными, не частью шаблона.
- XML: запретить DTD.
- Ввод — валидировать по allowlist, вывод — кодировать по контексту.
