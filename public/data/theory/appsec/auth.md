Аутентификация отвечает на вопрос «кто вы», авторизация — «что вам можно». Ошибки в обеих занимают в OWASP Top 10 первое (Broken Access Control) и седьмое (Identification and Authentication Failures) места. На собеседовании спрашивают, как хранить пароли, как защищаться от подбора и credential stuffing, как устроены сессии и JWT и как найти IDOR в коде.

## Хранение паролей

Пароль должен храниться необратимо и так, чтобы перебор утёкшей базы был дорогим.

| Способ | Оценка | Почему |
|---|---|---|
| Открытый текст, AES | Недопустимо | Утечка базы или ключа раскрывает все пароли |
| MD5, SHA-1, SHA-256 | Плохо | Миллиарды проверок в секунду на GPU |
| SHA-256 с солью | Плохо | Соль спасает от радужных таблиц, но не от скорости |
| bcrypt, scrypt | Хорошо | Медленные, с настраиваемой стоимостью |
| Argon2id | Рекомендуется | Медленный и требует много памяти, что мешает GPU |

```python
from argon2 import PasswordHasher
ph = PasswordHasher()                # соль генерируется и хранится в строке хэша
stored = ph.hash(password)
ph.verify(stored, attempt)           # исключение при несовпадении
```

- **Соль** — уникальная случайная строка на каждого пользователя, не секрет. Одинаковые пароли дают разные хэши.
- **Pepper** — общий секрет, хранится вне базы (KMS, HSM). Помогает, если утекла только база.
- **bcrypt учитывает только первые 72 байта**. Для кириллицы в UTF-8 это около 36 символов.

## Подбор паролей и MFA

- **Brute force** — перебор паролей для одного аккаунта. Защита — rate limiting по аккаунту и IP, нарастающие задержки, CAPTCHA. Жёсткая блокировка аккаунта позволяет атакующему блокировать чужие аккаунты.
- **Credential stuffing** — вход с парами логин/пароль из чужих утечек. На каждый аккаунт приходится одна-две попытки, поэтому блокировка не помогает. Защита — MFA, проверка паролей по базам утечек, детект ботов.
- **Перечисление пользователей** — разные сообщения «нет такого пользователя» и «неверный пароль» или разное время ответа. Отвечайте одинаково и выполняйте проверку фиктивного хэша.

MFA — факторы **разных** типов: знание (пароль, PIN), владение (TOTP, ключ FIDO2), биометрия. Пароль и секретный вопрос — один фактор. Самый стойкий к фишингу вариант — FIDO2/WebAuthn: ключ привязан к домену.

## Сессии

- Идентификатор сессии — длинный, из CSPRNG, в cookie с `HttpOnly; Secure; SameSite`.
- **Session fixation**: атакующий навязывает жертве известный ему ID. Защита — новый ID после входа и при повышении привилегий.
- Таймауты: idle (бездействие) и absolute (максимальный срок жизни).
- При смене пароля, выходе и подозрении на взлом — завершать остальные сессии и отзывать refresh-токены.

## JWT: типичные ошибки

JWT — подписанный (не зашифрованный) токен: payload читает любой, кто его видит.

```javascript
// Уязвимо: алгоритм берётся из заголовка токена
jwt.verify(token, publicKey);

// Безопасно: алгоритм задаёт сервер
jwt.verify(token, publicKey, { algorithms: ["RS256"] });
```

- **`alg: none`** — токен без подписи принимается как валидный.
- **Algorithm confusion** — токен подписан HS256 с публичным RSA-ключом в роли секрета.
- **Слабый секрет HS256** (`secret123`) подбирается офлайн по одному токену.
- **Нет отзыва** — stateless-токен работает до `exp`. Решение: короткий TTL, refresh-токены с ротацией и серверным отзывом, denylist по `jti`.
- **Хранение в `localStorage`** — доступно любому скрипту при XSS. Компромисс: access-токен в памяти, refresh-токен в `HttpOnly`-cookie с защитой от CSRF.
- Проверять `exp`, `aud`, `iss`, а не только подпись.

## OAuth 2.0 и OIDC

- **`state`** — защита от CSRF в колбэке: значение привязано к сессии и сверяется.
- **PKCE** — обязателен для SPA и мобильных клиентов: перехваченный код без `code_verifier` бесполезен.
- **`redirect_uri`** — точное совпадение с зарегистрированным. Проверка по префиксу пропускает `https://app.example.com.evil.com`.
- Implicit flow устарел: токен в URL утекает через историю и Referer.
- `client_secret` в мобильном или браузерном приложении не является секретом.

## Контроль доступа: IDOR и повышение привилегий

```python
# Уязвимо: IDOR — любой пользователь читает чужой заказ
order = Order.query.get_or_404(order_id)

# Безопасно: проверка владельца
order = Order.query.filter_by(id=order_id, user_id=current_user.id).first_or_404()
```

- **Горизонтальное повышение** — доступ к данным другого пользователя того же уровня (IDOR, BOLA).
- **Вертикальное** — получение прав администратора: эндпоинт без проверки роли или **mass assignment** (`user.update(**request.json)` с полем `role`).
- Защита: запрет по умолчанию, централизованная проверка прав, allowlist изменяемых полей (DTO, схемы).
- 401 — не аутентифицирован, 403 — нет прав. Иногда для чужих объектов возвращают 404, чтобы не раскрывать их существование.

> UUID вместо последовательных ID усложняет перебор, но не заменяет проверку прав.

## Частые вопросы на собеседовании

- **Почему не SHA-256 для паролей?** → Слишком быстрый; нужен Argon2id или bcrypt.
- **Чем соль отличается от pepper?** → Соль уникальна и хранится рядом с хэшем, pepper — общий секрет вне базы.
- **Как отозвать JWT?** → Короткий TTL, refresh-токены с серверным отзывом, denylist по `jti`.
- **Что такое algorithm confusion?** → Подпись HS256 публичным RSA-ключом, если сервер берёт `alg` из токена.
- **Как найти IDOR?** → Подставить ID чужого объекта от имени другого пользователя.
- **Зачем PKCE?** → Чтобы перехваченный authorization code нельзя было обменять на токен.

## Шпаргалка

- Пароли: Argon2id/bcrypt, соль, опционально pepper; никакого шифрования.
- Логин: rate limiting, MFA, одинаковые ответы.
- Сессия: новый ID после входа, таймауты, отзыв при смене пароля.
- JWT: фиксированный `algorithms`, сильный ключ, короткий TTL, проверка `exp`/`aud`/`iss`.
- OAuth: `state`, PKCE, точный `redirect_uri`.
- Доступ: проверка владельца каждого объекта, allowlist полей, deny by default.
