Конкурентность — главная причина, по которой выбирают Go. Горутины дешёвые, каналы встроены в язык, а пакет `sync` даёт классические примитивы. На собеседовании просят предсказать поведение каналов, найти deadlock или гонку, спроектировать worker pool и объяснить, как избежать утечки горутин.

## Горутины

`go f()` запускает функцию в новой горутине. Её стек начинается с нескольких килобайт и растёт по мере нужды, поэтому горутин могут быть сотни тысяч. Когда `main` возвращает управление, программа завершается, не дожидаясь остальных горутин.

```go
var wg sync.WaitGroup
for i := 0; i < 3; i++ {
    wg.Add(1)                 // до запуска горутины
    go func() {
        defer wg.Done()
        fmt.Println(i)        // Go 1.22+: у каждой итерации своя i
    }()
}
wg.Wait()                     // порядок вывода не определён
```

`WaitGroup` нельзя копировать: если передать его по значению, `Done` уменьшит счётчик копии, и `Wait` зависнет. С Go 1.25 есть `wg.Go(func() { ... })`, который сам вызывает `Add` и `Done`.

## Каналы

Канал — типизированная очередь для передачи данных между горутинами. **Небуферизованный** канал синхронизирует отправителя и получателя. **Буферизованный** позволяет отправить до `cap` значений без ожидания.

```go
ch := make(chan int)      // небуферизованный
// ch <- 1                // в одной горутине: deadlock!

buf := make(chan int, 2)
buf <- 1
buf <- 2
fmt.Println(len(buf), cap(buf))   // 2 2

close(buf)
v, ok := <-buf            // 1 true
v, ok = <-buf             // 2 true
v, ok = <-buf             // 0 false — канал закрыт и пуст
```

| Операция | nil-канал | закрытый канал |
|---|---|---|
| отправка | блокируется навсегда | panic |
| приём | блокируется навсегда | остаток буфера, затем нулевое значение и `false` |
| `close` | panic | panic |

Закрывает канал отправитель, причём один раз. `for v := range ch` читает до закрытия канала. Если все горутины заблокированы, рантайм завершает программу: `fatal error: all goroutines are asleep - deadlock!`.

## select

`select` ждёт первую готовую ветку. Если готовы несколько, выбирается случайная. Ветка `default` делает операцию неблокирующей.

```go
select {
case v := <-results:
    fmt.Println("got", v)
case <-time.After(time.Second):
    fmt.Println("timeout")
case <-ctx.Done():
    return ctx.Err()
}

select {
case ch <- v:
default:
    fmt.Println("канал полон, пропускаем")
}
```

Если присвоить каналу `nil`, его ветка в `select` выключается. Так делают, например, после закрытия одного из источников при слиянии каналов.

## Пакет sync и atomic

```go
type Cache struct {
    mu   sync.RWMutex
    data map[string]string
}

func (c *Cache) Get(k string) (string, bool) {
    c.mu.RLock()                // много читателей одновременно
    defer c.mu.RUnlock()
    v, ok := c.data[k]
    return v, ok
}

func (c *Cache) Set(k, v string) {
    c.mu.Lock()                 // один писатель
    defer c.mu.Unlock()
    c.data[k] = v
}

var once sync.Once
once.Do(initConfig)             // ровно один раз, остальные ждут

var hits atomic.Int64
hits.Add(1)
```

- `Mutex` не реентерабелен: повторный `Lock` в той же горутине приводит к deadlock;
- `sync.Once` — потокобезопасная ленивая инициализация, а `sync.OnceValue` (1.21+) ещё и возвращает значение;
- `atomic` подходит для счётчиков и флагов. Составные инварианты защищают мьютексом;
- `sync.Map` оптимизирована под сценарий «редко пишем, часто читаем» и непересекающиеся ключи.

## Гонки данных и детектор

Гонка — это одновременный доступ к памяти из нескольких горутин, когда хотя бы один из них — запись, а синхронизации нет. `n++` из многих горутин теряет инкременты, и результат не определён. Флаг `-race` (`go test -race`, `go run -race`) инструментирует код и сообщает о гонках, которые реально произошли во время выполнения.

## Worker pool, errgroup и утечки

```go
jobs := make(chan int)
results := make(chan int)
var wg sync.WaitGroup
for w := 0; w < 4; w++ {
    wg.Add(1)
    go func() {
        defer wg.Done()
        for j := range jobs {       // выйдет после close(jobs)
            results <- j * j
        }
    }()
}
go func() {
    for i := 1; i <= 10; i++ { jobs <- i }
    close(jobs)
}()
go func() { wg.Wait(); close(results) }()
for r := range results { fmt.Println(r) }
```

`errgroup` из `golang.org/x/sync` объединяет ожидание, первую ошибку и отмену:

```go
g, ctx := errgroup.WithContext(ctx)
g.SetLimit(8)
for _, url := range urls {
    g.Go(func() error { return fetch(ctx, url) })
}
err := g.Wait()   // первая ошибка; ctx отменён для остальных
```

**Утечка горутин** — горутина, которая навсегда заблокирована на канале или ждёт контекст, который никто не отменит. GC такие горутины не собирает. У каждой горутины должен быть понятный путь завершения.

## Частые вопросы на собеседовании

- Чем буферизованный канал отличается от небуферизованного? → небуферизованный синхронизирует стороны, а буферизованный блокирует отправителя только при полном буфере.
- Что будет при чтении из закрытого канала? → сначала остаток буфера, потом нулевое значение и `ok == false`.
- Кто должен закрывать канал? → отправитель, один раз. Получатель канал не закрывает.
- Как сделать таймаут? → `select` с `time.After` или `ctx.Done()`.
- Как найти гонку? → `go test -race` и защита общих данных мьютексом, атомиками или каналами.
- Как избежать утечки горутин? → отмена через контекст, закрытие каналов и буфер нужного размера.

## Шпаргалка

- `main` не ждёт горутины: нужны `WaitGroup`, каналы или `errgroup`.
- `wg.Add` — до `go`, `wg` — по указателю.
- Отправка в закрытый канал, повторный `close`, `close(nil)` — panic.
- Nil-канал блокирует навсегда.
- `select`: случайный выбор, `default` — без блокировки.
- RWMutex — много читателей или один писатель; Mutex не реентерабелен.
- Счётчики — `atomic.Int64`; проверка — `-race`.
