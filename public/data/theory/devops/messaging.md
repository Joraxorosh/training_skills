Очереди и брокеры сообщений развязывают сервисы во времени и по нагрузке: продюсер отправляет сообщение и не ждёт, пока потребитель его обработает. Это основа асинхронных и событийных архитектур. На собеседовании проверяют разницу моделей (очередь и лог), устройство Kafka (топики, партиции, consumer groups, репликация), RabbitMQ (exchanges, очереди, подтверждения), роль Redis и гарантии доставки.

## Зачем нужны брокеры

- **Асинхронность** — пользователь получает ответ сразу, тяжёлая работа выполняется в фоне.
- **Сглаживание пиков** — очередь буферизует нагрузку, потребители обрабатывают в своём темпе.
- **Развязка** — продюсер не знает, сколько и какие потребители существуют.
- **Fan-out** — одно событие получают несколько независимых сервисов.

Модели: **point-to-point** (очередь, каждое сообщение получает один из потребителей) и **pub/sub** (каждый подписчик получает копию).

## Сравнение Kafka, RabbitMQ и Redis

| | Kafka | RabbitMQ | Redis |
|---|---|---|---|
| Модель | Распределённый append-only лог | Брокер очередей (AMQP 0-9-1) | In-memory хранилище; Pub/Sub, Streams, списки |
| После чтения | Сообщение остаётся до истечения retention | Удаляется после ack | Pub/Sub — не хранит; Streams — хранит |
| Повторное чтение | Да, сдвигом offset | Нет (кроме streams в RabbitMQ) | Streams — да |
| Порядок | Внутри партиции | Внутри очереди (при одном потребителе) | Внутри стрима |
| Маршрутизация | По ключу в партицию | Гибкая: exchanges и bindings | Минимальная |
| Сильные стороны | Высокий throughput, event streaming, replay | Сложная маршрутизация, задачи, приоритеты, TTL | Низкая задержка, кэш, простые очереди |

## Kafka: топики, партиции, consumer groups

**Topic** делится на **партиции** — упорядоченные неизменяемые логи. Каждое сообщение в партиции имеет **offset**. Сообщения с одинаковым **ключом** попадают в одну партицию (hash(key) % partitions), поэтому порядок гарантирован только **внутри партиции**.

**Consumer group**: каждая партиция читается ровно одним потребителем группы. Если потребителей больше, чем партиций, лишние простаивают — число партиций ограничивает параллелизм. Разные группы читают топик независимо (это и есть pub/sub). Потребители коммитят offset в служебный топик `__consumer_offsets`; при добавлении или падении потребителя происходит **rebalance**.

Хранение: по `retention.ms`/`retention.bytes` или **log compaction** (сохраняется последнее значение для каждого ключа — для changelog-топиков).

**Репликация**: у партиции есть лидер и follower-реплики. **ISR** (in-sync replicas) — реплики, не отставшие от лидера. Надёжная конфигурация:

```properties
replication.factor=3
min.insync.replicas=2
acks=all
enable.idempotence=true
```

С `acks=all` запись подтверждается, когда её получили все реплики из ISR; если ISR меньше `min.insync.replicas`, продюсер получит ошибку вместо тихой потери данных.

Начиная с Kafka 4.0 **ZooKeeper удалён** — метаданные кластера управляются встроенным протоколом **KRaft**.

```bash
kafka-topics.sh --bootstrap-server kafka:9092 --create --topic orders --partitions 6 --replication-factor 3
kafka-console-producer.sh --bootstrap-server kafka:9092 --topic orders
kafka-console-consumer.sh --bootstrap-server kafka:9092 --topic orders --group g1 --from-beginning
kafka-consumer-groups.sh --bootstrap-server kafka:9092 --describe --group g1   # LAG
```

**Consumer lag** — насколько потребители отстают от конца партиции; главная метрика здоровья потребителей.

## RabbitMQ: exchanges и очереди

Продюсер публикует в **exchange**, который по **bindings** и **routing key** раскладывает сообщения в очереди.

| Тип exchange | Маршрутизация |
|---|---|
| direct | Точное совпадение routing key |
| topic | Шаблон: `*` — одно слово, `#` — ноль или больше слов (`logs.*.error`) |
| fanout | Во все привязанные очереди, ключ игнорируется |
| headers | По заголовкам сообщения |

Надёжность:

- **Ack потребителя**: сообщение удаляется только после `basic.ack`; при падении потребителя без ack оно вернётся в очередь (redelivery). `nack`/`reject` без requeue отправляют его в **DLX** (dead letter exchange), если он настроен.
- **Publisher confirms** — брокер подтверждает продюсеру приём сообщения.
- **Durable** очередь + **persistent** сообщения переживают рестарт брокера.
- **Prefetch** (`basic.qos`) ограничивает число неподтверждённых сообщений на потребителя — равномерное распределение и защита от перегрузки.
- **Quorum queues** (на основе Raft) — рекомендуемый тип реплицируемых очередей вместо устаревших classic mirrored queues, которые удалены в RabbitMQ 4.

## Redis как брокер

- **Pub/Sub** — fire-and-forget: сообщения не хранятся, офлайн-подписчик их теряет.
- **Lists** (`LPUSH` + `BRPOP`) — простая очередь задач; с `LMOVE` можно реализовать надёжную обработку.
- **Streams** (`XADD`, `XREADGROUP`, `XACK`) — лог с consumer groups и подтверждениями, похож на упрощённую Kafka; неподтверждённые сообщения видны в pending list (`XPENDING`, `XCLAIM`).

Redis держит данные в памяти; для сохранности нужна персистентность (RDB-снимки, AOF) и репликация. Он также используется как кэш, для rate limiting и распределённых блокировок.

## Гарантии доставки и идемпотентность

| Гарантия | Смысл | Как достигается |
|---|---|---|
| At-most-once | Может потеряться, не дублируется | Коммит offset/ack до обработки |
| At-least-once | Не теряется, может дублироваться | Ack/коммит после обработки (самый частый вариант) |
| Exactly-once | Ровно один эффект | Kafka: идемпотентный продюсер + транзакции в пределах Kafka; в общем случае — идемпотентный потребитель |

> На собеседовании часто спрашивают: «Как не обработать сообщение дважды?» Ответ: при at-least-once дубликаты неизбежны, поэтому потребитель делает обработку **идемпотентной** — хранит ID обработанных сообщений, использует upsert или уникальные ключи в БД. Для атомарной записи в БД и отправки события применяют паттерн **Transactional Outbox**.

Ещё важные паттерны: **DLQ** для «ядовитых» сообщений, которые постоянно падают; ретраи с backoff; **backpressure** — замедление продюсеров, когда потребители не успевают.

## Частые вопросы на собеседовании

- Kafka vs RabbitMQ? → Kafka — лог с retention и replay под высокий поток событий; RabbitMQ — брокер с гибкой маршрутизацией, сообщение удаляется после ack.
- Как гарантировать порядок в Kafka? → Одинаковый ключ → одна партиция; порядок только внутри партиции.
- Потребителей больше, чем партиций? → Лишние простаивают.
- Что такое ISR и `acks=all`? → Синхронные реплики; запись подтверждается всеми из ISR.
- Типы exchange в RabbitMQ? → direct, topic, fanout, headers.
- Как бороться с дублями? → Идемпотентный потребитель, outbox, дедупликация по ID.

## Шпаргалка

- Kafka: topic → partitions → offset; consumer group = 1 партиция на 1 потребителя
- `replication.factor=3`, `min.insync.replicas=2`, `acks=all`, идемпотентный продюсер
- Kafka 4.x — KRaft без ZooKeeper; метрика — consumer lag
- RabbitMQ: exchange (direct/topic/fanout/headers) → binding → queue; ack, prefetch, DLX, quorum queues
- Redis: Pub/Sub без хранения, Lists, Streams с XACK
- At-most-once / at-least-once / exactly-once; идемпотентность, outbox, DLQ
