Масштабирование — способность системы выдерживать рост нагрузки добавлением ресурсов. На собеседовании почти любая задача доходит до вопроса «а что будет при ×10 трафика?», и ответ строится из одних и тех же кирпичей: stateless-сервисы, балансировщики, автомасштабирование, API gateway и защита от перегрузки через rate limiting.

## Вертикальное и горизонтальное масштабирование

| | Вертикальное (scale up) | Горизонтальное (scale out) |
|---|---|---|
| Как | Больше CPU, RAM, быстрее диск | Больше машин |
| Предел | Потолок железа | Практически не ограничено |
| Отказоустойчивость | Одна точка отказа | Падение узла не критично |
| Сложность | Минимальная | Балансировка, распределённое состояние |
| Типичное применение | БД на старте, кэш | Веб- и API-серверы, воркеры |

Начинать с вертикального нормально: одна мощная машина с PostgreSQL выдерживает очень много. Горизонтальное масштабирование становится нужным, когда упираемся в предел или требования к доступности.

## Stateless-сервисы

Чтобы экземпляры можно было свободно добавлять и убирать, они не должны хранить состояние пользователя в памяти. Сессии, корзины, загруженные файлы выносят во внешние хранилища:

- сессии — в Redis или в подписанные токены (JWT);
- файлы — в объектное хранилище;
- данные — в БД.

Тогда любой экземпляр обработает любой запрос, а autoscaling и падения узлов не теряют данные. **Sticky sessions** (привязка клиента к узлу) — временный костыль: нагрузка распределяется неравномерно, а при падении узла сессии теряются.

## Балансировка нагрузки

```text
             ┌──────────────┐
 клиенты ──▶ │ L4/L7 балансир│──┬──▶ app-1
             └──────────────┘  ├──▶ app-2
                               └──▶ app-3   (health checks)
```

| | L4 | L7 |
|---|---|---|
| Видит | IP, порт, TCP/UDP | HTTP: путь, заголовки, cookie |
| Маршрутизация | По соединению | По URL, хосту, заголовку, canary |
| TLS | Пропускает насквозь | Может терминировать |
| Стоимость | Дешевле и быстрее | Больше CPU |

Алгоритмы:

- **Round robin** — по кругу; хорош для однородных запросов.
- **Weighted round robin** — с весами для серверов разной мощности.
- **Least connections** — туда, где меньше активных запросов; хорош при разной длительности запросов.
- **IP hash / consistent hashing** — один ключ всегда на один узел; нужен для кэшей и шардов.

**Health checks**: активные (балансировщик опрашивает `/health`) и пассивные (учитываются ошибки реальных запросов). Без них трафик продолжит идти на мёртвый узел.

### Consistent hashing

При `hash(key) % N` изменение N перемещает почти все ключи. В consistent hashing узлы и ключи лежат на кольце, ключ принадлежит ближайшему узлу по часовой стрелке. Добавление узла перемещает лишь ~1/N ключей. **Виртуальные узлы** (сотни точек на физический узел) выравнивают распределение и позволяют задавать веса.

## Autoscaling, API Gateway и service discovery

**Autoscaling** добавляет и убирает экземпляры по метрике: CPU, RPS на экземпляр, длина очереди, задержка. Реакция не мгновенная (сбор метрик, старт ВМ, прогрев), поэтому держат запас мощности и масштабируют заранее для предсказуемых пиков.

**API Gateway** — единая точка входа: маршрутизация к сервисам, аутентификация, rate limiting, TLS, агрегация ответов. Минус — лишний хоп и ещё одна компонента, которую надо резервировать.

**Service discovery** — реестр живых экземпляров (Consul, etcd, DNS в Kubernetes). Клиентский вариант: сервис сам берёт адреса из реестра и балансирует. Серверный: запрос идёт через балансировщик, который знает адреса.

## Rate limiting

Ограничение числа запросов защищает от злоупотреблений и перегрузки. Превышение — ответ `429 Too Many Requests` с `Retry-After`.

| Алгоритм | Идея | Плюсы | Минусы |
|---|---|---|---|
| Token bucket | Токены капают со скоростью r, ведро ёмкостью b | Разрешает всплески, экономен | Всплеск до b запросов |
| Leaky bucket | Очередь, вытекает с постоянной скоростью | Сглаживает поток | Не допускает всплесков, задержки |
| Fixed window | Счётчик на окно (минуту) | Очень простой | До 2× лимита на стыке окон |
| Sliding window log | Метки всех запросов за окно | Точный | Много памяти |
| Sliding window counter | Взвешенная сумма текущего и прошлого окна | Точный почти, дёшев | Аппроксимация |

В распределённой системе счётчики живут в общем хранилище, обычно Redis, а проверка и инкремент должны быть **атомарными**: `INCR` с проверкой результата или Lua-скрипт. Схема «прочитать — проверить — записать» даёт гонки и превышение лимита. Для глобального лимита через несколько регионов часто выбирают локальные счётчики с асинхронной синхронизацией: немного неточно, но без межрегиональной задержки на каждом запросе.

## Частые вопросы на собеседовании

- Почему сервисы делают stateless? → Чтобы экземпляры были взаимозаменяемы и легко масштабировались.
- L4 vs L7? → L7 видит HTTP и маршрутизирует по пути и заголовкам, L4 — только по IP и порту.
- Когда least connections лучше round robin? → Когда запросы сильно различаются по длительности.
- Зачем consistent hashing? → При изменении числа узлов переезжает ~1/N ключей, а не почти все.
- Token bucket vs leaky bucket? → Первый допускает всплески, второй выравнивает поток.
- Почему лимитер на Redis пропускает лишнее? → Неатомарные чтение и запись; нужен `INCR` или Lua.

## Шпаргалка

- Scale up — проще, но потолок и SPOF; scale out — stateless + балансировщик
- Состояние — в Redis, БД, объектном хранилище; sticky sessions — костыль
- L4 — TCP, быстро; L7 — HTTP, маршрутизация, TLS
- RR, weighted, least conn, consistent hashing с vnodes
- Autoscaling по CPU / RPS / длине очереди; держать headroom
- Rate limiting: token bucket (всплески), leaky bucket (ровно), sliding window (точно), `429`
