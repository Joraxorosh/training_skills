Большинство задач на собеседовании — вариации нескольких классических систем. Знать их разбор заранее полезно не для пересказа, а чтобы быстро увидеть ключевую проблему: генерацию ID, fan-out, доставку в реальном времени, работу с большими файлами. Ниже — сжатые разборы по одной схеме: требования, ключевые решения, узкие места.

## Сервис коротких ссылок

**Требования**: создать короткую ссылку, редирект по ней, опционально — кастомный алиас, TTL, аналитика. Read/write ≈ 100:1. При 100 млн новых ссылок в сутки: ~1 200 записей/с, ~120 000 чтений/с; 1 млрд ссылок по 500 байт — ~0.5 ТБ.

```text
POST /links {url} ─▶ API ─▶ ID generator ─▶ DB (code → url)
GET /{code}       ─▶ API ─▶ Redis cache ─▶ DB    ─▶ 302 Location: url
```

**Генерация кода**:

| Способ | Плюсы | Минусы |
|---|---|---|
| Счётчик + base62 | Нет коллизий, коротко | Счётчик — узкое место; коды предсказуемы |
| Диапазоны счётчика на сервер | Нет коллизий, редкие обращения к координатору | Пропуски при рестарте |
| Snowflake + base62 | Без координации | Код длиннее (~11 символов) |
| Хэш URL (усечённый) | Одинаковый URL — одинаковый код | Коллизии, нужна проверка |

base62 на 7 символов даёт 62⁷ ≈ 3.5 трлн кодов. **Snowflake**: 1 бит знака + 41 бит миллисекунд (~69 лет) + 10 бит машины + 12 бит последовательности (4096 ID в мс).

**Редирект**: `301` кэшируется браузером — меньше нагрузки, но теряется аналитика; `302` — каждый переход через сервис. Горячие ссылки (20% дают 80% трафика) отлично ложатся в кэш. Клики пишутся асинхронно через очередь.

## Лента новостей

**Требования**: публикация поста, лента из постов подписок, отсортированная по времени или рангу. Чтение сильно доминирует.

| Подход | Как | Плюсы | Минусы |
|---|---|---|---|
| Fan-out on write (push) | При публикации пост кладётся в ленты всех подписчиков | Чтение — один запрос к готовой ленте | Знаменитость с 50 млн подписчиков = 50 млн записей |
| Fan-out on read (pull) | Лента собирается при открытии | Дешёвая запись | Медленное чтение при многих подписках |
| Гибрид | Push для обычных, pull для знаменитостей | Баланс | Сложнее логика |

```text
post ─▶ Post Service ─▶ DB
          └─▶ queue ─▶ fan-out workers ─▶ Redis: feed:{user} (список post_id)
read feed: feed:{user} + посты знаменитостей (pull) ─▶ merge ─▶ hydrate из кэша постов
```

Ленты хранят как списки ID (ограниченной длины) в Redis, сами посты и профили — в отдельных кэшах. Ленты неактивных пользователей можно не обновлять и строить при входе.

## Чат

**Требования**: личные и групповые сообщения в реальном времени, история, статус «онлайн», доставка офлайн-пользователям.

- **Транспорт**: WebSocket — постоянное двунаправленное соединение. Отдельный слой chat-серверов держит соединения; маппинг `user → сервер` хранится в Redis.
- **Доставка**: сообщение сохраняется, затем через pub/sub отправляется серверу, где сидит получатель. Если получатель офлайн — push-уведомление, а при подключении клиент дочитывает с последнего известного ID.
- **Порядок**: время устройства ненадёжно. Используют порядковый номер внутри диалога или Snowflake-подобный ID.
- **Хранение**: wide-column БД (Cassandra, HBase), ключ партиции — `conversation_id`, кластеризация по ID сообщения.
- **Presence**: heartbeat каждые N секунд; нет heartbeat дольше таймаута — офлайн. Для больших групп статусы рассылают лениво.

## Хранилище файлов (Dropbox)

- Файл делится на **чанки** по ~4 МБ; у каждого — хэш содержимого.
- Чанки лежат в объектном хранилище, метаданные (файлы, версии, списки чанков) — в БД.
- При изменении загружаются только новые чанки — **дельта-синхронизация**; загрузка возобновляема и параллельна.
- **Дедупликация**: чанк с уже известным хэшем не загружается повторно.
- Клиент загружает напрямую в хранилище по **pre-signed URL**, сервер работает только с метаданными. Изменения рассылаются другим устройствам через long polling или WebSocket.

## Коротко о других задачах

| Задача | Ключевые решения |
|---|---|
| Rate limiter | Token bucket или sliding window в Redis, атомарно через Lua; `429` + `Retry-After`; лимитер в gateway |
| Уведомления | API → очереди по каналам → воркеры → APNs/FCM/SMTP; настройки и тихие часы; дедупликация по idempotency key; ретраи |
| Автодополнение | Trie с top-K в узлах, собирается офлайн из логов; неизменяемые снапшоты в памяти; кэш на CDN и клиенте |
| Top-K / лидерборд | Redis sorted set (`ZINCRBY`, `ZREVRANGE`); для огромных потоков — Count-Min Sketch и мерж окон |
| Видео | Загрузка в S3 → очередь → транскодирование в несколько битрейтов → сегменты HLS/DASH → CDN; плеер с адаптивным битрейтом |

## Частые вопросы на собеседовании

- Сколько кодов даёт base62 длиной 7? → ~3.5 трлн.
- 301 или 302 для короткой ссылки? → 302, если нужна аналитика; 301 снижает нагрузку.
- Как решить проблему знаменитостей в ленте? → Гибрид: их посты подмешиваются при чтении.
- Как упорядочить сообщения в чате? → Порядковый номер в рамках диалога, а не время клиента.
- Зачем чанки в Dropbox? → Дельта-синхронизация, возобновление загрузки, дедупликация.
- Как сделать лидерборд? → Redis sorted set.

## Шпаргалка

- Short URL: счётчик/диапазоны/Snowflake → base62, кэш, 302 для аналитики
- Feed: push для обычных, pull для знаменитостей, ленты как списки ID в Redis
- Chat: WebSocket, `conversation_id` как ключ партиции, sequence в диалоге, heartbeat
- Dropbox: чанки + хэши, S3 + метаданные в БД, pre-signed URL
- Autocomplete: trie + top-K, офлайн-сборка
- Video: async транскодирование, HLS/DASH, CDN, ABR
