Хранилище — обычно самая сложная для масштабирования часть системы. Сервисы приложения легко сделать stateless и размножить, а данные нужно где-то держать, реплицировать и делить так, чтобы не потерять консистентность там, где она важна. На собеседовании ждут обоснованного выбора типа БД, понимания репликации и шардирования и умения рассуждать о CAP без лозунгов.

## SQL или NoSQL

| Критерий | Реляционные (PostgreSQL, MySQL) | NoSQL (Cassandra, DynamoDB, MongoDB, Redis) |
|---|---|---|
| Модель | Таблицы, строгая схема, связи | Ключ-значение, документы, wide-column, графы |
| Транзакции | ACID, в том числе многострочные | Часто ограничены одним ключом или документом |
| Запросы | Гибкий SQL, JOIN, агрегаты | Под заранее известные паттерны доступа |
| Масштаб записи | Вертикально, шардирование вручную | Горизонтальное «из коробки» |
| Когда брать | Деньги, заказы, связи, отчёты | Огромный объём, простой доступ по ключу, гибкая схема |

Хороший ответ — «по умолчанию реляционная, пока не появится конкретная причина»: объём записи, который не тянет один лидер, данные без связей с доступом по ключу, требования к доступности важнее консистентности.

**Большие бинарные данные** (фото, видео, бэкапы) хранят в **объектном хранилище** (S3 и аналоги), а в БД — только метаданные и ключ объекта. Загрузку часто делают напрямую из клиента по pre-signed URL.

## Индексы и денормализация

Индекс (обычно B-tree) ускоряет поиск с O(N) до O(log N), но замедляет запись и занимает место. Составной индекс `(a, b, c)` работает по **левому префиксу**: помогает в фильтрах по `a` и `a, b`, но не по одному `b`.

**Денормализация** — намеренное дублирование данных ради быстрого чтения без JOIN: имя автора в посте, счётчик лайков в строке поста. Плата — обновление всех копий и риск рассинхрона.

## Репликация

| Схема | Запись | Плюсы | Минусы |
|---|---|---|---|
| Leader-follower | Только в лидера | Просто, нет конфликтов, масштаб чтения | Запись упирается в лидера, failover |
| Multi-leader | В любой из лидеров | Запись в нескольких ДЦ, офлайн-клиенты | Конфликты записи, их разрешение |
| Leaderless (Dynamo) | В любые узлы с кворумом | Высокая доступность, нет failover | Сложная консистентность, read repair |

**Синхронная** репликация не теряет подтверждённые данные, но увеличивает задержку и останавливает запись при недоступности реплики. **Асинхронная** быстрая, но реплики отстают (**replication lag**), а при падении лидера можно потерять последние записи.

### Аномалии отставания

- **Read-your-writes**: пользователь не видит своё изменение. Решение — читать свои данные с лидера какое-то время после записи или с реплики, догнавшей нужную позицию журнала.
- **Monotonic reads**: повторное чтение возвращает более старые данные. Решение — привязать пользователя к одной реплике.
- **Consistent prefix**: ответ виден раньше вопроса. Решение — писать причинно связанные данные в один раздел.

### Кворумы

В leaderless-системе с N репликами запись подтверждают W узлов, чтение опрашивает R узлов. При **R + W > N** множества пересекаются, и чтение увидит последнюю подтверждённую запись. Типично N = 3, W = 2, R = 2. Расхождения чинят **read repair**, **hinted handoff** и фоновая **anti-entropy** с Merkle-деревьями.

## Шардирование

```text
            ┌─ shard 0: users 0..999k
router ─────┼─ shard 1: users 1M..1.99M
 (по ключу) └─ shard 2: ...
```

| Стратегия | Плюсы | Минусы |
|---|---|---|
| По диапазону | Диапазонные запросы, упорядоченность | Горячие шарды (например, по времени) |
| По хэшу | Равномерное распределение | Диапазонные запросы идут во все шарды |
| По справочнику (directory) | Гибкое размещение | Справочник — ещё одна критичная компонента |
| Географическое | Данные рядом с пользователем | Неравномерные регионы |

**Ключ шардирования** выбирают под главный запрос: для чата — `conversation_id`, для заказов — `customer_id`. Ошибка в ключе приводит к scatter-gather на каждом запросе.

**Решардинг**: `hash % N` при смене N перемещает почти всё. Решения — **consistent hashing** или фиксированное число логических партиций (например, 1024), больше числа узлов: при росте узлы забирают целые партиции.

Цена шардирования: межшардовые JOIN и транзакции, глобальные уникальные ограничения, горячие ключи. Аналитику по всем данным выносят в отдельное колоночное хранилище через CDC или ETL.

## CAP, PACELC и модели консистентности

**CAP**: при сетевом разделении (P) система выбирает между консистентностью (C, ошибка вместо устаревших данных) и доступностью (A, ответ, возможно устаревший). Разделения неизбежны, поэтому реальный выбор — CP или AP на время сбоя.

**PACELC** дополняет: если разделения нет (Else), выбор между задержкой (L) и консистентностью (C). Cassandra и DynamoDB по умолчанию — PA/EL, Spanner — PC/EC.

| Модель | Гарантия |
|---|---|
| Линеаризуемость | Каждая операция видна всем мгновенно, как на одной копии |
| Последовательная | Все видят один порядок операций |
| Причинная (causal) | Причинно связанные операции видны в правильном порядке |
| Read-your-writes | Автор видит свои изменения |
| Eventual | Без новых записей реплики со временем сойдутся |

## Частые вопросы на собеседовании

- Когда NoSQL лучше SQL? → Огромный объём записи, доступ по ключу, гибкая схема, приоритет доступности.
- Как обеспечить read-your-writes при репликах? → Читать свои данные с лидера или с догнавшей реплики.
- Какое условие кворума? → R + W > N.
- Range vs hash шардирование? → Range удобен для диапазонов, но даёт горячие шарды; hash равномерен.
- Что такое CAP простыми словами? → При разделении сети выбираем ошибку или устаревший ответ.
- Где хранить видео? → В объектном хранилище, метаданные — в БД.

## Шпаргалка

- По умолчанию — реляционная БД; NoSQL — под конкретную причину
- Блобы — в S3, в БД — ключ и метаданные
- Leader-follower / multi-leader / leaderless; sync — надёжно, async — быстро
- Replication lag → read-your-writes, monotonic reads
- R + W > N; read repair, hinted handoff, anti-entropy
- Ключ шарда — под главный запрос; решардинг — consistent hashing или фиксированные партиции
- CAP: CP или AP при разделении; PACELC: L или C в штатном режиме
