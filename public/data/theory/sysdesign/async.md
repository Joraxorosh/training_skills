Как только система выходит за рамки одного сервиса с одной БД, появляются асинхронное взаимодействие, частичные отказы и распределённые транзакции. На собеседовании спрашивают, когда нужна очередь, как не потерять и не задвоить событие, как согласовать данные между сервисами без 2PC и как не дать одной упавшей зависимости положить всю систему.

## Очереди, логи и pub/sub

Очередь развязывает продюсера и консьюмера по времени: запрос принимается быстро, тяжёлая работа выполняется позже, пики сглаживаются, а консьюмеры масштабируются независимо.

| | Очередь (RabbitMQ, SQS) | Лог (Kafka) |
|---|---|---|
| После чтения | Сообщение удаляется после ack | Хранится по retention, независимо от чтения |
| Позиция | Брокер отслеживает доставку | Консьюмер хранит offset |
| Повторное чтение | Нет | Да, можно перемотать offset |
| Порядок | В пределах очереди, ломается при нескольких консьюмерах | Строго внутри партиции |
| Типичное применение | Задачи для воркеров | Поток событий, CDC, аналитика |

**Pub/sub**: издатель публикует событие в топик, каждый подписчик (в Kafka — каждая consumer group) получает свою копию. Событие «заказ создан» независимо обрабатывают оплата, склад и уведомления.

Порядок в Kafka гарантирован только **внутри партиции**, поэтому ключ партиционирования выбирают по сущности: все события одного `order_id` попадают в одну партицию.

## Гарантии доставки и идемпотентность

| Гарантия | Смысл | Цена |
|---|---|---|
| At-most-once | Может потеряться, не задвоится | Ack до обработки |
| At-least-once | Не потеряется, может задвоиться | Ack после обработки |
| Exactly-once | Ровно один эффект | Только в рамках одной системы или через идемпотентность |

На практике выбирают **at-least-once + идемпотентный обработчик**:

- таблица обработанных `message_id` (или idempotency key от клиента);
- идемпотентные операции: `UPSERT`, «установить статус» вместо «прибавить»;
- условные обновления по версии.

## Outbox, саги и 2PC

**Проблема двойной записи**: сервис пишет в БД и публикует в брокер — между этими действиями возможен сбой. **Transactional outbox** решает её: событие пишется в таблицу `outbox` в той же локальной транзакции, а отдельный релей (или CDC, например Debezium) публикует его в брокер с at-least-once.

```text
BEGIN
  INSERT INTO orders ...
  INSERT INTO outbox (event) ...
COMMIT
relay: SELECT FROM outbox → publish → mark sent
```

**2PC** (двухфазный коммит) даёт атомарность между участниками, но он блокирующий: при сбое координатора участники в состоянии prepared держат блокировки. Плюс синхронность снижает доступность. Между микросервисами его почти не используют.

**Сага** — последовательность локальных транзакций, где каждая при сбое отменяется **компенсирующим действием** (возврат денег, снятие резерва). Компенсации тоже должны быть идемпотентными.

| | Хореография | Оркестрация |
|---|---|---|
| Управление | Сервисы реагируют на события друг друга | Координатор отдаёт команды |
| Плюсы | Нет центра, слабая связность | Процесс виден явно, легко отлаживать |
| Минусы | Логику трудно увидеть целиком, циклы | Оркестратор — центральная компонента |
| Когда | 2–3 шага | Длинные процессы с ветвлениями |

## CQRS и event sourcing

**CQRS** разделяет модель записи и модель чтения. Чтения обслуживаются денормализованными проекциями под конкретные экраны, которые обновляются асинхронно по событиям. Цена — eventual consistency между моделями.

**Event sourcing** хранит не текущее состояние, а последовательность событий; состояние — свёртка событий. Плюсы: полный аудит, возможность пересобрать проекции. Минусы: версионирование событий, снапшоты для длинных историй, сложные запросы к текущему состоянию. CQRS и event sourcing часто используют вместе, но они независимы.

## Устойчивость к сбоям

- **Таймауты** на каждый сетевой вызов — иначе зависшая зависимость исчерпает пулы потоков и соединений.
- **Ретраи с exponential backoff и jitter** — интервал растёт, а случайный разброс разрывает синхронные волны. Ретраят только идемпотентные операции и ограничивают число попыток.
- **Retry budget** — ретраи на каждом уровне цепочки перемножаются: 3 уровня по 3 попытки дают до 27 вызовов. Ретраят на одном уровне и ограничивают долю повторов.
- **Circuit breaker** — при высокой доле ошибок перестаём звать зависимость и сразу отдаём ошибку или fallback.
- **Bulkhead** — отдельные пулы ресурсов на каждую зависимость, чтобы медленная не забрала всё.

```text
CLOSED ──(много ошибок)──▶ OPEN ──(таймаут)──▶ HALF-OPEN
   ▲                                         │
   └──────────(пробные вызовы успешны)───────┘
```

## Монолит или микросервисы

| | Монолит | Микросервисы |
|---|---|---|
| Деплой | Целиком | Независимо по сервисам |
| Масштабирование | Целиком | По сервисам |
| Транзакции | Локальные ACID | Саги, eventual consistency |
| Отладка | Проще | Распределённый трейсинг |
| Подходит | Маленькой команде, новому продукту | Многим командам, зрелому домену |

Микросервисы — прежде всего организационное решение. Частый совет — **модульный монолит** с чёткими границами и выделение сервисов по реальной причине. Худший вариант — «распределённый монолит»: много сервисов с общей БД и цепочками синхронных вызовов.

## Частые вопросы на собеседовании

- Kafka vs RabbitMQ? → Лог с хранением и replay против очереди с удалением после ack.
- Как не задвоить обработку при at-least-once? → Идемпотентность: ID сообщений, UPSERT, версии.
- Как атомарно записать в БД и отправить событие? → Transactional outbox.
- Почему не 2PC? → Блокирующий протокол, координатор — точка отказа.
- Хореография vs оркестрация? → События без центра против явного координатора.
- Зачем jitter в ретраях? → Разбить синхронные волны повторных запросов.

## Шпаргалка

- Очередь — буфер и развязка; Kafka — лог с offset и порядком в партиции
- At-least-once + идемпотентность = практический exactly-once
- Outbox вместо двойной записи; саги с компенсациями вместо 2PC
- CQRS — раздельные модели; event sourcing — события как источник истины
- Таймауты, backoff + jitter, retry budget, circuit breaker, bulkhead
- Модульный монолит → микросервисы по реальной необходимости
