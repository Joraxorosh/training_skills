Большая языковая модель (LLM) — это трансформер-декодер с миллиардами параметров, обученный предсказывать следующий токен. Для инженера важно понимать, как модель видит текст, откуда берутся её сильные и слабые стороны, как управлять генерацией и из чего складываются стоимость и задержка.

## Токены и контекст

Модель работает не с символами и не со словами, а с **токенами** — фрагментами из фиксированного словаря. Частые слова — один токен, редкие разбиваются на части. Популярный алгоритм — **BPE**: начинаем с байтов и итеративно объединяем самые частые пары, пока словарь не достигнет нужного размера. Неизвестных слов не бывает — любое собирается из кусочков.

Следствия:

- Цена и лимиты считаются в токенах; на разных языках один и тот же текст занимает разное число токенов.
- Задачи «посчитай буквы» и посимвольные операции даются модели плохо — она не видит символы напрямую.

**Контекстное окно** — максимум токенов за один вызов: системный промпт, история, документы и ответ делят один бюджет. Всё за пределами окна модель не видит; даже в пределах окна информация в середине длинного контекста может использоваться хуже.

## Как обучают LLM

| Этап | Данные | Что даёт |
|---|---|---|
| Pretraining | огромный корпус текстов и кода, next-token prediction | знания о языке и мире |
| Instruction tuning (SFT) | пары «инструкция → эталонный ответ» | умение следовать инструкциям и формату |
| Обучение по предпочтениям (RLHF, RLAIF, DPO) | сравнения «какой ответ лучше» от людей или модели | полезность, безопасность, стиль |

**Галлюцинации** — уверенные, правдоподобные, но ложные утверждения. Модель оптимизирована на правдоподобный текст, а не на истину. Снижают их опора на источники (RAG), разрешение отвечать «не знаю», проверка фактов инструментами.

## Параметры генерации

На каждом шаге модель выдаёт распределение по словарю, из которого выбирается токен.

- **temperature** — делит логиты перед softmax. Около 0 — почти детерминированный выбор самого вероятного токена; выше — разнообразнее и рискованнее.
- **top-k** — оставить k самых вероятных токенов.
- **top-p (nucleus)** — оставить минимальный набор токенов с суммарной вероятностью не меньше p; размер набора динамический.
- **max_tokens** — лимит длины ответа, на качество фактов не влияет.

Для извлечения данных и кода — низкая температура, для мозгового штурма — повыше.

## Адаптация модели

- **Промптинг и few-shot** — самый дешёвый способ, веса не меняются.
- **RAG** — подмешивать актуальные знания в контекст.
- **Full fine-tuning** — дообучение всех весов; дорого по памяти.
- **PEFT / LoRA** — веса заморожены, обучаются малые низкоранговые матрицы `ΔW = B·A`. Адаптер весит мегабайты, на одну базу можно навесить несколько. **QLoRA** — LoRA поверх квантизованной базы.

Fine-tuning хорош для устойчивого стиля, формата, узкого навыка и сокращения длинных промптов. Для часто меняющихся фактов лучше RAG.

## Инференс: память, стоимость, задержка

Память на веса ≈ число параметров × байт на параметр:

| Формат | Байт на параметр | Модель 7B |
|---|---|---|
| fp32 | 4 | ~28 ГБ |
| fp16 / bf16 | 2 | ~14 ГБ |
| int8 | 1 | ~7 ГБ |
| int4 | 0.5 | ~3.5 ГБ |

**Квантизация** уменьшает память и ускоряет генерацию ценой некоторой потери качества (int4 теряет больше int8).

Генерация состоит из двух фаз:

1. **Prefill** — весь вход обрабатывается параллельно; определяет **TTFT** (time to first token) и растёт с длиной промпта.
2. **Decode** — по одному токену; скорость ограничена пропускной способностью памяти.

**KV cache** хранит ключи и значения attention уже обработанных токенов, чтобы не пересчитывать префикс на каждом шаге. Его объём растёт с длиной контекста и числом параллельных запросов. **Prompt caching** у провайдеров переиспользует KV для совпадающего префикса, поэтому неизменную часть промпта ставят в начало, а переменную — в конец.

Стоимость API обычно считается по входным и выходным токенам (выходные дороже). Рычаги: меньшая модель для простых задач, короткие промпты, кэширование, batch-API.

## Модели и их виды

- **Open-weight** — веса доступны: можно развернуть у себя, дообучить, держать данные внутри периметра; платите инфраструктурой и эксплуатацией.
- **API-модели** — быстрый старт, нет забот о GPU, обычно сильнейшее качество; данные уходят провайдеру.
- **Embedding-модели** возвращают вектор для поиска и кластеризации; **чат-модели** генерируют текст.
- **Мультимодальные** модели принимают изображения, аудио и другие данные наряду с текстом: визуальный энкодер превращает картинку в последовательность векторов.

## Частые вопросы на собеседовании

- Что такое токен и почему модель плохо считает буквы? → Подслово из словаря; символы внутри токена явно не видны.
- Чем RLHF отличается от SFT? → SFT копирует эталон, RLHF оптимизирует по сравнительным предпочтениям.
- temperature vs top-p? → Температура меняет форму распределения, top-p обрезает хвост.
- Сколько памяти нужно 7B в fp16? → ~14 ГБ на веса плюс KV cache.
- Что такое KV cache и prompt caching? → Кэш attention внутри генерации и переиспользование префикса между запросами.
- Fine-tuning или RAG для новых фактов? → RAG; fine-tuning — для поведения и формата.

## Шпаргалка

- BPE: слияние частых пар; лимиты и цена — в токенах
- pretraining → SFT → preference tuning (RLHF/RLAIF/DPO)
- temperature ≈ 0 — детерминизм; top-p — динамическое ядро; top-k — фиксированное
- память весов = параметры × байты; fp16 = 2, int4 = 0.5
- prefill → TTFT; decode → токены/с; KV cache растёт с контекстом
- LoRA: заморозить базу, учить `B·A`
- статичное в начало промпта ради prompt caching
