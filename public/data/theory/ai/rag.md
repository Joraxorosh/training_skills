RAG (Retrieval-Augmented Generation) — архитектура, в которой перед генерацией ответа система находит релевантные фрагменты документов и передаёт их модели в контекст. Так LLM отвечает по вашим актуальным данным, может ссылаться на источники и не требует переобучения при каждом обновлении базы знаний. На собеседовании разбирают эмбеддинги, векторные индексы, чанкинг, гибридный поиск и диагностику плохих ответов.

## Эмбеддинги и сходство

**Эмбеддинг** — вектор фиксированной длины, отражающий смысл текста: похожие по смыслу тексты близки в пространстве. Его строит отдельная embedding-модель (bi-encoder).

**Косинусное сходство**: `cos(a, b) = a·b / (|a|·|b|)`, от −1 до 1, зависит только от направления векторов. Если векторы нормализованы до единичной длины, косинус равен скалярному произведению, которое дешевле считать.

```python
import numpy as np

a = np.array([1, 1, 0])
b = np.array([1, 0, 1])
print(a @ b / (np.linalg.norm(a) * np.linalg.norm(b)))  # ≈ 0.5
```

> Документы и запросы должны кодироваться одной и той же моделью. Векторы разных моделей несравнимы даже при одинаковой размерности, а смена модели требует полной переиндексации.

## Пайплайн RAG

Индексация (офлайн):

1. Загрузить и очистить документы, сохранить метаданные (источник, дата, права доступа).
2. Разбить на чанки.
3. Посчитать эмбеддинги и положить в векторный индекс.

Запрос (онлайн):

1. Посчитать эмбеддинг вопроса (иногда предварительно переформулировать его).
2. Найти top-k кандидатов, отфильтровать по метаданным и правам.
3. Переранжировать и оставить лучшие.
4. Передать их LLM с инструкцией отвечать по контексту и ссылаться на источники.

## Чанкинг

Документы режут на фрагменты, потому что у embedding-модели ограничен вход, вектор маленького фрагмента точнее отражает одну тему, а в контекст LLM нужно передать только релевантное.

- **Слишком крупные чанки** — вектор «усредняет» много тем, поиск неточен, контекст засоряется.
- **Слишком мелкие** — теряется окружение, ответ разорван.
- **Overlap** (перекрытие) — чтобы мысль на границе целиком попала хотя бы в один чанк.
- Лучше резать по структуре: разделы, заголовки, абзацы, функции в коде.
- **Parent document retrieval** — искать по мелким чанкам, а в LLM отдавать родительский фрагмент.

## Векторные индексы и базы

Точный поиск ближайших соседей — полный перебор O(N). **ANN** (approximate nearest neighbor) жертвует небольшой долей recall ради многократного ускорения.

| Индекс | Идея | Плюсы и минусы |
|---|---|---|
| Flat | полный перебор | точный, медленный на больших объёмах |
| HNSW | многоуровневый граф близости | высокий recall и скорость, много памяти; параметры `M`, `ef_search` |
| IVF | кластеры + поиск в `nprobe` ближайших | экономнее по памяти, recall зависит от `nprobe` |
| IVF-PQ | IVF + сжатие векторов product quantization | миллиарды векторов, ниже точность |

Инструменты: **FAISS** — библиотека ANN; **pgvector** — расширение PostgreSQL (векторы рядом с данными и правами в одной БД); **Qdrant**, Weaviate, Milvus — специализированные векторные БД; **Pinecone** — управляемый облачный сервис. Важны фильтрация по метаданным и обновление индекса без простоя.

## Гибридный поиск и re-ranking

**BM25** — лексический поиск по совпадению слов с учётом их редкости. Он точно находит коды ошибок, артикулы, имена и редкие термины, которые эмбеддинги «размывают». Векторный поиск сильнее в синонимах и перефразировании. **Гибридный поиск** запускает оба и объединяет списки, чаще всего через **Reciprocal Rank Fusion** — по позициям, без сравнения несопоставимых оценок.

**Re-ranking**: cross-encoder получает пару «запрос + документ» целиком и оценивает релевантность точнее bi-encoder-а, но медленно. Поэтому схема: быстрый retrieval top-50 → rerank → top-5 в промпт.

## Оценка и выбор подхода

Оценивают оба этапа отдельно:

- **Retrieval**: recall@k (попал ли нужный чанк в top-k), MRR, nDCG.
- **Generation**: faithfulness (ответ опирается на контекст, а не на выдумку), релевантность ответа вопросу, корректность цитат.

Если бот ошибается, сначала проверьте, был ли нужный фрагмент в контексте. Нет — чините поиск (чанкинг, гибрид, rerank, переформулирование). Есть — промпт или модель.

| Подход | Когда выбирать |
|---|---|
| RAG | большие и часто меняющиеся знания, нужны источники и разграничение доступа |
| Fine-tuning | устойчивый стиль, формат, узкий навык; не для фактов, которые меняются |
| Длинный контекст | небольшой корпус, разовый анализ нескольких документов целиком |

## Частые вопросы на собеседовании

- Почему косинус, а не евклидово расстояние? → Важно направление; для нормализованных векторов они дают одинаковый порядок.
- HNSW vs IVF? → Граф с высоким recall и большой памятью против кластеров с `nprobe`.
- Зачем гибридный поиск? → BM25 ловит точные термины и коды, векторы — смысл.
- Зачем cross-encoder? → Точнее оценивает пару, применяется к top-N кандидатов.
- Как отладить плохой ответ RAG? → Разделить ошибки retrieval и generation, проверить recall@k.
- RAG или fine-tuning для базы знаний компании? → RAG: обновляемость, источники, права доступа.

## Шпаргалка

- `cos = a·b / (|a||b|)`; нормализованные векторы → dot product
- одна embedding-модель для документов и запросов; смена модели → переиндексация
- чанки по структуре, overlap, parent document retrieval
- ANN: HNSW (`M`, `ef`), IVF (`nprobe`), PQ для сжатия
- гибрид BM25 + векторы через RRF, затем cross-encoder rerank
- метрики: recall@k, faithfulness, answer relevance
- фильтрация по правам — на этапе поиска
