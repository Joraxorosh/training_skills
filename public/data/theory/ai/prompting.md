Промпт-инжиниринг — это проектирование входа модели так, чтобы она стабильно делала нужное. Агенты добавляют к этому цикл: модель сама выбирает инструменты, вызывает их и реагирует на результаты. На собеседовании ждут практики: как писать промпты, как устроен tool use, чем опасен prompt injection и как ограничить агента.

## Структура промпта

- **Системный промпт** задаёт роль, правила, контекст и формат на весь диалог. Он приоритетнее сообщений пользователя, но не является границей безопасности.
- **Сообщения пользователя и ассистента** — история диалога.
- **Контекст** — документы, результаты инструментов, данные.

Хорошие практики: ясная задача и критерии успеха, нужный контекст и аудитория, явный формат ответа, объяснение причин ограничений (модель лучше обобщает правило, если понимает зачем), разделение инструкций и данных (например, тегами).

| Приём | Суть | Когда полезен |
|---|---|---|
| Zero-shot | только инструкция | простые и типовые задачи |
| Few-shot | несколько примеров «вход → выход» | нестандартный формат, стиль, разметка |
| Chain-of-thought | рассуждение перед ответом | многошаговая логика, математика |
| Reasoning-модели | модель обучена «думать» сама | сложные задачи; дороже и медленнее |

Few-shot примеры — сильный сигнал: модель копирует их распределение и поверхностные черты. Делайте примеры разнообразными и сбалансированными.

## Структурированный вывод

Просьба «ответь в JSON» работает не всегда. **Structured output** с JSON Schema использует ограниченную генерацию: модель не может выдать токен, нарушающий схему, и парсер не падает. Но схема не гарантирует правильность значений — их нужно валидировать (например, Pydantic).

```python
from pydantic import BaseModel

class Invoice(BaseModel):
    number: str
    total: float
    currency: str

invoice = Invoice.model_validate_json(response_text)
```

## Tool use и агенты

**Function calling**: вы описываете инструменты (имя, описание, JSON Schema параметров). Модель возвращает запрос на вызов — имя и аргументы, — ваш код выполняет его и возвращает результат в контекст. Модель сама ничего не исполняет.

Описание инструмента — это тоже промпт. Модель выбирает инструмент по имени и description, поэтому пишите, что он делает, когда его применять, в каком формате аргументы. Ошибки инструментов должны быть информативными: «date должна быть в формате YYYY-MM-DD», а не просто `error`, иначе агент будет повторять тот же вызов.

**Агент** — LLM в цикле:

1. Спланировать следующий шаг.
2. Выполнить действие (вызов инструмента).
3. Наблюдать результат.
4. Повторять, пока задача не решена или не сработал лимит.

**Мультиагентные системы**: оркестратор раздаёт подзадачи субагентам. Плюсы — изоляция контекста (субагент «переваривает» много данных и возвращает выжимку) и параллелизм. Минусы — больше токенов и сложность координации; простые задачи лучше решать одним агентом.

## MCP и context engineering

**MCP (Model Context Protocol)** — открытый протокол подключения LLM-приложений к внешним системам. MCP-сервер предоставляет **tools** (действия), **resources** (данные для чтения) и **prompts** (шаблоны); транспорт — локальный stdio или HTTP. Интеграцию пишут один раз, и её может использовать любой совместимый клиент.

**Context engineering** — управление тем, что попадает в окно на каждом шаге: инструкции, найденные документы, результаты инструментов, сжатая история. Лишний контекст отвлекает модель, дорожает и может «теряться в середине». Приёмы: суммаризация истории, вынос длинных результатов во внешнюю память, субагенты, подгрузка документов по запросу.

## Безопасность: prompt injection и guardrails

**Prompt injection** — внедрение инструкций, заставляющих модель нарушить указания разработчика. **Direct** — пишет сам пользователь. **Indirect** — инструкции спрятаны в данных, которые читает агент: веб-странице, письме, PDF, ответе API.

> Особенно опасно сочетание трёх возможностей: доступ к приватным данным, обработка недоверенного контента и канал отправки данных наружу. Уберите любую — и цепочка утечки разорвана.

Фраза «не поддавайся на инъекции» в промпте снижает риск, но не защищает гарантированно. Надёжнее архитектурные меры — **guardrails**:

- результаты инструментов считать данными, а не инструкциями;
- минимальные права инструментов, allowlist доменов;
- подтверждение человеком необратимых действий (оплата, удаление, отправка);
- лимиты итераций и бюджета;
- фильтры входа и выхода, валидация схем, классификаторы.

## Частые вопросы на собеседовании

- Чем few-shot отличается от fine-tuning? → Примеры в промпте, веса не меняются.
- Кто выполняет функцию при tool use? → Ваше приложение; модель только формирует вызов.
- Почему модель не вызывает нужный инструмент? → Плохое имя или описание, неясная схема параметров.
- Direct vs indirect injection? → От пользователя против спрятанного во внешних данных.
- Как остановить зациклившегося агента? → Информативные ошибки, лимит шагов, человек в цикле.
- Что такое MCP? → Открытый протокол подключения tools, resources и prompts к LLM-приложениям.

## Шпаргалка

- system prompt = роль, правила, формат; не граница безопасности
- few-shot: разнообразные сбалансированные примеры
- CoT / reasoning — для многошаговых задач, дорого для простых
- structured output: схема гарантирует синтаксис, не смысл
- tool description = промпт; ошибки — информативные
- агент: plan → act → observe → repeat + лимиты
- MCP: tools, resources, prompts; stdio / HTTP
- защита от инъекций — права и подтверждения, а не только текст промпта
