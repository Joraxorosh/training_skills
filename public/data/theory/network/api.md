Проектирование API — это договорённость между командами, которую потом годами нельзя сломать. Интервьюер хочет услышать не только «REST — это ресурсы», но и как вы делаете пагинацию, ретраи без дублей, лимиты, эволюцию схемы и когда выбираете gRPC, GraphQL или WebSocket вместо обычного HTTP.

## REST: ресурсы, методы, коды

URL называет ресурс существительными, действие задаёт метод:

```http
GET    /users/42/orders        # список заказов пользователя
POST   /orders                 # создать → 201 + Location: /orders/123
PUT    /orders/123             # заменить целиком
PATCH  /orders/123             # изменить часть полей
DELETE /orders/123             # → 204 No Content
```

`/getUserOrders?id=42` — признак RPC-стиля. `PUT` заменяет представление целиком, `PATCH` вносит частичные изменения (JSON Merge Patch, JSON Patch).

| Ситуация | Код |
|---|---|
| Синтаксически неверный JSON | 400 |
| Поля не прошли валидацию | 422 (или 400) |
| Нет или неверный токен | 401 |
| Нет прав | 403 |
| Ресурс уже существует, конфликт версии | 409 |
| Превышен лимит | 429 + `Retry-After` |
| Длительная операция принята | 202 + `Location` на статус |

Для долгих операций `POST /reports` возвращает `202 Accepted` и ссылку на ресурс операции; клиент опрашивает его или получает webhook. Держать HTTP-запрос открытым минутами нельзя: его оборвут таймауты прокси.

## Пагинация

**Offset** (`LIMIT 20 OFFSET 10000`) прост и позволяет прыгнуть на страницу N, но база сканирует и выбрасывает все пропущенные строки, а вставки сдвигают окно — появляются дубли и пропуски.

**Cursor (keyset)** запоминает позицию последнего элемента:

```sql
SELECT * FROM posts
WHERE (created_at, id) < (:last_created_at, :last_id)
ORDER BY created_at DESC, id DESC
LIMIT 20;
```

`id` нужен как tie-breaker: `created_at` может совпадать. Курсор отдают клиенту непрозрачной строкой (base64), запрос использует составной индекс и стабилен при вставках. Минус — нет перехода на произвольную страницу и обычно нет total.

## Надёжность: идемпотентность, лимиты, версионирование

`POST` не идемпотентен: если ответ потерялся, клиент не знает, прошла ли операция. **Idempotency-Key** решает это: клиент генерирует UUID, сервер сохраняет ключ с результатом и на повтор отдаёт тот же ответ.

```http
POST /v1/payments
Idempotency-Key: 8e03978e-40d5-43e8-bc93-6894a57f9324
```

**Rate limiting** защищает сервис и делит ресурсы между клиентами:

- token bucket — допускает всплеск до ёмкости ведра, средняя скорость = скорости пополнения
- leaky bucket — строго равномерный темп с очередью
- fixed window / sliding window — счётчик запросов за интервал

При превышении — `429` и `Retry-After`; клиент ретраит с exponential backoff и jitter.

**Версионирование**: в пути (`/v1/users`, проще для кэшей и людей), в заголовке (`Accept: application/vnd.acme.v2+json`) или в query-параметре. Добавление полей обратно совместимо, удаление и переименование — нет.

**OpenAPI** описывает API в YAML/JSON: по спецификации генерируют документацию (Swagger UI), клиенты, моки и contract-тесты.

## gRPC и Protocol Buffers

gRPC — RPC поверх HTTP/2 с контрактом в `.proto` и бинарной сериализацией protobuf. Режимы: unary, server streaming, client streaming, двунаправленный. Браузер не может вызвать gRPC напрямую (нет доступа к HTTP/2-фреймам и trailers), нужен gRPC-Web через прокси.

```proto
syntax = "proto3";

message User {
  int64 id = 1;
  string email = 3;
  string phone = 4;   // новое поле — безопасно
  reserved 2;         // номер удалённого поля не переиспользуем
}
```

В бинарном формате поле определяется **номером**, а не именем. Безопасно добавлять поля с новыми номерами; опасно менять тип и переиспользовать номера.

## GraphQL

Клиент запрашивает ровно нужные поля одним запросом — это решает **overfetching** (лишние поля) и **underfetching** (несколько запросов на экран) REST.

Проблемы:

- **N+1**: резолвер `author` вызывается для каждого из 50 постов → 51 запрос к базе. Решение — DataLoader: батч `WHERE id IN (...)` и кэш в пределах запроса.
- **HTTP-кэширование**: все запросы — `POST /graphql`, CDN кэширует по URL. Помогают persisted queries через `GET` с хэшем и нормализованный клиентский кэш.
- **Дорогие запросы**: нужны лимиты глубины и сложности.

## Реальное время и события

| Механизм | Направление | Транспорт | Когда |
|---|---|---|---|
| Long polling | Сервер → клиент | Обычный HTTP, запрос висит до события | Простой fallback |
| SSE | Сервер → клиент | `text/event-stream`, автопереподключение, `Last-Event-ID` | Уведомления, ленты, стриминг ответов LLM |
| WebSocket | Двунаправленный | HTTP `Upgrade` → `101`, затем фреймы | Чаты, игры, совместное редактирование |
| Webhook | Сервис → ваш сервер | `POST` на ваш URL | Интеграции между сервисами |

Приём webhook-ов: проверяйте HMAC-подпись тела, отклоняйте старые метки времени (replay), отвечайте 2xx быстро и обрабатывайте асинхронно, дедуплицируйте по id события — провайдер будет ретраить.

## Частые вопросы на собеседовании

- PUT или PATCH? → Полная замена против частичного изменения.
- Как не провести платёж дважды при ретрае? → Idempotency-Key.
- Offset или cursor? → Cursor для больших и часто меняющихся данных.
- Что такое N+1 в GraphQL? → Запрос на каждый элемент списка; лечится DataLoader.
- WebSocket или SSE? → SSE достаточно, если данные идут только от сервера.
- Как безопасно менять protobuf-схему? → Только добавлять поля, не трогать номера, `reserved` для удалённых.

## Шпаргалка

- Ресурсы — существительные; 201 + Location, 204, 202 для долгих операций
- 409 конфликт, 422 валидация, 429 + Retry-After
- Cursor: `(created_at, id)` + составной индекс
- Idempotency-Key для POST; token bucket допускает burst
- gRPC: HTTP/2 + protobuf, 4 режима, gRPC-Web для браузера
- GraphQL: N+1 → DataLoader; кэш → persisted queries
- WebSocket — двунаправленный; SSE — сервер → клиент; webhook — HMAC + идемпотентность
