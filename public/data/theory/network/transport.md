Транспортный уровень доставляет данные между процессами: IP довозит пакет до хоста, а порт указывает, какому приложению он предназначен. TCP даёт надёжный упорядоченный поток, UDP — минимальную обёртку над IP, а QUIC строит надёжность поверх UDP заново. На собеседовании любят состояния соединений из `ss`, тюнинг задержек и вопросы «почему HTTP/3 на UDP».

## Порты и идентификация соединения

Соединение TCP однозначно задаётся четвёркой: IP и порт источника, IP и порт назначения. Поэтому сервер на одном порту 443 держит тысячи клиентов. Клиентский порт ядро берёт из эфемерного диапазона (в Linux `net.ipv4.ip_local_port_range`, по умолчанию 32768–60999).

```bash
$ ss -tn
ESTAB 0 0 192.168.1.5:51234 93.184.216.34:443
```

К одному `IP:порт` клиент может открыть около 28 тысяч соединений. Если сервис открывает и закрывает соединения без пула, порты зависают в TIME_WAIT и появляется ошибка `Cannot assign requested address` — **исчерпание эфемерных портов**. Лечится keep-alive и пулами, `tcp_tw_reuse`, дополнительными IP.

## Жизненный цикл TCP

Установка: SYN → SYN-ACK → ACK. Закрытие: каждая сторона отправляет FIN и получает ACK. RST — аварийный обрыв, например ответ на SYN к закрытому порту («connection refused»).

| Состояние | Где | Что значит |
|---|---|---|
| `SYN_RECV` | Сервер | Получен SYN, ждём ACK; много таких — признак SYN flood |
| `ESTABLISHED` | Обе | Соединение открыто |
| `CLOSE_WAIT` | Пассивная сторона | Пир прислал FIN, приложение ещё не вызвало `close()` |
| `TIME_WAIT` | Активно закрывший | Ожидание 2×MSL (в Linux 60 с) |

Растущий `CLOSE_WAIT` — почти всегда утечка сокетов в приложении. **TIME_WAIT** нужен по двум причинам: можно повторить последний ACK, если он потерялся, а запоздавшие сегменты старого соединения не попадут в новое с той же четвёркой. **SYN cookies** защищают от SYN flood: сервер не хранит полуоткрытые соединения, а кодирует их параметры в своём начальном sequence number.

TCP — **поток байтов**, границы `send()` не сохраняются: два сообщения по 100 байт могут прийти одним `recv()` на 200 байт или кусками. Поэтому протоколы сами задают кадрирование: длина-префикс, разделитель, `Content-Length`.

## Надёжность, flow control и congestion control

Каждый байт имеет sequence number, получатель подтверждает принятое ACK-ами. Потеря определяется двумя способами: по таймеру RTO или по **трём дублирующим ACK** (fast retransmit — быстрее, без ожидания таймера).

Два разных окна:

- **rwnd** (flow control) — сколько свободно в буфере получателя, защищает получателя
- **cwnd** (congestion control) — сколько отправитель решился держать «в полёте», защищает сеть

Отправляется не больше min(rwnd, cwnd). В **slow start** cwnd удваивается каждый RTT до ssthresh, дальше растёт медленно (congestion avoidance), при потере уменьшается. **CUBIC** (по умолчанию в Linux) реагирует на потери, **BBR** моделирует пропускную способность узкого места и минимальный RTT и не заполняет буферы роутеров.

Пропускная способность одного соединения ограничена окном: скорость ≤ окно / RTT. Без window scaling окно 64 КБ, и при RTT 80 мс это около 6,5 Мбит/с даже на гигабитном канале. Чтобы заполнить канал, окно должно быть не меньше **bandwidth-delay product**.

## Задержки: Nagle, delayed ACK, keepalive

**Алгоритм Нейгла** не отправляет новый мелкий сегмент, пока предыдущий не подтверждён. Получатель же откладывает ACK (delayed ACK, до ~40 мс). Вместе они дают характерные задержки 40 мс у интерактивных протоколов, поэтому HTTP-клиенты, Redis и базы включают `TCP_NODELAY`.

**TCP keepalive** после простоя шлёт пробы и закрывает соединение, если пир молчит. Заодно не даёт NAT и файрволам забыть соединение.

```bash
net.ipv4.tcp_keepalive_time = 7200    # первая проба через 2 часа простоя
net.ipv4.tcp_keepalive_intvl = 75
net.ipv4.tcp_keepalive_probes = 9
```

Не путайте с HTTP keep-alive — переиспользованием соединения для нескольких запросов.

## UDP и QUIC

UDP добавляет к IP только порты, длину и контрольную сумму (8 байт заголовка). Нет соединения, доставки, порядка и контроля перегрузки. Он подходит, когда опоздавшие данные бесполезны (VoIP, игры, стриминг), когда запрос помещается в один пакет (DNS, DHCP) и как основа для своих протоколов (QUIC, WireGuard).

**Head-of-line blocking**: TCP отдаёт байты строго по порядку, поэтому одна потеря задерживает всё, что пришло после. В HTTP/2 это значит, что страдают все стримы сразу.

**QUIC** (RFC 9000) решает это поверх UDP:

- независимые стримы: потеря влияет только на свой стрим
- рукопожатие совмещено с TLS 1.3: 1 RTT для нового соединения, 0-RTT для повторного
- Connection ID: соединение переживает смену IP (Wi-Fi → LTE)
- шифруется почти всё, включая служебные данные; реализация в user space, что ускоряет развитие протокола

> Обратная сторона QUIC: некоторые сети блокируют UDP/443, и клиенты откатываются на TCP.

## Частые вопросы на собеседовании

- Кто попадает в TIME_WAIT и зачем? → Активно закрывшая сторона, на 2×MSL: повтор последнего ACK и защита от старых сегментов.
- Много CLOSE_WAIT — что делать? → Искать в коде незакрытые сокеты.
- Flow control vs congestion control? → rwnd защищает получателя, cwnd — сеть.
- Откуда задержка 40 мс? → Nagle + delayed ACK, лечится `TCP_NODELAY`.
- Зачем HTTP/3 ушёл на UDP? → Убрать HOL blocking TCP, ускорить рукопожатие, миграция соединений.
- Что гарантирует UDP? → Только контрольную сумму датаграммы.

## Шпаргалка

- Соединение = 4-кортеж; эфемерные порты 32768–60999
- RST — обрыв; FIN — штатное закрытие; TIME_WAIT 60 с в Linux
- 3 дубля ACK → fast retransmit; таймаут → RTO
- Скорость ≤ окно / RTT; BDP = bandwidth × RTT
- `TCP_NODELAY` против Нейгла; keepalive по умолчанию 7200 с
- UDP: 8 байт заголовка, DNS, DHCP, VoIP, QUIC
- QUIC: UDP, TLS 1.3 внутри, стримы без HOL, Connection ID
