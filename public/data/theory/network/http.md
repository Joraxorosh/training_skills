HTTP — протокол запрос-ответ, на котором работает веб и большинство API. Семантика (методы, коды, заголовки) одинакова во всех версиях, а меняется транспорт: текст поверх TCP в HTTP/1.1, бинарные фреймы в HTTP/2, QUIC в HTTP/3. TLS отвечает за шифрование и подлинность сервера. На собеседовании проверяют свойства методов, коды ответов, кэширование и что происходит при установке HTTPS-соединения.

## Сообщения и методы

```http
GET /index.html HTTP/1.1
Host: example.com
Accept: text/html

HTTP/1.1 200 OK
Content-Type: text/html
Content-Length: 1256
```

В HTTP/1.1 заголовок `Host` обязателен: на одном IP живёт много сайтов. В HTTP/2 и HTTP/3 его роль играет псевдозаголовок `:authority`.

| Метод | Safe | Идемпотентный | Назначение |
|---|---|---|---|
| GET, HEAD | Да | Да | Чтение |
| OPTIONS | Да | Да | Возможности, CORS preflight |
| PUT | Нет | Да | Полная замена |
| DELETE | Нет | Да | Удаление |
| POST | Нет | Нет | Создание, произвольные действия |
| PATCH | Нет | Не гарантирован | Частичное изменение |

**Safe** — не меняет состояние. **Идемпотентный** — повтор даёт тот же результат, такие запросы можно безопасно ретраить.

## Коды ответов

- `200` OK, `201` Created (+ `Location`), `202` Accepted, `204` No Content
- `301`/`308` — постоянный редирект, `302`/`307` — временный; 307 и 308 сохраняют метод и тело, а при 301/302 браузеры превращают POST в GET
- `304` Not Modified — ответ на условный запрос, без тела
- `400` неверный запрос, `401` не аутентифицирован, `403` нет прав, `404`, `409` конфликт, `429` лимит
- `502` апстрим вернул мусор или недоступен, `503` сервис временно не может, `504` апстрим не ответил вовремя

## Кэширование

`Cache-Control` управляет кэшами браузера и общими (CDN, прокси):

| Директива | Смысл |
|---|---|
| `max-age=N` | Свежесть N секунд |
| `s-maxage=N` | То же для общих кэшей, переопределяет max-age |
| `no-cache` | Хранить можно, но перед использованием ревалидировать |
| `no-store` | Не хранить нигде |
| `private` / `public` | Только браузер / любые кэши |
| `stale-while-revalidate=N` | N секунд отдавать устаревшее, обновляя в фоне |

Ревалидация: сервер отдаёт `ETag: "33a64df5"` (или `Last-Modified`), клиент повторяет запрос с `If-None-Match: "33a64df5"` и получает `304` без тела. `If-Match` с ETag используют наоборот — для оптимистичной блокировки при изменении (иначе `412`).

`Vary: Accept-Encoding` добавляет заголовок запроса к ключу кэша, чтобы gzip-версия не досталась клиенту без gzip. `Vary: Cookie` или `User-Agent` практически отключает кэширование в CDN.

## Cookies и безопасность

```http
Set-Cookie: sid=a1b2c3; Path=/; Max-Age=3600; Secure; HttpOnly; SameSite=Lax
```

- `Max-Age`/`Expires` — без них cookie сессионная
- `Secure` — только по HTTPS; `HttpOnly` — недоступна JavaScript
- `SameSite` — ограничивает отправку в кросс-сайтовых запросах
- `Domain` — без него cookie только для точного хоста

**HSTS** (`Strict-Transport-Security: max-age=31536000; includeSubDomains`) заставляет браузер ходить на домен только по HTTPS и запрещает пропускать ошибки сертификата. Первый визит защищает HSTS preload list.

## Версии HTTP

**HTTP/1.1**: соединения постоянные по умолчанию (`Connection: close` закрывает), но запросы в одном соединении идут последовательно, поэтому браузеры открывают ~6 соединений на хост.

**HTTP/2**: бинарный фрейминг, мультиплексирование стримов в одном TCP-соединении, сжатие заголовков **HPACK**. Head-of-line blocking на уровне TCP остаётся: одна потеря тормозит все стримы.

**HTTP/3** работает поверх QUIC (UDP), где потеря влияет только на свой стрим, а сжатие заголовков — QPACK. Поскольку TCP не может «переключиться» на UDP, браузер узнаёт о поддержке из `Alt-Svc: h3=":443"` или DNS-записи `HTTPS` (SVCB) и при блокировке UDP откатывается на TCP.

## TLS 1.3

1. ClientHello: версии, шифры, **key share**, SNI (имя сайта), ALPN (`h2`, `http/1.1`).
2. ServerHello со своим key share — ключи уже вычислены, дальше всё зашифровано.
3. Сервер отправляет Certificate, CertificateVerify, Finished.
4. Клиент проверяет цепочку и отправляет Finished вместе с первыми данными.

Итого **1 RTT** (TLS 1.2 — 2 RTT). При возобновлении возможен **0-RTT**, но такие данные уязвимы к replay, поэтому годятся только для идемпотентных запросов.

Что изменилось относительно 1.2: только эфемерный (EC)DHE, значит forward secrecy обязательна; статический RSA, CBC и RC4 удалены; сертификат передаётся зашифрованным. **SNI** открыт, его скрывает отдельное расширение ECH.

Сервер должен отдавать leaf-сертификат и **промежуточные**; корень берётся из trust store клиента. Без intermediate браузер может справиться, а curl и Java — нет.

```bash
openssl s_client -connect example.com:443 -servername example.com -showcerts
curl -v --http2 https://example.com
```

## Частые вопросы на собеседовании

- Чем PUT отличается от POST? → PUT идемпотентен и заменяет ресурс по известному URL.
- no-cache и no-store? → Ревалидировать перед использованием против «не хранить вовсе».
- 502 и 504? → Плохой ответ или отказ соединения против таймаута апстрима.
- Что дал HTTP/2 и что осталось нерешённым? → Мультиплексирование и HPACK; HOL на уровне TCP.
- Сколько RTT у TLS 1.3? → 1, при возобновлении 0-RTT.
- Зачем SNI? → Выбрать сертификат, когда на одном IP много доменов.

## Шпаргалка

- Safe: GET, HEAD, OPTIONS; идемпотентные: + PUT, DELETE
- 307/308 сохраняют метод; 304 — ответ на If-None-Match
- `s-maxage` для CDN, `no-cache` ≠ `no-store`, `Vary` расширяет ключ
- Cookie: Secure, HttpOnly, SameSite, Max-Age
- HTTP/2: фреймы, стримы, HPACK; HTTP/3: QUIC, Alt-Svc
- TLS 1.3: 1 RTT, (EC)DHE, зашифрованный Certificate, открытый SNI
