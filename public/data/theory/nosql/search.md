Elasticsearch — распределённый поисковый и аналитический движок на базе Apache Lucene. Его используют для полнотекстового поиска, фасетной навигации, логов и observability. OpenSearch — его открытый форк. На собеседовании спрашивают, как устроен инвертированный индекс, чем `text` отличается от `keyword`, как работают шарды и почему ES — не основная БД.

## Инвертированный индекс и анализ

Инвертированный индекс отображает каждый **терм** в список документов (posting list) с частотами и позициями. Поиск сводится к выбору и пересечению таких списков.

```text
doc1: "Red running shoes"   doc2: "Blue shoes"
red     -> [doc1]
running -> [doc1]
shoes   -> [doc1, doc2]
blue    -> [doc2]
```

Термы получаются **анализатором**:

1. **Char filters** — правка исходного текста (удаление HTML, замены).
2. **Tokenizer** — разбиение на токены (`standard`, `whitespace`, `ngram`).
3. **Token filters** — нормализация: `lowercase`, стоп-слова, стемминг (`russian`), синонимы.

Обычно тот же анализатор применяется и к строке запроса, поэтому «Shoes» находит «shoes».

## Mapping: text и keyword

| | `text` | `keyword` |
|---|---|---|
| Анализ | Да, разбивается на токены | Нет, одно значение целиком |
| Запросы | `match`, `match_phrase` | `term`, `terms`, `prefix` |
| Сортировка и агрегации | Нет (fielddata выключена) | Да, через doc_values |
| Примеры | Заголовок, описание | Статус, email, id, бренд |

Строка без явного mapping по умолчанию становится `text` с подполем `.keyword` (`ignore_above: 256`). Для продакшена задают явный mapping и `"dynamic": "strict"`, чтобы избежать mapping explosion. Тип существующего поля сменить нельзя — только reindex. Одно значение можно индексировать двумя способами через multi-fields:

```json
"name": { "type": "text", "fields": { "raw": { "type": "keyword" } } }
```

## Запросы: query и filter context

```json
GET /products/_search
{
  "query": {
    "bool": {
      "must":   [ { "match": { "title": "running shoes" } } ],
      "filter": [ { "term":  { "brand": "acme" } },
                  { "range": { "price": { "lte": 100 } } } ],
      "should": [ { "term": { "in_stock": true } } ]
    }
  }
}
```

- **Query context** (`must`, `should`) отвечает на вопрос «насколько подходит» и считает `_score`.
- **Filter context** (`filter`, `must_not`) отвечает «подходит или нет», без скоринга, и кэшируется. Все точные условия выносят сюда.

Частая ошибка — `term` по text-полю: строка запроса не анализируется, а в индексе лежат токены в нижнем регистре, и совпадения нет.

**BM25** — алгоритм релевантности по умолчанию. В отличие от TF-IDF, вклад частоты терма насыщается (параметр `k1`), а длина поля нормализуется (параметр `b`). IDF по умолчанию считается по каждому шарду отдельно, поэтому на малых индексах скоры «гуляют» — помогает `dfs_query_then_fetch`.

## Агрегации и пагинация

```json
"size": 0,
"aggs": {
  "by_brand":  { "terms": { "field": "brand", "size": 10 } },
  "avg_price": { "avg":   { "field": "price" } }
}
```

Бывают bucket-агрегации (`terms`, `date_histogram`, `range`) и metric-агрегации (`avg`, `sum`, `cardinality` — приблизительная, на HyperLogLog++). Terms-счётчики приблизительны: каждый шард отдаёт свой локальный топ.

**Пагинация**: `from + size` ограничено `index.max_result_window` = 10 000, потому что каждый шард собирает и сортирует `from + size` документов. Для глубокой пагинации используют `search_after` с **Point in Time** и уникальным tie-breaker в сортировке. Для выгрузки всего индекса раньше применяли scroll, сейчас рекомендуется PIT + `search_after`.

## Шарды, реплики и near-real-time

- Индекс делится на **primary shards** — каждый является отдельным индексом Lucene. Документ попадает в шард по `hash(_routing) % number_of_primary_shards`, поэтому число primary меняется только через reindex, split или shrink.
- **Реплики** повышают отказоустойчивость и пропускную способность поиска. Их число можно менять динамически. Реплика никогда не лежит на одном узле со своим primary. Запись идёт в primary, а затем на все реплики.
- Ориентир — шарды размером 10–50 ГБ. Тысячи мелких шардов (**oversharding**) расходуют heap и раздувают cluster state.

**Near-real-time**: документ попадает в in-memory буфер и translog, а видимым для поиска становится после **refresh** (по умолчанию раз в 1 с), который создаёт новый сегмент. **Flush** делает Lucene commit на диск и очищает translog. Сегменты неизменяемы: обновление — это пометка удаления и новая версия документа, а **merge** фоново сливает сегменты и вычищает удалённые документы.

## Индексация и эксплуатация

- **Bulk API** вместо поштучной индексации: пачки по несколько мегабайт резко снижают накладные расходы.
- При массовой загрузке увеличивают `refresh_interval` (или ставят `-1`) и временно убирают реплики, а после загрузки возвращают настройки.
- **Aliases** позволяют переиндексировать без простоя: строим `products_v2`, затем атомарно переключаем alias `products` на новый индекс.
- **Index templates** задают mapping и настройки для новых индексов, например ежедневных индексов логов.
- **ILM** (в OpenSearch — ISM) управляет жизненным циклом: rollover по размеру или возрасту, перевод на «тёплые» узлы, удаление старых индексов.
- Heap JVM — не больше примерно половины RAM и до ~31 ГБ (compressed oops). Остальную память забирает page cache ОС, в которой живут сегменты Lucene.

## Не основная БД; Elasticsearch и OpenSearch

Причины не делать ES источником правды:

- нет многодокументных ACID-транзакций;
- изменение mapping требует переиндексации;
- near-real-time видимость;
- исторически более слабые гарантии сохранности при split brain и сбоях.

Типичная архитектура: PostgreSQL или MongoDB как источник правды, синхронизация в ES через CDC (Debezium) или очередь и возможность переиндексировать с нуля через alias-переключение.

| | Elasticsearch 8 | OpenSearch |
|---|---|---|
| Происхождение | Elastic | Форк ES 7.10 (2021, изначально AWS) |
| Лицензия | Elastic License / SSPL / AGPL | Apache 2.0 |
| UI | Kibana | OpenSearch Dashboards |
| Совместимость | — | Базовые API ES 7.10; клиенты ES 8 не всегда совместимы |

## Частые вопросы на собеседовании

- Что такое инвертированный индекс? → Отображение терма в список документов с позициями; основа полнотекстового поиска.
- `text` или `keyword`? → `text` — для полнотекстового поиска с анализом; `keyword` — для точных совпадений, сортировки и агрегаций.
- Почему документ не находится сразу после индексации? → Near-real-time: документ виден после refresh, по умолчанию через 1 с.
- Query или filter context? → Filter не считает score и кэшируется, поэтому точные условия выносят туда.
- Как сделать глубокую пагинацию? → `search_after` + PIT вместо `from`/`size`.
- Можно ли изменить число шардов? → Primary — только через reindex, split или shrink; реплики — в любой момент.

## Шпаргалка

- Анализатор: char filters → tokenizer → token filters.
- `match` — для text, `term` — для keyword.
- Точные условия — в `filter`; релевантность — BM25 (`k1`, `b`).
- `from + size` ≤ 10 000; глубже — `search_after` + PIT.
- Refresh 1 с → видимость; flush → commit; merge → чистка удалённых.
- Шард 10–50 ГБ; реплики не ускоряют запись.
- ES — вторичный индекс рядом с основной БД; OpenSearch — Apache 2.0 форк ES 7.10.
