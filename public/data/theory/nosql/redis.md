Redis — in-memory сервер структур данных: его используют как кэш, хранилище сессий, счётчики, rate limiter, очереди, таблицы лидеров и распределённые блокировки. На собеседовании проверяют, понимаете ли вы, **почему он быстрый и где его ограничения**: однопоточное выполнение, вытеснение, персистентность, асинхронная репликация и кластеризация.

## Типы данных

| Тип | Команды | Применение |
|---|---|---|
| String | `SET`, `GET`, `INCR`, `SETEX` | Кэш значений, счётчики, флаги |
| Hash | `HSET`, `HGET`, `HINCRBY` | Объекты с полями (профиль, корзина) |
| List | `LPUSH`, `RPOP`, `BLPOP`, `LRANGE` | Простые очереди, последние N событий |
| Set | `SADD`, `SISMEMBER`, `SINTER` | Уникальные элементы, теги, пересечения |
| Sorted Set | `ZADD`, `ZINCRBY`, `ZREVRANGE` | Лидерборды, приоритеты, sliding window |
| Stream | `XADD`, `XREADGROUP`, `XACK` | Персистентный лог событий с consumer groups |
| Bitmap | `SETBIT`, `BITCOUNT` | Флаги по id пользователя, активность по дням |
| HyperLogLog | `PFADD`, `PFCOUNT` | Приблизительный подсчёт уникальных (до 12 КБ, ошибка около 0.81%) |

```text
ZINCRBY leaderboard 50 "player:7"
ZREVRANGE leaderboard 0 9 WITHSCORES   # топ-10
HSET user:1 name Ann age 30
PFADD uv:2026-11-25 user:1 user:2 user:1
PFCOUNT uv:2026-11-25                  # около 2
```

## Модель выполнения

Команды выполняются **последовательно в одном потоке**, поэтому каждая команда атомарна, и не нужны блокировки. Скорость обеспечивают данные в памяти, эффективные структуры и мультиплексирование I/O. С версии 6 есть I/O-потоки, но они только читают и пишут сокеты.

Обратная сторона: любая долгая команда блокирует всех клиентов.

- `KEYS *` — O(N) по всем ключам. Используйте `SCAN` с курсором.
- `HGETALL`, `SMEMBERS`, `LRANGE 0 -1` по big key. Используйте `HSCAN`/`SSCAN`.
- `DEL` огромного ключа. Используйте `UNLINK`, который освобождает память в фоне.

Big keys ищут командой `redis-cli --bigkeys`. Их дробят на бакеты на уровне приложения.

## TTL и вытеснение

`EXPIRE key 60` или `SET key v EX 60` задают время жизни. `TTL` возвращает оставшиеся секунды, `-1` — если срока нет, `-2` — если ключа нет. Истёкшие ключи удаляются лениво (при обращении) и активно (выборочной фоновой проверкой).

При достижении `maxmemory` работает `maxmemory-policy`:

- `noeviction` (по умолчанию) — записи получают ошибку OOM;
- `allkeys-lru` / `allkeys-lfu` — вытеснение из всех ключей, типичный выбор для кэша;
- `volatile-lru` / `volatile-lfu` / `volatile-ttl` / `volatile-random` — только среди ключей с TTL; если таких нет, поведение как у `noeviction`;
- `allkeys-random`.

LRU и LFU в Redis приблизительные: используется выборка ключей, а не точный список.

## Персистентность и репликация

| | RDB | AOF |
|---|---|---|
| Что пишет | Снимок памяти по расписанию (fork + запись) | Журнал всех операций записи |
| Потери при сбое | Всё после последнего снимка | При `appendfsync everysec` — около 1 секунды |
| Размер и рестарт | Компактный файл, быстрая загрузка | Больше, переписывается (rewrite) |

Часто включают оба: начиная с Redis 7 AOF хранится как набор файлов с RDB-базой и инкрементами.

**Репликация асинхронная**: мастер отвечает клиенту, не дожидаясь реплик. При failover подтверждённые записи могут потеряться. `WAIT numreplicas timeout` сокращает окно потерь, но не даёт строгой консистентности.

## Sentinel и Cluster

- **Sentinel** — мониторинг, автоматический failover и service discovery для одного мастера с репликами. Шардирования нет.
- **Cluster** — шардирование по **16384 hash-слотам**: `slot = CRC16(key) mod 16384`. У каждого мастера свой диапазон слотов и свои реплики. Клиент получает `MOVED`/`ASK` и знает топологию.

Multi-key команды, `MULTI` и Lua в Cluster работают только для ключей одного слота. Связанные ключи объединяют hash tag:

```text
MSET {user:1}:name Ann {user:1}:age 30   # один слот, работает
MSET user:1:name Ann user:2:name Bob     # CROSSSLOT error
```

## Транзакции, pipelining, Lua

- **Pipelining** — отправка пачки команд без ожидания ответов. Экономит RTT, но не атомарен.
- **MULTI/EXEC** — команды выполняются подряд без вклинивания других клиентов. **Отката нет**: ошибка выполнения затрагивает только свою команду. `WATCH` даёт оптимистичную блокировку: EXEC отменяется, если ключ изменился.
- **Lua** (`EVAL`, функции в Redis 7) — скрипт выполняется атомарно и позволяет «прочитать, проверить, изменить». Долгий скрипт блокирует сервер.

## Распределённые блокировки и pub/sub

```text
SET lock:order:42 <uuid> NX PX 30000
```

`NX` — только если ключа нет, `PX` — TTL, чтобы упавший клиент не держал лок вечно. Уникальный токен нужен, чтобы при освобождении не снять чужой лок:

```lua
if redis.call("GET", KEYS[1]) == ARGV[1] then
  return redis.call("DEL", KEYS[1])
end
return 0
```

**Redlock** захватывает лок на большинстве из N независимых мастеров. Критика Клеппмана: пауза GC или скачок часов позволяет двум клиентам считать себя владельцами. Для корректности нужны **fencing-токены**, проверяемые хранилищем. Redis-лок хорош для эффективности (не делать работу дважды), а для строгой корректности берут etcd, ZooKeeper или БД.

**Pub/Sub** доставляет сообщения только текущим подписчикам (at-most-once) и ничего не хранит. Для надёжной доставки используют **Streams** с consumer groups и `XACK`.

## Типичные применения

**Rate limiter с фиксированным окном** — счётчик на пользователя и минуту:

```text
INCR rl:user:42:202611251530
EXPIRE rl:user:42:202611251530 60 NX   # NX: поставить TTL только при первом запросе
```

Если `INCR` вернул больше лимита — отказ. Для точного **скользящего окна** используют sorted set: `ZADD` с timestamp, `ZREMRANGEBYSCORE` для старых записей, `ZCARD` для подсчёта — и всё это в одном Lua-скрипте.

**Очередь задач**: `LPUSH` + `BRPOP` — просто, но сообщение теряется, если воркер упал после `BRPOP`. Надёжнее Streams: `XREADGROUP` выдаёт сообщение потребителю группы, оно висит в pending, пока не придёт `XACK`, а зависшие забирает `XAUTOCLAIM`.

**Сессии и кэш** — строки или hash с TTL. **Счётчики уникальных** — HyperLogLog. **Флаги активности по дням** — bitmap, где бит с номером `user_id` равен 1, а `BITCOUNT` считает активных.

## Частые вопросы на собеседовании

- Почему Redis быстрый, если он однопоточный? → Данные в памяти, нет блокировок и переключений контекста, I/O-мультиплексирование. Узкое место обычно сеть, а не CPU.
- Чем `SCAN` лучше `KEYS`? → Итеративный обход по курсору без долгой блокировки сервера.
- RDB или AOF? → RDB — компактные снимки с потерей данных между ними; AOF `everysec` — потеря около секунды. Часто включают оба.
- Есть ли откат в MULTI/EXEC? → Нет. Только последовательное выполнение без вклинивания; `WATCH` — для CAS.
- Sentinel или Cluster? → Sentinel — HA без шардирования; Cluster — шардирование по 16384 слотам плюс failover.
- Как сделать распределённый лок? → `SET NX PX` с уникальным токеном и освобождение через Lua. Для корректности нужны fencing-токены.

## Шпаргалка

- Лидерборд — ZSET, уникальные посетители — HyperLogLog, очередь с подтверждениями — Stream.
- `KEYS` → `SCAN`, `DEL` big key → `UNLINK`.
- `TTL`: `-1` — без срока, `-2` — нет ключа.
- Кэш: `allkeys-lru`/`allkeys-lfu`; `volatile-*` без TTL-ключей ведёт себя как `noeviction`.
- AOF `everysec` — потеря около 1 с; репликация асинхронная.
- Cluster: 16384 слота, hash tag `{...}` для multi-key.
- MULTI/EXEC без отката; pipelining без атомарности; Lua атомарен.
- Pub/Sub — at-most-once; Streams — с хранением и ACK.
