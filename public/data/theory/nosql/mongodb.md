MongoDB — самая популярная документная БД: данные хранятся как BSON-документы в коллекциях, схема гибкая, а масштабирование строится на replica set и шардировании. На собеседовании обычно спрашивают про моделирование (embedding или referencing), индексы и правило ESR, aggregation pipeline, write и read concern, а также выбор shard key.

## Документы, BSON и ObjectId

**BSON** — бинарное представление JSON с дополнительными типами: `Date`, `ObjectId`, `Decimal128`, `Int64`, `BinData`. Максимальный размер документа — **16 МБ**.

Каждый документ имеет уникальное поле `_id`. По умолчанию это **ObjectId** из 12 байт: 4 байта timestamp в секундах, 5 байт случайного значения и 3 байта счётчика. Он генерируется на клиенте без координации и примерно монотонно растёт.

```javascript
db.users.insertOne({ name: "Ann", age: 25, tags: ["vip"] })
db.users.find({ age: { $gte: 18, $lt: 30 }, tags: "vip" })
db.users.find({ $or: [{ city: "Moscow" }, { age: { $gt: 60 } }] }, { name: 1, _id: 0 })
db.orders.updateOne({ _id: 1 }, { $inc: { qty: 2 }, $push: { log: "added" } })
```

Изменения одного документа атомарны, включая вложенные поля и массивы.

## Моделирование: embedding или referencing

| Критерий | Встраивать (embed) | Ссылаться (reference) |
|---|---|---|
| Связь | «Содержит», один-к-немногим | Один-ко-многим без ограничения, многие-ко-многим |
| Чтение | Данные нужны вместе | Части запрашиваются отдельно |
| Рост | Ограниченный массив | Неограниченный рост (комментарии, логи) |
| Обновления | Редкие, атомарно с родителем | Частые, независимые |

Анти-паттерн — **unbounded array**: миллионы комментариев внутри поста упрутся в лимит 16 МБ. Решения: отдельная коллекция со ссылкой `postId`, **bucket pattern** (группы по N элементов) и **subset pattern** (в посте только последние 10 комментариев).

## Индексы

- Одиночные, составные (compound), multikey (по массивам), текстовые, геоиндексы, hashed.
- **TTL-индекс** — удаляет документы по полю Date (монитор запускается примерно раз в 60 секунд).
- Частичные (`partialFilterExpression`) и уникальные индексы.

Составной индекс `{ a: 1, b: 1, c: 1 }` работает по **префиксам**: `a`, `a+b`, `a+b+c`. Запрос только по `b` его эффективно не использует.

**Правило ESR**: в составном индексе сначала поля с **Equality**, затем **Sort**, затем **Range**.

```javascript
db.orders.find({ status: "A", qty: { $gt: 10 } }).sort({ date: -1 })
db.orders.createIndex({ status: 1, date: -1, qty: 1 })   // E, S, R
db.sessions.createIndex({ createdAt: 1 }, { expireAfterSeconds: 3600 })
```

У multikey-индекса есть ограничение: в составном индексе у одного документа массивом может быть только одно из полей. План запроса проверяют через `explain("executionStats")`: ищут `IXSCAN` вместо `COLLSCAN` и сравнивают `totalDocsExamined` с `nReturned`.

## Aggregation pipeline

Пайплайн — последовательность стадий, каждая из которых преобразует поток документов.

```javascript
db.orders.aggregate([
  { $match: { status: "paid" } },                 // фильтр как можно раньше, по индексу
  { $unwind: "$items" },                          // один документ на элемент массива
  { $group: { _id: "$items.sku", total: { $sum: "$items.qty" } } },
  { $sort: { total: -1 } },
  { $limit: 10 },
  { $lookup: { from: "products", localField: "_id",
               foreignField: "sku", as: "product" } }
])
```

`$lookup` — это left outer join с другой коллекцией. Частое использование на горячем пути говорит о том, что модель стоит пересмотреть. `$match` и `$sort` в начале пайплайна могут использовать индексы. Стадии ограничены 100 МБ памяти, если не включён `allowDiskUse` (в новых версиях он включён по умолчанию).

## Replica set, write и read concern

Replica set — один **primary** (принимает записи) и несколько **secondary**, которые применяют **oplog**. При потере primary узлы, у которых есть **большинство голосов**, выбирают новый primary. Поэтому членов нечётное число, и их разносят минимум по трём площадкам.

| Настройка | Значение | Смысл |
|---|---|---|
| writeConcern | `w: 1` | Подтвердил primary; при failover возможен rollback |
| writeConcern | `w: "majority"` | Подтвердило большинство; запись переживёт failover |
| readConcern | `local` | Последние данные узла, могут откатиться |
| readConcern | `majority` | Только подтверждённые большинством |
| readConcern | `linearizable` | Самая сильная гарантия, только на primary |
| readPreference | `secondary` / `nearest` | Разгрузка primary ценой устаревших данных |

Для read-your-writes используют чтение с primary или **causally consistent sessions**.

## Шардирование и транзакции

Шардированный кластер состоит из шардов (каждый — replica set), роутеров `mongos` и config servers. Данные делятся на chunk-и по **shard key**:

- высокая кардинальность и равномерная частота значений;
- ключ присутствует в частых запросах, чтобы они были targeted, а не scatter-gather;
- монотонный ключ (timestamp, ObjectId) при range-шардировании создаёт **hot shard**. Решение — hashed shard key или составной ключ.

Начиная с MongoDB 5.0 ключ можно сменить через `reshardCollection`, но это дорогая операция.

**Многодокументные транзакции** доступны с 4.0 (replica set) и 4.2 (шардированный кластер). По умолчанию они ограничены 60 секундами и дороже одиночных операций. Хорошая модель данных обходится атомарностью одного документа в большинстве случаев.

## Частые анти-паттерны

- **Реляционная схема в MongoDB**: десятки коллекций и `$lookup` на каждый запрос. Документная модель выигрывает, только когда документ совпадает с единицей чтения.
- **Запросы без индекса**: на больших коллекциях COLLSCAN съедает диск и кэш WiredTiger. Профилировщик (`db.setProfilingLevel(1)`) и `explain` находят такие запросы.
- **Слишком много индексов**: каждый индекс замедляет запись и занимает RAM. Неиспользуемые находят через `$indexStats`.
- **`skip` для глубокой пагинации**: сервер всё равно проходит пропущенные документы. Лучше range-пагинация по индексированному полю: `find({ _id: { $gt: lastId } }).limit(20)`.
- **Огромные документы**, которые читают ради пары полей. Помогают проекции и разделение на «горячую» и «холодную» части.

## Частые вопросы на собеседовании

- Когда встраивать, а когда ссылаться? → Встраивать, если данные читаются вместе и массив ограничен; ссылаться при неограниченном росте и независимом доступе.
- Что такое ESR? → Порядок полей составного индекса: Equality, Sort, Range.
- Как выбирают primary? → Голосованием, нужно большинство голосующих членов. При чётном разделении primary не будет.
- Чем `w: 1` отличается от `w: "majority"`? → Первое может откатиться при failover, второе — нет.
- Как выбрать shard key? → Кардинальность, равномерность, наличие в запросах, отсутствие монотонности.
- Есть ли в MongoDB транзакции? → Да, многодокументные ACID, но с лимитами и накладными расходами.

## Шпаргалка

- BSON, лимит 16 МБ, ObjectId: время + случайное значение + счётчик.
- Индексы работают по префиксам; ESR; TTL-индекс по полю Date.
- `explain`: `IXSCAN` хорошо, `COLLSCAN` плохо.
- Pipeline: `$match` → `$unwind` → `$group` → `$sort` → `$lookup` (left join).
- Replica set: primary + secondary, oplog, выборы по большинству.
- `w: "majority"` + `readConcern: "majority"` — данные не откатятся.
- Shard key: кардинальность, равномерность, targeted-запросы, без монотонности.
