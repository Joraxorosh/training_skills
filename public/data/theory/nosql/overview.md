NoSQL — это общее название для хранилищ, которые отказываются от реляционной модели (или части её гарантий) ради горизонтального масштабирования, гибкой схемы или специализированного доступа к данным. На собеседовании редко спрашивают «что лучше, SQL или NoSQL». Чаще просят объяснить, **какое хранилище выбрать под конкретный паттерн доступа** и какую консистентность вы при этом получаете.

## Основные типы NoSQL

| Тип | Модель данных | Примеры | Типичные задачи |
|---|---|---|---|
| Key-value | Ключ → непрозрачное значение | Redis, Memcached, DynamoDB | Кэш, сессии, счётчики, rate limiting |
| Документный | JSON/BSON-документы с вложенностью | MongoDB, Couchbase, CouchDB | Каталоги, профили, контент с разной структурой |
| Wide-column | Партиции со строками, отсортированными по ключу | Cassandra, ScyllaDB, HBase | Интенсивная запись, история сообщений, IoT |
| Графовый | Узлы и рёбра со свойствами | Neo4j, Amazon Neptune | Социальные связи, рекомендации, антифрод |
| Поисковый | Инвертированный индекс | Elasticsearch, OpenSearch | Полнотекстовый поиск, логи, фасеты |
| Time-series | Точки с временной меткой | InfluxDB, TimescaleDB, Prometheus | Метрики, телеметрия, ретеншен по времени |

Отдельно стоят колоночные OLAP-СУБД (ClickHouse): это не NoSQL в классическом смысле, а аналитические базы с SQL, но их часто обсуждают рядом.

## Когда NoSQL, а когда реляционная БД

Реляционная БД — разумный выбор по умолчанию: ACID-транзакции, JOIN, внешние ключи, ad-hoc запросы. NoSQL оправдан, когда:

- объём записи или данных не помещается в один сервер, и нужно шардирование «из коробки»;
- паттерны доступа известны заранее и простые (по ключу, по партиции);
- структура данных сильно варьируется, и жёсткая схема мешает;
- нужна специализированная операция: полнотекстовый поиск, обход графа, TTL-кэш.

И наоборот, деньги, складские остатки, сложные отчёты с произвольными JOIN — территория реляционных БД. Многие системы используют **polyglot persistence**: PostgreSQL как источник правды, Redis для кэша, Elasticsearch для поиска, ClickHouse для аналитики. Цена такого подхода — синхронизация данных между хранилищами (CDC, очереди) и рост операционной сложности.

## CAP и PACELC

**CAP**: в распределённой системе при сетевом разделении (Partition) нельзя одновременно гарантировать консистентность (Consistency — каждое чтение видит последнюю запись, то есть линеаризуемость) и доступность (Availability — каждый запрос к живому узлу получает ответ).

- **CP** — при разделении часть узлов отказывает, но данные не расходятся (MongoDB с majority, etcd, ZooKeeper).
- **AP** — все узлы отвечают, но могут отдать устаревшее (Cassandra с ONE, DynamoDB по умолчанию).

Partition в реальной сети не выбирают — он случается. Поэтому «CA-система» имеет смысл только для одного узла. Многие БД настраиваемы: та же Cassandra с QUORUM/QUORUM ведёт себя гораздо ближе к CP.

**PACELC** дополняет CAP: если разделения нет (Else), остаётся выбор между задержкой (Latency) и консистентностью. Синхронное ожидание реплик делает операции медленнее.

> C в CAP и C в ACID — разные вещи. В ACID это соблюдение инвариантов и ограничений, в CAP — линеаризуемость чтений.

## ACID, BASE и eventual consistency

**ACID** — Atomicity, Consistency, Isolation, Durability. **BASE** — Basically Available, Soft state, Eventual consistency: система всегда отвечает, состояние реплик может временно расходиться, но со временем сходится.

**Eventual consistency** гарантирует только сходимость. Без дополнительных гарантий возможны аномалии:

- чтение сразу после записи возвращает старое значение;
- пользователь не видит собственный комментарий (нарушение **read-your-writes**);
- повторное чтение возвращает более старую версию (нарушение **monotonic reads**).

Кворумы дают более сильную гарантию: при N репликах, W подтверждениях записи и R опрошенных при чтении условие `R + W > N` обеспечивает пересечение множеств реплик.

```text
N = 3, W = 2, R = 2  ->  2 + 2 > 3, чтение увидит последнюю подтверждённую запись
N = 3, W = 1, R = 1  ->  1 + 1 < 3, возможно устаревшее чтение
```

Конфликты параллельных записей решают через **last-write-wins** (просто, но молча теряет обновления при расхождении часов), векторные часы с siblings или CRDT.

## Schema-on-read и денормализация

В реляционной БД схема проверяется при записи (**schema-on-write**). В документных и key-value хранилищах структура интерпретируется приложением при чтении (**schema-on-read**): документы одной коллекции могут иметь разные поля. Это ускоряет эволюцию, но переносит валидацию и миграции в код. В MongoDB при этом можно включить JSON Schema validation.

**Денормализация** — сознательное дублирование данных, чтобы обслужить запрос одним чтением без JOIN:

```json
{
  "_id": "post-17",
  "title": "Про индексы",
  "author": { "id": 42, "name": "Ann Smith" }
}
```

Чтение быстрое, но при смене имени автора нужно обновить все его посты. Поэтому дублируют обычно редко меняющиеся поля, а модель строят от запросов, а не от сущностей.

## Как выбрать хранилище на практике

На system design интервью выбор БД стоит обосновать вопросами, а не названием модной технологии:

1. **Какие запросы?** По ключу, по диапазону внутри сущности, полнотекстовые, обходы связей, агрегации по миллиардам строк.
2. **Какое соотношение чтения и записи?** Write-heavy нагрузка тяготеет к LSM-хранилищам (Cassandra), read-heavy — к кэшу перед основной БД.
3. **Какая консистентность нужна?** Баланс счёта требует линеаризуемости, счётчик лайков переживёт eventual consistency.
4. **Какой объём и рост?** Десятки гигабайт спокойно живут в одном PostgreSQL. Сотни терабайт с равномерной записью — повод для шардирования.
5. **Кто будет эксплуатировать?** Каждое новое хранилище — это бэкапы, мониторинг, обновления и дежурства.

Пример: мессенджер. Профили и настройки — PostgreSQL. История сообщений по чату — Cassandra с партицией `chat_id` и бакетом по времени. Онлайн-статусы и счётчики непрочитанных — Redis. Поиск по сообщениям — Elasticsearch, наполняемый из очереди событий.

> Хороший ответ на интервью называет не только выбранную БД, но и то, чем вы платите за этот выбор.

## Частые вопросы на собеседовании

- Чем NoSQL отличается от SQL? → Не «лучше или хуже», а другая модель данных и другие гарантии: проще масштабировать горизонтально, но меньше гибкости запросов и транзакционности.
- Объясните CAP. → При сетевом разделении приходится выбирать между консистентностью и доступностью. Без разделения можно иметь обе.
- Что такое eventual consistency и какие аномалии она допускает? → Реплики со временем сходятся. Возможны устаревшие чтения, нарушения read-your-writes и monotonic reads.
- Когда вы бы не выбрали NoSQL? → Финансовые транзакции, сложные отчёты с JOIN, неизвестные заранее запросы.
- Что такое polyglot persistence и в чём его минус? → Разные хранилища под разные задачи. Минусы — синхронизация данных и эксплуатационная сложность.
- Как кворум даёт консистентность? → Условие `R + W > N` гарантирует, что чтение заденет хотя бы одну реплику со свежей записью.

## Шпаргалка

- Key-value — доступ по ключу; документная — JSON с вложенностью; wide-column — запись и партиции; граф — связи; поиск — инвертированный индекс; time-series — метрики.
- Реляционная БД — выбор по умолчанию; NoSQL — под конкретный паттерн доступа и масштаб.
- CAP: при partition выбираем C или A; PACELC: иначе выбираем L или C.
- BASE = Basically Available, Soft state, Eventual consistency.
- `R + W > N` — пересечение кворумов.
- LWW прост, но теряет обновления; альтернативы — векторные часы и CRDT.
- Денормализация ускоряет чтение и усложняет запись.
