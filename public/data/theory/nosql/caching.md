Кэш — самый дешёвый способ снизить задержку и нагрузку на БД, но и источник самых коварных багов: устаревших данных, лавин промахов и гонок. На собеседовании по system design почти всегда спрашивают, какой паттерн кэширования выбрать, как инвалидировать данные и как защититься от stampede, penetration и avalanche.

## Паттерны чтения и записи

| Паттерн | Как работает | Плюсы | Минусы |
|---|---|---|---|
| Cache-aside (lazy loading) | Приложение читает кэш; при промахе — БД, затем кладёт в кэш | Просто, кэшируется только нужное | Первый запрос медленный, возможны гонки |
| Read-through | Кэш-библиотека сама загружает из БД при промахе | Логика в одном месте | Нужен провайдер с загрузчиком |
| Write-through | Запись синхронно в кэш и в БД | Кэш всегда актуален | Задержка записи, кэшируется лишнее |
| Write-behind (write-back) | Запись в кэш, в БД — асинхронно пачками | Очень быстрая запись | Риск потери данных, сложная консистентность |
| Write-around | Запись только в БД, кэш заполняется при чтении | Не засоряет кэш | Первое чтение после записи — промах |

Cache-aside — самый распространённый вариант:

```python
def get_user(uid):
    key = f"user:{uid}"
    user = cache.get(key)
    if user is None:
        user = db.query_user(uid)
        cache.set(key, user, ttl=300 + random.randint(0, 30))
    return user

def update_user(uid, data):
    db.update_user(uid, data)    # сначала источник правды
    cache.delete(f"user:{uid}")  # потом инвалидация
```

## Инвалидация и консистентность

«Есть только две сложные вещи в информатике: инвалидация кэша и именование». Основные стратегии:

- **TTL** — простая верхняя граница устаревания. Её ставят всегда, даже при явной инвалидации, как страховку.
- **Явное удаление** при записи. Удалять надёжнее, чем перезаписывать: два параллельных `set` могут прийти в обратном порядке, а `delete` идемпотентен.
- **Порядок** — сначала БД, потом удаление ключа. Если сначала удалить ключ, читатель успеет положить в кэш старое значение до обновления БД.
- **Версионирование** — ключ включает версию (`product:42:v17`) или запись в кэш идёт только при более новой версии.
- **CDC-инвалидация** — подписка на журнал БД (Debezium по binlog/WAL). Ловит изменения в обход приложения и упорядочена по коммитам, но асинхронна.

Остаточная гонка в cache-aside: читатель A получил промах и прочитал старое значение, писатель B обновил БД и удалил ключ, а A положил старое значение в кэш. Окно маленькое; его сужают коротким TTL, **delayed double delete** (повторное удаление через несколько сотен миллисекунд) или CDC.

> Кэш почти никогда не бывает строго консистентным с БД. Правильный вопрос — сколько устаревания допустимо для этих данных.

## Stampede, penetration, avalanche

| Проблема | Что происходит | Решения |
|---|---|---|
| Stampede (dog-piling) | Истёк популярный ключ, и толпа запросов одновременно пересчитывает его | Мьютекс на пересчёт, probabilistic early expiration, stale-while-revalidate |
| Penetration | Запросы к несуществующим ключам всегда проходят в БД | Negative caching с коротким TTL, Bloom-фильтр, валидация входных данных |
| Avalanche | Массовое одновременное истечение ключей или падение кэш-узла | Jitter TTL, прогрев, HA-кэш, circuit breaker и rate limit на БД |
| Hot key | Один ключ перегружает один шард | Локальный L1-кэш, копии ключа с суффиксами, read-реплики |

**Мьютекс**: только получивший лок пересчитывает значение, остальные ждут, повторяют чтение или отдают устаревшее значение.

```text
SET lock:product:42 <token> NX PX 5000
```

**Probabilistic early expiration (XFetch)**: каждый запрос с растущей вероятностью пересчитывает значение до истечения TTL. Блокировки не нужны.

```python
if now - delta * beta * math.log(random.random()) >= expiry:
    value = recompute()   # delta — время пересчёта, beta обычно равен 1
```

**Bloom-фильтр** отвечает «точно нет» или «возможно, есть»: ложноположительные ответы бывают, ложноотрицательных нет, а удаление в классическом варианте невозможно.

## Выбор TTL и вытеснение

- TTL определяется допустимым устареванием: курсы валют — секунды, справочник стран — часы или сутки.
- Добавляйте **jitter** (±10%), чтобы ключи не истекали одновременно.
- Negative caching — с коротким TTL, иначе только что созданный объект долго будет «не найден».
- Политика вытеснения: **LRU** вымывается однократными сканами, **LFU** устойчивее к ним. В Redis для кэша обычно ставят `allkeys-lru` или `allkeys-lfu`.

## Локальный и распределённый кэш; Memcached и Redis

| | Локальный (in-process) | Распределённый (Redis, Memcached) |
|---|---|---|
| Задержка | Наносекунды, без сети | Около миллисекунды, сеть и сериализация |
| Консистентность между инстансами | У каждого своя копия | Общая копия |
| Объём | Ограничен heap процесса | Масштабируется шардированием |
| Инвалидация | Сложнее: pub/sub, короткий TTL | Одно удаление ключа |

Часто используют двухуровневую схему: L1 локально (Caffeine, in-memory LRU) с коротким TTL и L2 в Redis.

**Memcached** — простой многопоточный кэш «ключ → байты» без персистентности и встроенной репликации. **Redis** выполняет команды в одном потоке, но предлагает структуры данных, TTL, персистентность, репликацию, Cluster, Lua и pub/sub. Сегодня по умолчанию обычно выбирают Redis, а Memcached — когда нужен только очень простой кэш с вертикальным масштабированием по ядрам.

## Уровни кэширования и метрики

Кэш бывает на каждом слое системы, и вопрос «где кэшировать» не менее важен, чем «как»:

- **Браузер и CDN** — HTTP-заголовки `Cache-Control`, `ETag`, `max-age`, `stale-while-revalidate`. Идеально для статики и публичных ответов API.
- **Reverse proxy** — nginx `proxy_cache`, Varnish: кэш целых HTTP-ответов перед приложением.
- **Приложение** — локальный кэш и Redis для объектов, результатов запросов, отрендеренных фрагментов.
- **БД** — buffer pool и page cache ОС. Его не нужно дублировать: горячие страницы и так в памяти.

Чем ближе к пользователю кэш, тем он эффективнее, но тем сложнее его инвалидировать.

Что мониторить:

- **Hit rate** — доля попаданий. Падение hit rate часто первым сигнализирует о проблеме.
- **Evictions** — растущее число вытеснений говорит о нехватке памяти.
- **Задержка** p99 команд кэша и **память** (фрагментация, big keys).
- **Нагрузка на БД** при холодном кэше: система должна переживать полный промах хотя бы в деградированном режиме. Иначе рестарт кэша кладёт БД.

Холодный старт смягчают прогревом популярных ключей и постепенным переключением трафика.

## Частые вопросы на собеседовании

- Какой паттерн кэширования вы выберете? → По умолчанию cache-aside с TTL и удалением ключа после записи в БД; write-through — если важна свежесть кэша.
- Почему удалять ключ, а не обновлять? → Параллельные `set` приходят в произвольном порядке, а удаление идемпотентно.
- Как защититься от stampede? → Мьютекс на пересчёт, XFetch, stale-while-revalidate.
- Чем penetration отличается от avalanche? → Penetration — промахи по несуществующим ключам; avalanche — массовое одновременное истечение ключей или падение кэша.
- Как бороться с hot key? → Локальный кэш, размножение ключа по шардам, read-реплики.
- Memcached или Redis? → Redis богаче (структуры, персистентность, кластер); Memcached проще и многопоточен.

## Шпаргалка

- Cache-aside: читаем кэш → промах → БД → кэш с TTL.
- При записи: сначала БД, потом удаление ключа.
- TTL всегда, с jitter.
- Stampede → мьютекс, XFetch; penetration → negative cache, Bloom; avalanche → jitter, HA.
- Hot key → L1-кэш и копии ключа.
- LFU устойчивее LRU к сканам.
- CDC-инвалидация ловит все изменения, но асинхронна.
